# 3.1. Что такое API и HTTP

## Зачем это нужно

Тестировщик, который тестирует только через UI, всегда на шаг медленнее и менее стабилен, чем тот, кто умеет проверять то же самое напрямую через API. Клик по кнопке в браузере в итоге превращается в один или несколько HTTP-запросов — и если ты понимаешь, что происходит на этом уровне, ты можешь проверить бизнес-логику быстрее, надёжнее и без танцев с локаторами.

## Теория

**API (Application Programming Interface)** — это набор правил, по которым одна программа может обращаться к другой за данными или функциональностью. Можно провести аналогию с меню в кафе: тебе не обязательно знать, как устроена кухня — достаточно знать, что можно заказать (доступные "методы") и что ты получишь в ответ.

В вебе самый распространённый вид API — **REST API поверх HTTP**. Именно с ним мы и будем работать весь модуль. Есть и другие подходы (SOAP, GraphQL, gRPC, WebSocket), но в большинстве коммерческих проектов на позиции QA automation тебе для начала хватит HTTP/REST.

### Клиент-серверная модель

Всё взаимодействие строится по схеме "клиент — сервер":

- **Клиент** — тот, кто инициирует запрос (браузер, мобильное приложение, твой тест на `requests`).
- **Сервер** — тот, кто принимает запрос, что-то с ним делает (читает из базы, считает, валидирует) и отправляет ответ.

Клиент отправляет **запрос (request)**, сервер возвращает **ответ (response)**. Это применимо и когда ты открываешь сайт в браузере, и когда пишешь тест — разница только в том, кто выступает клиентом.

### Из чего состоит URL

Прежде чем разбирать запросы и ответы, полезно разобрать по частям адрес, по которому они отправляются — он будет встречаться в каждом уроке этого модуля:

```
https://jsonplaceholder.typicode.com/comments?postId=1
```

- **Схема** (`http` или `https`) — по какому протоколу идёт соединение. `https` — тот же HTTP, но поверх зашифрованного TLS-соединения; в реальных проектах API почти всегда доступны только по `https`.
- **Хост** — адрес сервера (`jsonplaceholder.typicode.com`), к которому идёт запрос.
- **Путь** — какой ресурс на этом сервере запрашивается (`/comments`).
- **Query-строка** — необязательные параметры после `?`, в формате `ключ=значение`; несколько параметров соединяются через `&` (например, `?postId=1&_limit=5`).

### HTTP: протокол, на котором всё это работает

**HTTP (HyperText Transfer Protocol)** — протокол прикладного уровня, по которому передаются запросы и ответы между клиентом и сервером.

### HTTP не хранит состояние (stateless)

Каждый запрос обрабатывается независимо от предыдущих — сервер не "помнит" тебя между запросами сам по себе. Например, если тебе нужно снова получить те же данные, что и в прошлый раз, все нужные параметры придётся передать заново — сервер не хранит контекст предыдущего запроса:

```bash
curl "https://jsonplaceholder.typicode.com/posts?userId=1"   # сервер ничего не "запомнил" из прошлых запросов
curl "https://jsonplaceholder.typicode.com/posts?userId=1"   # поэтому userId=1 нужно передать заново
```

Именно из-за stateless-природы HTTP появились механизмы вроде токенов и cookie — они переносят "память" о состоянии на сторону клиента (который сам прикладывает нужные данные к каждому запросу) или в отдельное хранилище на сервере. Подробнее об этом — в уроке 3.4 про авторизацию.

### Структура запроса

Запрос состоит из метода, URL, заголовков и (не всегда) тела. Упрощённо он выглядит так:

```
GET /users/123 HTTP/1.1
Host: jsonplaceholder.typicode.com
Accept: application/json
```

Первая строка — метод (`GET`) и путь (`/users/123`). Дальше — заголовки: `Host` (на какой домен идёт запрос) и `Accept` (в каком формате клиент готов получить ответ). Про методы подробно — в следующем уроке, про заголовки — в уроке 3.4.

### Структура ответа

Ответ состоит из статус-кода, заголовков и тела:

```
HTTP/1.1 200 OK
Content-Type: application/json

{
  "id": 123,
  "name": "Leanne Graham"
}
```

Первая строка — статус-код (`200`) и его текстовая расшифровка (`OK`). Дальше — заголовки ответа (здесь `Content-Type` говорит, что тело — JSON), а после пустой строки — само тело. Про статус-коды подробно — в уроке 3.3.

Когда ты в тесте пишешь `requests.get(...)`, библиотека `requests` формирует именно такой запрос за тебя и парсит именно такой ответ — тебе не нужно писать эти строки руками. Но полезно понимать, что происходит "под капотом", когда что-то идёт не так (например, сервер вернул не тот `Content-Type`, а тест падает на `response.json()`).

## Пример

В нашем общем репозитории (`boilerplate/`) API-тесты ходят на публичный демо-сервис [jsonplaceholder.typicode.com](https://jsonplaceholder.typicode.com). Это фейковый REST API: он ничего реально не сохраняет, но отвечает как настоящий сервер — с корректными статус-кодами и JSON-телом. Именно поэтому он удобен для учёбы: не нужно поднимать локальный сервер или получать доступ к боевому стенду.

```bash
curl https://jsonplaceholder.typicode.com/users/1
```

Ответ придёт в формате JSON — том самом, который мы будем разбирать в тестах весь модуль.

## Частые ошибки

- Путать API вообще и REST API поверх HTTP — думать, что "API" обязательно значит "HTTP-запрос". API — понятие шире (например, методы класса в Python — тоже API), просто в контексте этого модуля мы всегда говорим про HTTP.
- Считать, что раз HTTP stateless, то "сессии" и "токены авторизации" — что-то незначительное. Наоборот: именно из-за stateless-природы HTTP их изобрели, чтобы сервер вообще мог отличать один твой запрос от другого.
- Игнорировать заголовки ответа и опираться только на тело. Например, `Content-Type` подсказывает, чего вообще ожидать в теле — JSON это, HTML или что-то ещё.

## Мини-задания

1. **Разминка.** Выполни `curl https://jsonplaceholder.typicode.com/users/1` без флагов и посмотри, что пришло — только тело ответа. Затем выполни ту же команду с флагом `-i` и определи, какая часть структуры ответа из "Теории" стала видна дополнительно.
2. **Основное.** Выполни `curl -i https://jsonplaceholder.typicode.com/users/1`. Найди в выводе статус-строку, заголовок `Content-Type` и тело ответа. Определи, сколько полей верхнего уровня в JSON-объекте пользователя и есть ли среди них вложенные объекты.
3. **Ближе к практике.** Выполни `curl -i https://jsonplaceholder.typicode.com/users/99999` (заведомо несуществующий пользователь) и сравни вывод с результатом задания 2: чем отличается статус-строка, изменился ли `Content-Type`, что теперь в теле ответа. Запиши, по каким именно частям ответа (а не "на глаз") тест должен был бы отличать "пользователь найден" от "пользователь не найден".
4. **Со звёздочкой.** Выполни `curl -i https://jsonplaceholder.typicode.com/guide/` — это уже не API-эндпоинт, а обычная страница документации. Сравни её `Content-Type` с тем, что был у `/users/1`, и объясни, почему `response.json()` в тесте упал бы с ошибкой, если бы вместо адреса API-эндпоинта в коде по ошибке оказался этот адрес.
