# 3.1. Что такое API и HTTP

## Зачем это нужно

Тестировщик, который тестирует только через UI, всегда на шаг медленнее и менее стабилен, чем тот, кто умеет проверять то же самое напрямую через API. Клик по кнопке в браузере в итоге превращается в один или несколько HTTP-запросов — и если ты понимаешь, что происходит на этом уровне, ты можешь проверить бизнес-логику быстрее, надёжнее и без танцев с локаторами.

## Теория

**API (Application Programming Interface)** — это набор правил, по которым одна программа может обращаться к другой за данными или функциональностью. Можно провести аналогию с меню в кафе: тебе не обязательно знать, как устроена кухня — достаточно знать, что можно заказать (доступные "методы") и что ты получишь в ответ.

В вебе самый распространённый вид API — **REST API поверх HTTP**. Именно с ним мы и будем работать весь модуль. Есть и другие подходы (SOAP, GraphQL, gRPC, WebSocket), но в большинстве коммерческих проектов на позиции QA automation тебе для начала хватит HTTP/REST.

### Клиент-серверная модель

Всё взаимодействие строится по схеме "клиент — сервер":

- **Клиент** — тот, кто инициирует запрос (браузер, мобильное приложение, твой тест на `requests`).
- **Сервер** — тот, кто принимает запрос, что-то с ним делает (читает из базы, считает, валидирует) и отправляет ответ.

Клиент отправляет **запрос (request)**, сервер возвращает **ответ (response)**. Это применимо и когда ты открываешь сайт в браузере, и когда пишешь тест — разница только в том, кто выступает клиентом.

### HTTP: протокол, на котором всё это работает

**HTTP (HyperText Transfer Protocol)** — протокол прикладного уровня, по которому передаются запросы и ответы между клиентом и сервером. Две вещи, которые важно понимать про HTTP с самого начала:

1. **HTTP без состояния (stateless).** Каждый запрос обрабатывается независимо от предыдущих — сервер не "помнит" тебя между запросами сам по себе. Именно поэтому существуют механизмы вроде токенов и cookie — они переносят "память" о состоянии на сторону клиента или в отдельное хранилище на сервере.
2. **У запроса и ответа есть чёткая структура.** Запрос состоит из метода, URL, заголовков и (не всегда) тела. Ответ — из статус-кода, заголовков и тела. Про методы и статус-коды — в следующих двух уроках.

### Как это выглядит "на проводе"

Упрощённо HTTP-запрос выглядит так:

```
GET /users/123 HTTP/1.1
Host: jsonplaceholder.typicode.com
Accept: application/json
```

А ответ — так:

```
HTTP/1.1 200 OK
Content-Type: application/json

{
  "id": 123,
  "name": "Leanne Graham"
}
```

Когда ты в тесте пишешь `requests.get(...)`, библиотека `requests` формирует именно такой запрос за тебя и парсит именно такой ответ — тебе не нужно писать эти строки руками. Но полезно понимать, что происходит "под капотом", когда что-то идёт не так (например, сервер вернул не тот `Content-Type`, а тест падает на `response.json()`).

## Пример

В нашем общем репозитории (`boilerplate/`) API-тесты ходят на публичный демо-сервис [jsonplaceholder.typicode.com](https://jsonplaceholder.typicode.com). Это фейковый REST API: он ничего реально не сохраняет, но отвечает как настоящий сервер — с корректными статус-кодами и JSON-телом. Именно поэтому он удобен для учёбы: не нужно поднимать локальный сервер или получать доступ к боевому стенду.

```bash
curl https://jsonplaceholder.typicode.com/users/1
```

Ответ придёт в формате JSON — том самом, который мы будем разбирать в тестах весь модуль.

## Частые ошибки

- Путать API вообще и REST API поверх HTTP — думать, что "API" обязательно значит "HTTP-запрос". API — понятие шире (например, методы класса в Python — тоже API), просто в контексте этого модуля мы всегда говорим про HTTP.
- Считать, что раз HTTP stateless, то "сессии" и "токены авторизации" — что-то незначительное. Наоборот: именно из-за stateless-природы HTTP их изобрели, чтобы сервер вообще мог отличать один твой запрос от другого.
- Игнорировать заголовки ответа и опираться только на тело. Например, `Content-Type` подсказывает, чего вообще ожидать в теле — JSON это, HTML или что-то ещё.

## Мини-задание

Выполни `curl -i https://jsonplaceholder.typicode.com/users/1` (флаг `-i` покажет заголовки ответа). Найди в выводе статус-строку, `Content-Type` и тело ответа. Определи, сколько полей верхнего уровня в JSON-объекте пользователя и есть ли среди них вложенные объекты.
