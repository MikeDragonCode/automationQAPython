# 3.3. Коды состояния HTTP

## Зачем это нужно

Первое, что проверяет почти любой API-тест, — это статус-код ответа. `assert response.status_code == 200` — самая частая строчка в этом модуле. Чтобы писать осмысленные проверки (а не копировать код отовсюду), нужно понимать, что означает каждая группа кодов и какие коды стоит ожидать в каких сценариях, включая "несчастливые" пути.

## Теория

Статус-код — это трёхзначное число в начале ответа сервера, которое коротко сообщает результат обработки запроса. Коды делятся на пять групп по первой цифре.

- **1xx — информационные.** На практике в API-тестах почти не встречаются, можно не запоминать подробно.
- **2xx — успех.** Запрос обработан так, как ожидалось.
  - `200 OK` — успешный запрос (обычно для GET, PUT, PATCH).
  - `201 Created` — ресурс успешно создан (обычно для POST).
  - `204 No Content` — запрос выполнен успешно, но в ответе нет тела (часто встречается после DELETE).
- **3xx — редиректы.** Клиенту нужно сходить по другому адресу. В API-тестах встречается реже, чем в браузерных сценариях.
- **4xx — ошибка на стороне клиента.** Запрос сформирован неправильно, или у клиента нет прав/данных.
  - `400 Bad Request` — некорректный запрос (например, невалидный JSON или отсутствует обязательное поле).
  - `401 Unauthorized` — не пройдена аутентификация (нет токена или он невалиден).
  - `403 Forbidden` — аутентификация пройдена, но прав на это действие нет.
  - `404 Not Found` — ресурс не найден (например, запросили пользователя с несуществующим id).
  - `422 Unprocessable Entity` — запрос синтаксически корректен, но данные не проходят валидацию (например, email не в том формате).
- **5xx — ошибка на стороне сервера.** Что-то сломалось на бэкенде, и это не вина клиента.
  - `500 Internal Server Error` — необработанная ошибка сервера.
  - `502`/`503` — сервер недоступен или перегружен.

### Как увидеть код в ответе

Статус-код — это не часть тела ответа, а отдельное поле, которое видно и в `curl -i` (первая строка вывода), и в `response.status_code` при работе через `requests`:

```bash
curl -i https://jsonplaceholder.typicode.com/users/1      # HTTP/1.1 200 OK  — успешный GET
curl -i https://jsonplaceholder.typicode.com/users/9999   # HTTP/1.1 404 Not Found — такого пользователя нет
```

### Какой код ожидать от какого метода

Коды состояния и HTTP-методы (урок 3.2) связаны: у каждого метода есть "типичный" код успеха, который стоит держать в голове при написании `assert`:

| Метод | Типичный код успеха |
|---|---|
| GET | `200 OK` |
| POST | `201 Created` (ресурс создан) |
| PUT | `200 OK` |
| PATCH | `200 OK` |
| DELETE | `200 OK` или `204 No Content` |

Это не жёсткий стандарт, обязательный для всех API без исключений, — конкретное поведение всегда нужно сверять с документацией сервиса, а не угадывать. Но если тест на успешное создание пользователя ожидает `200`, а не `201` — почти наверняка это тест написан "на автомате", по шаблону других тестов, без сверки со смыслом метода.

### Почему это важно для тестов, а не только "для справки"

Хороший API-тест никогда не проверяет только happy path (успешный сценарий). Не менее важны так называемые "негативные" тесты — когда мы намеренно провоцируем ошибку и проверяем, что сервер отвечает **правильным** кодом ошибки, а не, скажем, `500` там, где должен быть `404`. Если сервер на некорректный запрос возвращает `200 OK` с телом ошибки внутри — это тоже баг, и его тоже можно поймать проверкой статус-кода.

## Пример

В нашем общем репозитории уже есть пример именно такой негативной проверки — тест на несуществующего пользователя, `boilerplate/tests/api/test_users.py`:

```python
@allure.title("Получение несуществующего пользователя возвращает 404")
def test_get_user_not_found(self, users_client: UsersClient):
    with allure.step("Запрашиваем заведомо несуществующего пользователя"):
        response = users_client.get_user_api(user_id=999)

    with allure.step("Проверяем статус-код ответа"):
        assert response.status_code == 404
```

Обрати внимание: тест не проверяет тело ответа — только статус-код. Это осознанный выбор для базовой негативной проверки. Мы разберём этот тест целиком в уроке 3.12, когда познакомимся со всей структурой `UsersClient`.

## Частые ошибки

- Проверять в тесте только happy path и не писать ни одного теста на ошибочный сценарий (несуществующий id, невалидные данные, отсутствие авторизации).
- Путать `401` и `403` — первое означает "я не знаю, кто ты", второе — "я знаю, кто ты, но тебе сюда нельзя".
- Считать, что `200 OK` всегда значит "всё хорошо" — некоторые (плохо спроектированные) API возвращают `200` с телом вида `{"error": "..."}`. В таких случаях тест должен проверять и статус-код, и содержимое тела.
- Не глядя писать `assert response.status_code == 200` для любого запроса — для POST, создающего ресурс, корректный код может быть `201`, а не `200`.

## Мини-задания

1. **Разминка.** Отправь GET на три адреса: `https://jsonplaceholder.typicode.com/users/1` (существует), `https://jsonplaceholder.typicode.com/users/9999` (не существует), `https://jsonplaceholder.typicode.com/posts/9999` (не существует). Для каждого запиши статус-код и определи, к какой группе (2xx/4xx) он относится.
2. **Основное.** Отправь запрос на несуществующий ресурс `https://jsonplaceholder.typicode.com/users/9999` и посмотри на статус-код в ответе. Затем отправь `POST` на `https://jsonplaceholder.typicode.com/posts` с телом `{"title": "test"}` и сравни статус-код с тем, что ты получил на GET-запрос из урока 3.1. Объясни себе, почему коды разные.
3. **Ближе к практике.** Выбери три сценария: получение существующего пользователя, получение несуществующего пользователя, создание нового поста через POST. Для каждого сначала запиши одной строкой "ожидаемый код + почему" (как будущий `assert`), а затем проверь реальным запросом, совпало ли твоё предсказание с ответом сервера.
4. **Со звёздочкой.** Выполни `curl -i https://httpbin.org/status/401` и `curl -i https://httpbin.org/status/403` — httpbin умеет специально возвращать любой запрошенный код по адресу `/status/<код>`. Убедись, что тела ответов пустые, и своими словами повтори разницу между этими двумя кодами (см. "Частые ошибки" выше) — какой из них означает "я не знаю, кто ты", а какой "я знаю, кто ты, но тебе сюда нельзя".
