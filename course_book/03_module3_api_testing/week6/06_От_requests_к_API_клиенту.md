# 3.6. От requests.get() в тесте — к API-клиенту

## Зачем это нужно

Это последний урок недели, и он — мост к недели 7, где ты начнёшь построчно разбирать готовый `APIClient` из общего репозитория. Прежде чем читать чужой код, полезно самому прочувствовать проблему, которую этот код решает: почему в реальных проектах никто не пишет `requests.get(...)` напрямую в теле теста.

## Теория

Возьмём тесты из прошлого урока и представим, что их не три, а тридцать. Что в них будет повторяться раз за разом?

1. **Базовый URL.** `https://jsonplaceholder.typicode.com` — в каждом тесте, к каждому эндпоинту.
2. **Заголовки.** Если API требует авторизации — `Authorization: Bearer ...` нужно передавать в каждый запрос.
3. **Таймаут.** Если ты один раз решил, что таймаут должен быть 10 секунд — нужно не забыть повторить это в каждом вызове.
4. **Путь до ресурса.** Если у тебя есть логика "получить пользователя по id" — она размазана по всем тестам, которые дергают `/users/{id}`, вместо того чтобы жить в одном месте.

Если формат ответа API или базовый URL изменится, тебе придётся находить и чинить это в каждом тесте отдельно. Это и называется **дублированием**, и оно — главный враг поддерживаемости тестов.

### Идея API-клиента

**API-клиент** — это класс (или набор классов), который берёт на себя всю "механику" общения с конкретным API: базовый URL, заголовки, таймаут, формирование пути к ресурсу — и предоставляет тестам простые, понятные методы вроде `get_user(user_id)` вместо голого `requests.get(f"{BASE_URL}/users/{user_id}", headers=..., timeout=...)`.

Тест при этом становится короче и, что важнее, **читается как описание бизнес-логики**, а не как рецепт похода в сеть:

```python
# Было (requests напрямую)
response = requests.get(
    f"{BASE_URL}/users/{user_id}",
    headers={"Authorization": f"Bearer {token}"},
    timeout=10,
)

# Стало (через клиент)
response = users_client.get_user_api(user_id)
```

### requests.Session — первый шаг к клиенту

Прежде чем переходить к полноценному клиенту, важно познакомиться с `requests.Session`. Это объект, который хранит настройки (заголовки, cookie) между несколькими запросами и переиспользует TCP-соединение — то есть решает как минимум проблему "заголовки в каждом запросе":

```python
import requests

session = requests.Session()
session.headers.update({"Authorization": "Bearer my_token"})

response = session.get("https://jsonplaceholder.typicode.com/users/1")
print(response.json())
```

Всё, что попадёт в `session.headers`, будет автоматически подставляться в каждый запрос через эту сессию — заголовок больше не нужно передавать вручную каждый раз.

Но у `requests.Session` нет из коробки понятия `base_url` (в отличие от, например, библиотеки `httpx`, где `httpx.Client(base_url=...)` — встроенная возможность). Поэтому в следующем уроке модуля (уже в рамках недели 7) мы разберём небольшой класс `BaseUrlSession` из `boilerplate/clients/api_client.py`, который добавляет это поведение поверх `requests.Session`, и класс `APIClient`, который строится уже поверх неё.

## Пример

Набросок (пока учебный, не финальный код репозитория) того, к чему мы идём:

```python
import requests


class APIClient:
    def __init__(self, session: requests.Session):
        self.session = session

    def get(self, url: str, params: dict | None = None) -> requests.Response:
        return self.session.get(url, params=params)

    def post(self, url: str, json: dict | None = None) -> requests.Response:
        return self.session.post(url, json=json)


class UsersClient(APIClient):
    def get_user_api(self, user_id: int) -> requests.Response:
        return self.get(f"/users/{user_id}")


session = requests.Session()
session.headers.update({"Authorization": "Bearer my_token"})

users_client = UsersClient(session=session)
response = users_client.get_user_api(user_id=1)
```

Это уже очень близко к реальной структуре `boilerplate/clients/`. В следующем уроке мы посмотрим на настоящий код — со всеми деталями, которых здесь не хватает (`base_url`, таймаут по умолчанию, полный набор HTTP-методов).

## Частые ошибки

- Пытаться сразу спроектировать "идеальный" клиент со всеми возможными фичами вместо того, чтобы начать с простого базового класса и наращивать функциональность по мере необходимости — именно так был построен `APIClient` в общем репозитории.
- Смешивать транспортный уровень (HTTP-запросы) и уровень схем данных (Pydantic) в одном классе — про правильное разделение поговорим в модуле недели 7.
- Считать, что раз в проекте уже есть `APIClient`, велосипед изобретать не нужно — но при этом всё равно писать в тестах `requests.get(...)` напрямую "потому что так быстрее". Именно ради того, чтобы так не делать, клиент и существует.

## Мини-задание

Возьми три теста, которые ты написал в мини-задании урока 3.5 (голый `requests`). Перепиши их вручную так, чтобы весь код похода в сеть (базовый URL, заголовки) был вынесен в отдельную переменную/функцию, а сам тест обращался к ней, а не к `requests` напрямую. Это не обязано быть полноценным классом — цель упражнения в том, чтобы почувствовать, где именно проходит граница между "тестовой логикой" и "механикой HTTP".
