# 3.4. Заголовки и авторизация

## Зачем это нужно

Почти любой API в коммерческом проекте закрыт авторизацией — открытые демо-эндпоинты вроде JSONPlaceholder скорее исключение, чем правило. Если ты не понимаешь, как работает передача токена через заголовки, ты не сможешь протестировать ни один реальный защищённый API.

## Теория

**Заголовки (headers)** — это метаданные запроса и ответа: пары "ключ: значение", которые не являются основным телом сообщения, но управляют тем, как это сообщение обрабатывать. Примеры:

- `Content-Type` — какой формат данных в теле (`application/json`, `application/x-www-form-urlencoded` и т. д.).
- `Accept` — какой формат ответа клиент готов принять.
- `Authorization` — данные для аутентификации запроса.

### Идентификация, аутентификация, авторизация — в чём разница

Эти три термина часто путают:

- **Идентификация** — "кто ты?" (например, ты вводишь email/логин).
- **Аутентификация** — "докажи, что ты это ты" (например, вводишь пароль, или сервер проверяет твой токен).
- **Авторизация** — "что тебе можно?" (даже успешно аутентифицированный пользователь может не иметь прав на конкретное действие — тогда сервер вернёт `403 Forbidden`).

### Основные схемы передачи авторизации в HTTP

**Basic Authentication.** Логин и пароль склеиваются через двоеточие и кодируются в Base64, результат кладётся в заголовок:

```
Authorization: Basic dXNlcm5hbWU6cGFzc3dvcmQ=
```

Base64 — это не шифрование, а просто кодирование, поэтому Basic Auth имеет смысл только поверх HTTPS. Встречается редко — в основном во внутренних или простых системах.

**Сессионная аутентификация (cookie-based).** После логина сервер создаёт сессию и отдаёт клиенту идентификатор сессии в cookie. Дальше браузер сам прикладывает эту cookie к каждому запросу. Классика для традиционных веб-приложений, менее характерна для API, с которыми мы работаем в этом курсе.

**Токен-based (то, с чем ты будешь работать чаще всего).** После успешного логина сервер выдаёт токен (часто — [JWT](https://jwt.io/)), который клиент дальше передаёт в заголовке `Authorization` в каждом запросе:

```
Authorization: Bearer <ACCESS_TOKEN>
```

Слово `Bearer` буквально означает "предъявитель" — сервер доверяет любому, кто предъявит этот токен, не требуя ничего дополнительного при каждом запросе. Именно поэтому токены нужно защищать так же, как пароли: если токен утечёт, им может воспользоваться кто угодно до истечения срока его действия.

Есть и вариант **API Key** — статичный ключ, который выдаётся один раз и передаётся так же через заголовок (`Authorization: ApiKey <KEY>` или собственный заголовок вроде `X-API-Key`). В отличие от JWT, у API-ключа обычно нет встроенного срока действия — это одновременно и удобство, и риск.

### Почему это важно для архитектуры клиента

Забегая вперёд (подробно разберём в модуле недели 7): если API требует авторизации, разумно не передавать заголовок `Authorization` вручную в каждом запросе, а настроить его один раз — на уровне HTTP-сессии. Тогда все запросы через эту сессию будут автоматически "подписаны" токеном. Именно так устроен `requests.Session` — и именно поэтому наш общий репозиторий строит API-клиенты поверх сессии, а не поверх одиночных вызовов `requests.get(...)`.

## Пример

Передать заголовок с токеном через `requests` можно так:

```python
import requests

headers = {"Authorization": "Bearer my_secret_token"}
response = requests.get("https://httpbin.org/get", headers=headers)

print(response.json())  # заголовки будут видны в теле ответа — httpbin их просто отражает
```

JSONPlaceholder, на котором построены тесты в `boilerplate/`, авторизации не требует — это осознанный выбор для учебного проекта: студент должен сосредоточиться на структуре клиента и Pydantic-схемах, а не тратить время на получение тестового токена. Но `APIClient`, который мы разберём в модуле недели 7, спроектирован так, что добавить заголовок `Authorization` для авторизованного API — это одна строчка в месте создания сессии, а не правки во всех методах клиента.

## Частые ошибки

- Путать аутентификацию и авторизацию — считать, что раз запрос прошёл `401`, то дальше точно можно всё (может прийти `403` на конкретное действие).
- Хардкодить токен в тексте теста вместо того, чтобы получать его через логин-эндпоинт или переменные окружения — тестовые токены имеют свойство протухать, а хардкод в репозитории — это ещё и риск утечки в реальных проектах.
- Забывать заголовок `Content-Type: application/json` при отправке JSON вручную (через `curl` или низкоуровневые библиотеки) — без него сервер может не суметь разобрать тело запроса. `requests` при использовании параметра `json=` в `post/put/patch` подставляет этот заголовок сам.
- Путать `Bearer <token>` и просто `<token>` — без префикса `Bearer` многие серверы не распознают заголовок.

## Мини-задание

Выполни `requests.get("https://httpbin.org/headers", headers={"Authorization": "Bearer test123"})` (можно и через `curl -H`) и посмотри на тело ответа: `httpbin.org` отражает обратно все заголовки, которые ты отправил. Убедись, что твой заголовок `Authorization` дошёл до сервера именно в том виде, в котором ты его отправил.
