# 3.2. HTTP-методы: GET, POST, PUT, PATCH, DELETE

## Зачем это нужно

Выбор метода — это не формальность, а часть контракта API. Тест, который дергает `POST` там, где по смыслу должен быть `PATCH`, либо не пройдёт, либо (что хуже) пройдёт, но будет проверять не то, что нужно. Умение по описанию эндпоинта понять, каким методом его вызывать, — база, без которой дальше двигаться некуда.

## Теория

HTTP-метод — это часть запроса, которая говорит серверу, **какое действие** клиент хочет выполнить над ресурсом. В REST-подходе есть негласное соглашение: одни и те же URL по-разному ведут себя в зависимости от метода. Например, `/users/5`:

- `GET /users/5` — получить пользователя с id=5.
- `PUT /users/5` — полностью заменить пользователя с id=5.
- `PATCH /users/5` — частично обновить пользователя с id=5.
- `DELETE /users/5` — удалить пользователя с id=5.

Разберём методы, с которыми ты будешь работать чаще всего.

### GET — получить данные

Используется для чтения. По конвенции GET-запросы не должны изменять состояние на сервере — это называется **безопасный метод** (safe method). Тело запроса у GET, как правило, не используется — все параметры передаются в URL (path-параметры вроде `/users/5` или query-параметры вроде `/users?userId=1`).

```bash
curl https://jsonplaceholder.typicode.com/users/5
```

### POST — создать данные / выполнить действие

Чаще всего используется для создания нового ресурса (например, регистрация пользователя) или для операций, которые не укладываются в "чистый CRUD" (например, `/login`). Данные передаются в теле запроса, обычно в формате JSON, и отправляются на адрес **коллекции**, а не конкретного элемента — новый пользователь создаётся через `POST /users`, а не `POST /users/5` (id ещё не существует, его назначит сервер).

```bash
curl -X POST https://jsonplaceholder.typicode.com/users \
     -H "Content-Type: application/json" \
     -d '{"name": "QA Student"}'
```

### PUT — полностью заменить ресурс

Ожидается, что клиент присылает **все** поля ресурса — сервер полностью заменяет старую версию новой. Если ты пришлёшь только часть полей, по строгой семантике REST остальные должны быть сброшены или обнулены (на практике конкретные API иногда ведут себя мягче — это всегда нужно проверять по документации, а не угадывать).

```bash
curl -X PUT https://jsonplaceholder.typicode.com/users/5 \
     -H "Content-Type: application/json" \
     -d '{"id": 5, "name": "Fully Replaced User"}'
```

### PATCH — частично обновить ресурс

В отличие от PUT, PATCH ожидает только те поля, которые нужно изменить. Остальные поля ресурса остаются как были. Это самый частый метод для операций вида "обнови email пользователя, не трогая остальное".

```bash
curl -X PATCH https://jsonplaceholder.typicode.com/users/5 \
     -H "Content-Type: application/json" \
     -d '{"email": "updated@example.com"}'
```

### DELETE — удалить ресурс

Удаляет ресурс по идентификатору. Тело запроса обычно не нужно.

```bash
curl -X DELETE https://jsonplaceholder.typicode.com/users/5
```

### Идемпотентность — важное свойство

Метод называется **идемпотентным**, если повторный вызов с теми же параметрами не меняет результат по сравнению с одним вызовом. `GET`, `PUT` и `DELETE` идемпотентны (удалить уже удалённый ресурс — то же самое, что удалить его один раз, с точки зрения конечного состояния; выполнить один и тот же `PUT` дважды подряд оставит ресурс в одном и том же состоянии). `POST` — нет: два одинаковых POST-запроса на создание пользователя обычно создадут двух разных пользователей с разными id:

```bash
# каждый из этих двух вызовов создаст СВОЙ ресурс с новым id,
# хотя тело запроса одно и то же
curl -X POST https://jsonplaceholder.typicode.com/users -d '{"name": "QA Student"}'
curl -X POST https://jsonplaceholder.typicode.com/users -d '{"name": "QA Student"}'
```

Это важно держать в голове при написании тестов: если тест несколько раз наступает на один и тот же POST, будь готов к дублям, а вот повторный запуск теста на PUT/DELETE не должен ничего сломать именно благодаря идемпотентности.

## Пример

Отправить эти запросы можно как через `curl`, так и через `requests` (с этой библиотекой подробно познакомимся в уроке 3.5):

```bash
curl https://jsonplaceholder.typicode.com/users/1                     # GET
curl -X POST https://jsonplaceholder.typicode.com/users \
     -H "Content-Type: application/json" \
     -d '{"name": "QA Student"}'                                      # POST
curl -X PATCH https://jsonplaceholder.typicode.com/users/1 \
     -H "Content-Type: application/json" \
     -d '{"name": "Updated Name"}'                                    # PATCH
curl -X DELETE https://jsonplaceholder.typicode.com/users/1           # DELETE
```

Обрати внимание: JSONPlaceholder ничего реально не сохраняет — сервер просто отвечает так, как ответил бы настоящий REST API, но данные не персистятся между запросами. Это нормально для учебных целей: мы проверяем, что API **правильно отвечает** на запрос, а не ведём реальную базу данных.

## Частые ошибки

- Использовать POST везде, "потому что он с телом запроса" — даже для обновления или удаления. Метод должен соответствовать действию, а не быть выбран по удобству.
- Путать PUT и PATCH и присылать в PUT только часть полей, ожидая, что остальные не изменятся, — это поведение PATCH, а не PUT.
- Забывать, что тело GET-запроса — не стандартная практика, и пытаться передать через него JSON вместо query-параметров.
- Не проверять в тестах именно то поведение, которое подразумевает метод (например, для DELETE — что ресурс действительно перестаёт быть доступен по GET после удаления).

## Мини-задания

1. **Разминка.** Отправь `curl` на `https://jsonplaceholder.typicode.com/posts/1` (GET) и `curl -X POST https://jsonplaceholder.typicode.com/posts -d '{"title": "test"}'` (POST). Запиши статус-код каждого ответа и определи, какой из двух методов создал новый ресурс, а какой просто прочитал существующий.
2. **Основное.** Открой документацию [jsonplaceholder.typicode.com/guide](https://jsonplaceholder.typicode.com/guide/) и выпиши для ресурса `/posts` все доступные методы и что каждый из них должен делать, отметив, какие из них идемпотентны. Затем проверь себя на практике: отправь `GET`, `PUT`, `PATCH` и `DELETE` на `https://jsonplaceholder.typicode.com/posts/1`, а `POST` — на `https://jsonplaceholder.typicode.com/posts`. Запиши рядом с каждым методом реальный статус-код и краткое содержание ответа — сверь с тем, что предсказал по документации.
3. **Ближе к практике.** Отправь `PUT` на `https://jsonplaceholder.typicode.com/posts/1` с телом `{"title": "only title"}` (без остальных полей поста), а затем отдельным запросом — `PATCH` на тот же адрес с тем же телом. Сравни, что вернул сервер в обоих случаях, и опиши своими словами разницу в поведении, которую ты увидел между "полной заменой" и "частичным обновлением".
4. **Со звёздочкой.** Отправь `DELETE` на `https://jsonplaceholder.typicode.com/posts/1` дважды подряд и сравни статус-коды обоих ответов. Затем отправь `POST` на `https://jsonplaceholder.typicode.com/posts` дважды подряд с одинаковым телом и сравни `id` в обоих ответах. Объясни, как эти два эксперимента подтверждают (или нет) идемпотентность DELETE и её отсутствие у POST.
