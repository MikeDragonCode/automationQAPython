# 3.13. Добавляем новый метод в клиент: update_user_api

## Зачем это нужно

Это последний теоретический урок модуля, и он — прямая репетиция домашнего задания. Ты уже разобрал, как устроен `UsersClient` целиком (уроки 3.7–3.12). Теперь разберём, как **добавить** в него новый метод, не ломая и не переписывая то, что уже есть, — именно так выглядит обычная задача на реальном проекте: "добавь метод под новый эндпоинт".

## Теория

В `UsersClient` уже есть `get_users_api`, `get_user_api`, `create_user_api`, `delete_user_api` (низкоуровневые, возвращают `Response`) и `get_user`, `create_user` (высокоуровневые, возвращают Pydantic-модель). Обрати внимание: **`delete_user_api` уже существует в клиенте**, но в `test_users.py` для него пока нет ни одного теста. Значит, в домашнем задании тебе предстоит не только добавить новый метод, но и написать тесты на уже существующий, но непокрытый метод — тоже частая ситуация в реальной работе.

Метода для обновления пользователя (`PATCH /users/{id}`) в клиенте пока нет вообще — это тот метод, который мы добавим по шагам ниже.

### Шаг 1. Схема запроса на обновление

PATCH — метод частичного обновления (урок 3.2): клиент присылает только те поля, которые хочет изменить. Значит, в схеме запроса все поля должны быть опциональными (урок 3.9):

```python
# clients/users/users_schema.py — добавляем рядом с существующими схемами

class UpdateUserRequestSchema(BaseModel):
    """
    Описание структуры запроса на частичное обновление пользователя.
    Все поля опциональны — PATCH отправляет только то, что нужно изменить.
    """
    name: str | None = None
    username: str | None = None
    email: EmailStr | None = None
```

Обрати внимание: используем `EmailStr`, а не простой `str`, точно так же, как в уже существующей `UserSchema`. Это не просто "для красоты" — на реальном (а не фейковом) API схема с `EmailStr` не даст тебе даже попытаться отправить в API заведомо невалидный email: `UpdateUserRequestSchema(email="not-an-email")` упадёт с `pydantic.ValidationError` ещё до похода в сеть. Это осмысленный негативный тест сам по себе — подробнее в домашнем задании.

Для ответа переиспользуем уже существующую `UserSchema` — JSONPlaceholder на `PATCH /users/{id}` для "существующих" (захардкоженных на сервере) id 1–10 возвращает полноценный объект пользователя той же формы, что и `GET /users/{id}`.

### Шаг 2. Метод в клиенте

Добавляем в `UsersClient`, рядом с остальными методами, по той же схеме "сначала `_api`-метод, затем — при необходимости — высокоуровневый":

```python
# clients/users/users_client.py

class UsersClient(APIClient):
    # ...существующие методы без изменений...

    def update_user_api(self, user_id: int, request: UpdateUserRequestSchema) -> Response:
        return self.patch(
            f"/users/{user_id}",
            json=request.model_dump(exclude_none=True),
        )

    def update_user(self, user_id: int, request: UpdateUserRequestSchema) -> UserSchema:
        response = self.update_user_api(user_id, request)
        return UserSchema.model_validate_json(response.text)
```

Разберём то, чего раньше не было в клиенте:

- `self.patch(...)` — метод из базового `APIClient` (урок 3.7), уже готов к использованию, ничего дополнительно реализовывать не нужно.
- `request.model_dump(exclude_none=True)` — важная деталь. Так как все поля `UpdateUserRequestSchema` опциональны и по умолчанию равны `None`, обычный `model_dump()` отправил бы в API поля со значением `None` для всех незаполненных атрибутов. `exclude_none=True` убирает из итогового словаря поля, равные `None`, — в теле запроса останутся только те поля, которые студент реально захотел изменить. Это именно та семантика, которую и подразумевает PATCH (урок 3.2).
- `update_user_api` возвращает сырой `Response` — пригодится для негативных тестов и проверки статус-кода.
- `update_user` сразу возвращает провалидированный `UserSchema` — пригодится для happy-path тестов, где удобно проверить конкретные поля через атрибуты.

### Шаг 3. Импорт новой схемы

Не забудь обновить импорт в начале `users_client.py`:

```python
from clients.users.users_schema import (
    CreateUserRequestSchema,
    CreateUserResponseSchema,
    UpdateUserRequestSchema,  # добавили
    UserSchema,
)
```

## Пример

Использование нового метода в тесте — по тому же паттерну, что и `test_create_user` из урока 3.12:

```python
def test_update_user_name(users_client: UsersClient):
    request = UpdateUserRequestSchema(name="New Name")

    updated_user = users_client.update_user(user_id=1, request=request)

    assert updated_user.name == "New Name"
```

А вот пример клиентской (не серверной) негативной проверки, о которой шла речь выше — она не делает ни одного сетевого запроса:

```python
import pytest
from pydantic import ValidationError


def test_update_user_invalid_email_is_rejected_by_schema():
    with pytest.raises(ValidationError):
        UpdateUserRequestSchema(email="not-an-email")
```

Такой тест ловит ошибку валидации раньше, чем она вообще могла бы стать проблемой на реальном API — это ценно само по себе, независимо от того, как именно ведёт себя конкретный бэкенд.

## Частые ошибки

- Забыть `exclude_none=True` при сериализации `UpdateUserRequestSchema` — тогда в PATCH-запрос уйдут лишние поля со значением `null`, и метод перестанет вести себя как частичное обновление.
- Сделать все поля в схеме запроса обязательными — тогда придётся передавать вообще все поля пользователя при любом, даже самом маленьком, изменении, что противоречит смыслу PATCH.
- Добавить новый метод в середину класса произвольным образом, ломая порядок "сначала все `_api`-методы, потом высокоуровневые" — нарушение уже сложившегося в файле соглашения затрудняет чтение кода для следующего человека.
- Не обновить импорты после добавления новой схемы и словить `NameError` при первом запуске.

## Мини-задание

В своём форке `boilerplate/` добавь `UpdateUserRequestSchema` в `users_schema.py` и `update_user_api`/`update_user` в `users_client.py`, как показано выше. Напиши и запусти локально (`pytest -m api -v`) тест `test_update_user_name`, проверяющий, что после `update_user(user_id=1, request=UpdateUserRequestSchema(name="New Name"))` поле `name` в ответе действительно равно `"New Name"`. Это и есть первый шаг домашнего задания — подробное описание и критерии готовности смотри в следующем уроке.
