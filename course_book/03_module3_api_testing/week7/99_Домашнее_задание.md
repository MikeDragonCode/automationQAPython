# 3.14. Домашнее задание

## Формулировка

Открой PR в свой форк общего репозитория (`boilerplate/`) с 5–7 новыми API-тестами. Тесты должны опираться на новые методы `UsersClient`, которые ты добавишь по образцу урока 3.13, а не на голые вызовы `requests`.

Минимальный набор изменений:

1. **Добавь `UpdateUserRequestSchema`** в `clients/users/users_schema.py` — все поля опциональны (`name`, `username`, `email`), под частичное обновление через PATCH. Используй `EmailStr` для поля `email`, как в уже существующей `UserSchema`.
2. **Добавь `update_user_api` и `update_user`** в `clients/users/users_client.py` — по паттерну "низкоуровневый метод возвращает `Response`, высокоуровневый — Pydantic-модель", как показано в уроке 3.13. Не забудь `exclude_none=True` при сериализации запроса.
3. **Напиши тесты на `update_user_api`/`update_user`** — как минимум один happy-path тест (обновление одного поля, проверка через атрибуты ответа).
4. **Напиши тесты на уже существующий, но пока непокрытый `delete_user_api`** — как минимум один тест, проверяющий успешный статус-код.
5. **Добавь минимум один "несчастливый" тест**, который проверяет не happy path. Хорошие варианты для нашего демо-API (см. пояснение ниже, почему не любой негативный сценарий сюда подходит):
   - `UpdateUserRequestSchema(email="not-an-email")` должна упасть с `pydantic.ValidationError` ещё до похода в сеть — это валидный и полезный негативный тест, не зависящий от поведения конкретного сервера.
   - Запрос несуществующего пользователя через `get_user_api` (метод уже есть и уже покрыт тестом в `test_users.py` — используй его как образец, если хочешь написать вариацию, например, с другим граничным id).

Итого у тебя должно получиться 5–7 тестов в `tests/api/test_users.py` (можно дописать в существующий класс `TestUsers` или добавить новые тестовые методы рядом).

### Почему не "PATCH/DELETE несуществующего пользователя → 404"

JSONPlaceholder — фейковый API: ничего не сохраняет по-настоящему, а на `PATCH`/`DELETE` для **любого** id (даже несуществующего) отвечает `200 OK`, просто эхом возвращая присланные данные. Это легко проверить самостоятельно:

```bash
curl -i -X PATCH https://jsonplaceholder.typicode.com/users/9999 \
     -H "Content-Type: application/json" -d '{"name": "x"}'
# HTTP/1.1 200 OK — а не 404, как можно было бы ожидать от настоящего API
```

Поэтому тест вида "обнови несуществующего пользователя и жди 404" **не сработает** — не из-за ошибки в твоём коде, а потому что сам демо-сервис так не умеет. Это не баг задания, а особенность конкретного публичного API, с которой полезно познакомиться: **не пиши негативный тест, не проверив вручную, как API реально ведёт себя** (через `curl` или Postman) — иначе тест либо не будет иметь смысла, либо будет falsely red/green. Именно поэтому пункт 5 выше явно указывает на клиентскую (Pydantic) валидацию как на надёжный источник негативного сценария для этого демо-API — она не зависит от поведения сервера.

## Критерии "готово"

- [ ] Новый метод `update_user_api` (и, по желанию, `update_user`) добавлен в `UsersClient`, который по-прежнему наследуется от `APIClient` — новая архитектура не вводится, используется существующая.
- [ ] Для запроса на обновление есть Pydantic-схема (`UpdateUserRequestSchema`) с опциональными полями; для ответа переиспользована существующая `UserSchema`.
- [ ] Все новые тесты используют фикстуру `users_client`, а не создают клиент вручную и не вызывают `requests` напрямую.
- [ ] Есть минимум 5 тестов, среди них — минимум один явно негативный/граничный сценарий (не только happy path).
- [ ] Один из тестов проверяет уже существующий `delete_user_api` (ранее непокрытый).
- [ ] `pytest -m api -v` проходит локально зелёным целиком, включая уже существовавшие до тебя тесты.
- [ ] PR открыт в общий репозиторий, в описании — что сделано и как проверить (см. правила PR в `boilerplate/README.md`).

## Что не входит в это домашнее задание

Allure-разметка (`allure.step`, `allure.title`) — это тема модуля 5. В существующих тестах она уже есть, и ты можешь по аналогии добавить её в свои новые тесты (это не будет лишним), но отсутствие Allure-декораторов не считается недочётом на этом этапе — критерии "готово" выше их не требуют.
