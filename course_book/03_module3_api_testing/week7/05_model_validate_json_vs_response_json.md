# 3.11. model_validate_json vs response.json()

## Зачем это нужно

В `UsersClient` (урок 3.8) высокоуровневые методы используют `UserSchema.model_validate_json(response.text)`, а не более очевидный на первый взгляд `UserSchema(**response.json())`. Разница между этими двумя подходами — не стилистическая придирка, а вопрос того, насколько твой тест устойчив к неожиданному поведению сервера.

## Теория

Есть два способа превратить ответ сервера в Pydantic-объект.

### Вариант 1: response.json() + распаковка словаря

```python
data = response.json()          # шаг 1: распарсить JSON в dict
user = UserSchema(**data)       # шаг 2: распаковать dict в модель
```

Здесь работа разбита на два независимых шага. Сначала `requests` сам парсит тело ответа как JSON (используя обычный `json.loads` внутри), и только потом результат передаётся в Pydantic.

**Проблема:** если сервер вернул не JSON (например, HTML-страницу ошибки от прокси, пустое тело при `204`, или просто битый JSON) — упадёт `response.json()`, ещё до того, как в дело вступит Pydantic. Ошибка будет в духе `json.decoder.JSONDecodeError`, и разбираться, что пошло не так, придётся по тексту исключения из чужой библиотеки.

### Вариант 2: model_validate_json

```python
user = UserSchema.model_validate_json(response.text)
```

Здесь `response.text` — это сырая строка тела ответа, без предварительного парсинга через `requests`. Метод `model_validate_json` сам парсит эту строку **и** сразу валидирует её на соответствие модели — за один шаг, средствами самого Pydantic.

**Почему это надёжнее:**

1. Ошибка парсинга и ошибка валидации происходят в одном и том же месте, с одинаковым типом исключения (`pydantic.ValidationError`) — не нужно ловить два разных типа ошибок в разных библиотеках.
2. Сообщение об ошибке от Pydantic обычно понятнее и конкретнее, чем стандартное исключение JSON-парсера — оно сразу указывает, какое поле проблемное.
3. Меньше промежуточных шагов — данные не проходят лишний раз через generic `dict`, а сразу превращаются в типизированный объект.

### Когда какой вариант использовать

Если ты уверен, что API всегда возвращает предсказуемый корректный JSON (что в целом верно для стабильных внутренних API), разница между вариантами не критична, и `UserSchema(**response.json())` тоже рабочий вариант. Но `model_validate_json(response.text)` — более защищённый способ по умолчанию, и именно поэтому он используется во всех высокоуровневых методах `UsersClient` в нашем репозитории. Придерживайся этого же паттерна, когда будешь добавлять свои методы в домашнем задании.

## Пример

Вот как это выглядит в реальном методе `UsersClient` (`boilerplate/clients/users/users_client.py`):

```python
def get_user_api(self, user_id: int) -> Response:
    return self.get(f"/users/{user_id}")

def get_user(self, user_id: int) -> UserSchema:
    response = self.get_user_api(user_id)
    return UserSchema.model_validate_json(response.text)
```

`get_user_api` возвращает сырой `Response` — им пользуются негативные тесты (урок 3.8). `get_user` берёт этот же `Response`, достаёт `response.text` и валидирует его в `UserSchema` — им пользуются позитивные тесты, которым нужен удобный доступ к полям.

Если бы сервер неожиданно вернул, скажем, пустое тело (например, из-за сбоя прокси), `model_validate_json("")` упадёт с понятным `ValidationError`, где будет явно видно, что тело не является валидным JSON-объектом — вместо непрозрачного `JSONDecodeError` где-то в недрах `requests`.

## Частые ошибки

- Смешивать подходы в одном методе без причины — например, один раз использовать `response.json()`, в другом методе того же клиента — `model_validate_json`, без единой логики выбора.
- Вызывать `model_validate_json` на негативных сценариях (`404`, `422`), где тело ответа заведомо не соответствует основной схеме, — в таких тестах нужно проверять `response.status_code` через `_api`-метод, а не пытаться валидировать ошибку как успешный ответ.
- Забывать, что `model_validate_json` ожидает именно **строку** (`response.text`), а не уже распарсенный словарь — попытка передать `response.json()` в `model_validate_json` приведёт к ошибке типа.

## Мини-задание

Возьми `users_client.get_user_api(user_id=999)` (несуществующий пользователь, вернёт `404` с пустым или отличным от `UserSchema` телом). Попробуй передать `response.text` в `UserSchema.model_validate_json(...)` и посмотри на текст исключения `ValidationError`. Сравни с тем, что случилось бы при попытке `UserSchema(**response.json())` на том же ответе — оба варианта не сработают, но сообщения об ошибке будут отличаться.
