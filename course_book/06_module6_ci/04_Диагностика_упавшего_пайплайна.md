# 6.4. Диагностика упавшего пайплайна

## Зачем это нужно

Красный крестик на PR — самая частая причина, по которой джуниор идёт к более опытному коллеге "а что это значит". Цель этого урока — чтобы в 80% случаев ответ находился самостоятельно, за пару минут, по логам.

## Теория

Алгоритм диагностики — один и тот же для GitHub Actions и GitLab CI:

1. **Найти, какой именно job упал.** Если пайплайн состоит из нескольких stages/jobs (как в общем репозитории — сначала `unit-and-api`, потом `ui`), падение одного job'а не означает, что упало всё — смотри конкретно на красный элемент.
2. **Открыть лог именно упавшего шага**, а не всего job'а целиком. В GitHub Actions шаги разворачиваются по клику, в GitLab CI — лог job'а один сплошной, но упавшая команда обычно выделена и находится в конце.
3. **Отличить три типа падений:**
   - **Упал тест** (`assert` не выполнился, exception в тесте) — в логе виден pytest-traceback с именем теста. Это твоя зона ответственности — либо баг в коде, либо баг в тесте.
   - **Упала установка окружения** (`pip install` не смог поставить пакет, `playwright install` не скачался) — в логе ошибка ДО начала pytest. Часто временная проблема сети/реестра пакетов — можно попробовать перезапустить job.
   - **Упал сам pipeline-конфиг** (опечатка в YAML, несуществующий job в `needs:`) — тогда тесты вообще не запускаются, ошибка появляется на этапе валидации файла, ещё до логов job'ов.
4. **Скачать артефакты**, если это не помогло. `allure-results`, которые загружает CI (см. уроки 6.2–6.3), можно скачать и открыть локально через `allure serve` — иногда полный Allure-отчёт нагляднее, чем сырой текстовый лог.
5. **Перезапустить job вручную**, если причина — временная (сеть, флейковый тест). В GitHub Actions — кнопка "Re-run jobs" на странице workflow run. В GitLab CI — кнопка "Retry" у конкретного job'а в интерфейсе пайплайна.

## Пример

Типичный сценарий: ты открыл PR с новым API-тестом, job `unit-and-api` красный. Лог показывает:

```
FAILED tests/api/test_users.py::TestUsers::test_get_user - AssertionError: assert 2 == 1
```

Это явно случай 1 — упал тест, а не окружение. Дальше это обычная отладка теста: смотрим, что метод `get_user` вернул `id=2` вместо ожидаемого `id=1` — скорее всего, ошибка в самом тесте (например, скопировали фикстуру и забыли поменять параметр), а не в API.

Другой пример:

```
ERROR: Could not find a version that satisfies the requirement playwright==1.47.0
```

Это случай 2 — не установилось окружение, скорее всего временная проблема с реестром пакетов или неверная версия в `requirements.txt`. Здесь сначала стоит попробовать перезапустить job, и только если повторяется — разбираться с версией пакета.

## Частые ошибки

- Смотреть только на итоговый статус ("Failed") и не открывать сам лог — почти вся полезная информация внутри развёрнутого шага/job'а.
- Пытаться чинить локально то, что на самом деле является проблемой самого CI-раннера (например, недоступность внешнего пакетного реестра) — сначала стоит перепроверить: воспроизводится ли падение локально (`pytest -m "unit or api"` у себя).
- Ре-раниться "на автомате" при любом падении, не читая лог — если тест действительно падает стабильно (не флейк), повторный запуск просто трижды покажет ту же ошибку и потратит время CI-раннера.

## Мини-задание

Специально сломай один свой тест (например, поставь заведомо неверный `assert`), запушь ветку/открой PR, дождись падения пайплайна и пройди весь алгоритм: найди упавший job → открой лог упавшего шага → определи тип падения (тест / окружение / конфиг) → откати "поломку".
