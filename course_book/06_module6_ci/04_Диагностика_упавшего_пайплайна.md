# 6.4. Диагностика упавшего пайплайна

## Зачем это нужно

Красный крестик на PR — самая частая причина, по которой джуниор идёт к более опытному коллеге "а что это значит". Цель этого урока — чтобы в 80% случаев ответ находился самостоятельно, за пару минут, по логам.

## Теория

### Шаг 1-2: найти упавший job и открыть его лог

Если пайплайн состоит из нескольких stages/jobs (как в общем репозитории — сначала `unit-and-api`, потом `ui`, см. уроки 6.1-6.3), падение одного job'а не означает, что упало всё — смотри конкретно на красный элемент, а не на пайплайн в целом. Дальше нужно открыть лог именно упавшего шага, а не всего job'а целиком: в GitHub Actions шаги разворачиваются по клику, в GitLab CI лог job'а один сплошной, но упавшая команда обычно выделена и находится в конце.

### Три типа падений

Дальше важно отличить, что именно упало — это определяет твои следующие действия:

- **Упал тест** — `assert` не выполнился, exception в тесте. В логе виден pytest-traceback с именем теста:
  ```
  FAILED tests/api/test_users.py::TestUsers::test_get_user - AssertionError: assert 2 == 1
  ```
  Это твоя зона ответственности — либо баг в коде, либо баг в тесте.
- **Упала установка окружения** — `pip install` не смог поставить пакет, `playwright install` не скачался. В логе ошибка ДО начала pytest:
  ```
  ERROR: Could not find a version that satisfies the requirement playwright==1.47.0
  ```
  Часто временная проблема сети/реестра пакетов — можно попробовать перезапустить job.
- **Упал сам pipeline-конфиг** — опечатка в YAML, несуществующий job в `needs:`. Тогда тесты вообще не запускаются, что-то вроде ошибки валидации самого файла ещё до того, как появятся логи job'ов:
  ```
  Invalid workflow file: .github/workflows/ci.yml — ... error parsing job "ui": needs value 'unit_and_api' does not match ...
  ```
  Такую ошибку не получится "перезапустить" — сначала нужно поправить сам YAML-файл.

### Скачать артефакты и решить, перезапускать ли job

Если лога недостаточно — можно скачать артефакты. `allure-results`, которые загружает CI (см. уроки 6.2-6.3), можно скачать и открыть локально через `allure serve` (модуль 5) — иногда полный Allure-отчёт нагляднее, чем сырой текстовый лог.

Дальше — решение, перезапускать ли job вручную. Это имеет смысл только для временных причин (сеть, флейковый тест): в GitHub Actions — кнопка "Re-run jobs" на странице workflow run, в GitLab CI — кнопка "Retry" у конкретного job'а. Если же тест падает стабильно (тип "упал тест" выше) — повторный запуск просто покажет ту же ошибку и потратит время раннера впустую; здесь нужно чинить код или тест, а не рестартовать.

## Пример

Типичный сценарий: ты открыл PR с новым API-тестом, job `unit-and-api` красный. Лог показывает:

```
FAILED tests/api/test_users.py::TestUsers::test_get_user - AssertionError: assert 2 == 1
```

Это явно случай "упал тест", а не окружение. Дальше это обычная отладка теста: смотрим, что метод `get_user` вернул `id=2` вместо ожидаемого `id=1` — скорее всего, ошибка в самом тесте (например, скопировали фикстуру и забыли поменять параметр), а не в API.

Другой пример:

```
ERROR: Could not find a version that satisfies the requirement playwright==1.47.0
```

Это случай "упало окружение", скорее всего временная проблема с реестром пакетов или неверная версия в `requirements.txt`. Здесь сначала стоит попробовать перезапустить job, и только если повторяется — разбираться с версией пакета.

## Частые ошибки

- Смотреть только на итоговый статус ("Failed") и не открывать сам лог — почти вся полезная информация внутри развёрнутого шага/job'а.
- Пытаться чинить локально то, что на самом деле является проблемой самого CI-раннера (например, недоступность внешнего пакетного реестра) — сначала стоит перепроверить: воспроизводится ли падение локально (`pytest -m "unit or api"` у себя).
- Ре-раниться "на автомате" при любом падении, не читая лог — если тест действительно падает стабильно (не флейк), повторный запуск просто трижды покажет ту же ошибку и потратит время CI-раннера.

## Мини-задания

1. **Разминка.** Дан лог: `pip._vendor.pip._internal.exceptions.DistributionNotFound: No matching distribution found for allure-pytest==2.13.5`. Определи, к какому из трёх типов падения он относится (тест / окружение / конфиг), и объясни, по какому признаку ты это понял.
2. **Основное.** Даны два лога:
   - `E   AssertionError: Locator expected to have text "Dashboard" but has text "Dashbord"`
   - `Error: Process completed with exit code 1. yaml: line 34: did not find expected key`

   Для каждого определи тип падения и предложи следующее действие (чинить тест / перезапустить job / чинить YAML-файл).
3. **Ближе к практике.** Специально сломай один свой тест (например, поставь заведомо неверный `assert`), запушь ветку/открой PR, дождись падения пайплайна и пройди весь алгоритм: найди упавший job → открой лог упавшего шага → определи тип падения (тест / окружение / конфиг) → откати "поломку".
4. **Со звёздочкой.** Твой UI-тест иногда падает в CI, но не всегда, и всегда проходит у тебя локально. Лог показывает `TimeoutError: Timeout 30000ms exceeded waiting for locator(...)` без стабильного паттерна — то падает, то нет. К какому из трёх типов падения это ближе всего? Стоит ли сразу чинить код теста или сначала имеет смысл просто перезапустить job — и как в принципе отличить "проблему действительно починили" от "просто повезло с перезапуском"?
