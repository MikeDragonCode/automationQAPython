# 5.2. allure.step и allure.title

## Зачем это нужно

Название функции теста (`test_get_user`) и её докстринг — это то, что видит разработчик, читающий код. А человек, который просто смотрит отчёт после ночного прогона в CI, кода не открывает. Ему нужно человекочитаемое название сценария и пошаговая раскладка того, что происходило — именно это дают `allure.title` и `allure.step`.

## Теория

### allure.title — человекочитаемое имя теста

`@allure.title("...")` задаёт название теста в отчёте вместо технического `test_get_user`:

```python
@allure.title("Получение пользователя по id")
def test_get_user(self, users_client: UsersClient):
    ...
```

В отчёте вместо `test_get_user` увидишь "Получение пользователя по id" — понятно даже тому, кто ни разу не открывал код.

### allure.epic и allure.feature — группировка тестов

`@allure.epic("...")` и `@allure.feature("...")` группируют тесты в отчёте по крупным разделам (например `epic="API"`, `feature="Users"`) — по ним строится дерево в интерфейсе Allure. Так это уже сделано в `boilerplate/tests/api/test_users.py`:

```python
@allure.epic("API")
@allure.feature("Users")
@pytest.mark.api
class TestUsers:
    ...
```

Декораторы висят на классе, а не на каждом методе — это распространяется на все тесты внутри `TestUsers`, повторять на каждом методе не нужно.

### allure.step — шаги внутри теста

`with allure.step("..."):` оборачивает часть теста в именованный шаг. В отчёте шаги показываются как раскрывающийся список, и если тест упал — видно, на каком именно шаге. Важно: это **context manager**, а не декоратор — синтаксис у него именно `with allure.step(...):`, а не `@allure.step(...)` над функцией.

```python
with allure.step("Запрашиваем пользователя с id=1"):
    user = users_client.get_user(user_id=1)

with allure.step("Проверяем, что данные пользователя корректны"):
    assert user.id == 1
    assert "@" in user.email
```

Если упадёт второй `assert`, в отчёте будет видно: шаг "Запрашиваем пользователя..." — зелёный, шаг "Проверяем, что данные..." — красный, и именно в нём — traceback. Не нужно перечитывать весь тест, чтобы понять, где именно сломалось.

### Шаги можно вкладывать друг в друга

`allure.step` — это обычный `with`-блок на чистом Python, поэтому шаги можно вкладывать один в другой сколько нужно, и в отчёте это отобразится вложенной раскрывающейся иерархией:

```python
with allure.step("Готовим и отправляем регистрацию"):
    with allure.step("Заполняем форму"):
        registration_page.fill_registration_form(**user_data)
    with allure.step("Отправляем форму"):
        registration_page.click_registration_button()
```

Полезно, когда один логический этап сценария состоит из нескольких мелких действий, которые хочется видеть по отдельности, но не хочется "распылять" на верхний уровень шагов теста.

Всё, что описано выше, уже используется в общем репозитории — открой:

```
boilerplate/tests/api/test_users.py
boilerplate/tests/ui/test_registration.py
```

## Пример

Разбор реального теста из `boilerplate/tests/api/test_users.py`:

```python
@allure.epic("API")
@allure.feature("Users")
@pytest.mark.api
class TestUsers:

    @allure.title("Получение пользователя по id")
    def test_get_user(self, users_client: UsersClient):
        with allure.step("Запрашиваем пользователя с id=1"):
            user = users_client.get_user(user_id=1)

        with allure.step("Проверяем, что данные пользователя корректны"):
            assert user.id == 1
            assert "@" in user.email
```

Если упадёт второй `assert`, в отчёте будет видно: шаг "Запрашиваем пользователя..." — зелёный, шаг "Проверяем, что данные..." — красный, и именно в нём — traceback. Не нужно перечитывать весь тест, чтобы понять, где именно сломалось.

Обрати внимание на связку `@allure.epic` + `@allure.feature` на уровне класса — это распространяется на все тесты внутри `TestUsers`, повторять на каждом методе не нужно.

## Частые ошибки

- Слишком мелкая разбивка на шаги (`allure.step` на каждую строчку) — отчёт превращается в такой же шум, каким был код без разметки. Шаг — это осмысленный кусок сценария ("открыли форму", "заполнили и отправили", "проверили результат"), а не техническая мелочь.
- `allure.title` дублирует то, что и так понятно из имени функции — тогда декоратор не добавляет пользы. Хорошее название описывает бизнес-сценарий, а не техническую механику.
- Забыть, что `allure.step` — это context manager (`with allure.step(...):`), а не декоратор — синтаксис у него другой, чем у `allure.title`.

## Мини-задания

1. **Разминка.** Возьми один тест из `boilerplate/tests/unit/test_string_utils.py` (у него пока нет никакой allure-разметки) и добавь ему только `@allure.title(...)` с человекочитаемым названием — без шагов, только этот один факт.
2. **Основное.** Возьми любой свой тест из модуля 3 или 4 (API или UI) и добавь в него `@allure.title` с человекочитаемым названием и минимум два `allure.step` — один на подготовку/действие, один на проверку.
3. **Ближе к практике.** Открой `test_create_user` в `boilerplate/tests/api/test_users.py` — заметь, что подготовка данных (`CreateUserRequestSchema(...)`) сейчас не обёрнута ни в какой шаг, в отличие от отправки запроса и проверки результата. Добавь для неё шаг `allure.step("Готовим данные нового пользователя")`, чтобы в отчёте сценарий из трёх шагов (подготовка → действие → проверка) был виден целиком.
4. **Со звёздочкой.** Для теста `test_get_user_not_found` сначала напиши "плохой" `allure.title`, который просто дублирует имя функции (например `"test get user not found"`), а рядом — хороший, который описывает бизнес-сценарий. Сравни оба варианта и сформулируй словами, чем хороший title лучше с точки зрения человека, читающего отчёт, а не код.
