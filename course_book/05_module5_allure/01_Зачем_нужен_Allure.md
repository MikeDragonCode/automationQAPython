# 5.1. Зачем нужен Allure

## Зачем это нужно

Когда тестов десять, вывода `pytest -v` в терминале достаточно. Когда тестов двести и часть из них падает в CI по ночам — нужно, чтобы кто угодно (включая тебя самого через неделю) мог открыть отчёт и за 30 секунд понять: что упало, на каком шаге сценария, с каким запросом или на каком экране. Именно это делает Allure.

## Теория

### Проблема: pytest говорит мало

Обычный вывод `pytest -v` — это список имён тестов и статусов:

```
tests/api/test_users.py::TestUsers::test_get_user PASSED
tests/api/test_users.py::TestUsers::test_get_user_not_found PASSED
tests/ui/test_registration.py::TestRegistration::test_successful_registration FAILED
```

По этой строке не видно, на каком именно шаге упал `test_successful_registration`: на открытии страницы, на заполнении формы или на проверке перехода на Dashboard. Чтобы узнать — нужно читать код теста и, скорее всего, перезапускать его локально. В CI, где нет возможности повесить `print()` и посмотреть глазами на экран, это особенно неудобно.

### Из чего состоит Allure: два разных инструмента

Allure — это не библиотека для написания тестов, а инструмент отчётности. Он состоит из двух частей:

- **`allure-pytest`** — плагин, который во время прогона собирает данные о тестах (шаги, вложения, метаданные) и складывает их в папку с "сырыми" JSON-файлами (обычно `allure-results/`).
- **Allure CLI** — отдельная программа, которая превращает эти JSON-файлы в HTML-отчёт с графиками, деревом тестов, историей запусков.

После обычного прогона с `allure-pytest` в папке результатов лежат только JSON-файлы, отчёта там ещё нет:

```bash
pytest --alluredir=allure-results
ls allure-results
# 3f2e1a-result.json  9c04bb-result.json  ...  environment.properties
```

Как превратить эти файлы в HTML — отдельный урок 5.4.

### Разметка не обязательна, но меняет качество отчёта

Без разметки в коде Allure всё равно покажет список тестов и их статус — примерно то же, что и обычный pytest-отчёт: имя теста и pass/fail. Разметка (`allure.step`, `allure.title`, `allure.epic`/`allure.feature` — подробно разберём в уроке 5.2) — это то, что превращает отчёт из "список точек" в читаемую историю сценария: раскрывающиеся шаги внутри теста, человекочитаемое название вместо `test_successful_registration`, группировка по разделам приложения.

### Зависимость уже подключена в проекте

В `boilerplate/requirements.txt` уже есть:

```
allure-pytest==2.13.5
```

Значит, плагин будет активирован автоматически при установке `pip install -r requirements.txt` — писать конфиг для его подключения не нужно.

## Пример

Достаточно запустить тесты с одним дополнительным флагом:

```bash
pytest --alluredir=allure-results
```

После этого в папке `allure-results/` появятся файлы вида `*-result.json` — по одному на тест, плюс служебные файлы окружения. Как превратить их в HTML-отчёт — в уроке 5.4.

## Частые ошибки

- Ждать красивый отчёт сразу после `pytest --alluredir=...` — это ещё не отчёт, а сырые данные. Нужен отдельный шаг генерации (`allure generate` или `allure serve`).
- Путать `allure-pytest` (Python-плагин, ставится через pip) и Allure CLI (отдельная программа, ставится отдельно — через brew/scoop/архив с сайта). Это два разных инструмента.
- Держать старую папку `allure-results/` между прогонами без её очистки — тогда в отчёте копятся результаты вперемешку со старыми запусками. Обычно `allure-results/` добавляют в `.gitignore` (это уже сделано в `boilerplate/.gitignore`) и очищают перед новым прогоном.

## Мини-задания

1. **Разминка.** Установи зависимости из `boilerplate/requirements.txt`, запусти `pytest --alluredir=allure-results` и открой глазами получившийся один `*-result.json` — найди в нём поле `"status"` и пойми, за какой тест он отвечает по полю `"fullName"` или `"name"`.
2. **Основное.** Запусти те же тесты дважды: сначала `pytest -v` (обычный вывод в терминал), затем `pytest --alluredir=allure-results`. Сравни, какую информацию терминал не показывает вообще, а JSON-файлы уже содержат (подсказка: посмотри на поля вроде `start`/`stop` и на пустой пока список шагов `steps`).
3. **Ближе к практике.** Прогони весь набор тестов проекта (`pytest --alluredir=allure-results`, без фильтра по маркерам) и посчитай, сколько файлов `*-result.json` появилось в `allure-results/`. Сверь это число с количеством тестовых функций/методов в `boilerplate/tests/` — сходится ли оно, и почему один тест даёт ровно один `-result.json`.
4. **Со звёздочкой.** Запусти `pytest --alluredir=allure-results` два раза подряд, не удаляя папку между прогонами. Посмотри, что произошло с содержимым `allure-results/` — файлов стало больше или они перезаписались? Объясни, почему это именно та проблема "накопления мусора между прогонами", о которой предупреждает раздел "Частые ошибки", и почему её обычно решают простой очисткой папки перед новым запуском.
