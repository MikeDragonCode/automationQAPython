# 5.3. Вложения: скриншоты и логи при падении

## Зачем это нужно

Текст ошибки ("`AssertionError: Dashboard != Dashbord`") — это полезно, но для UI-теста скриншот в момент падения часто говорит больше, чем весь traceback. Не нужно гадать, что творилось на экране — можно просто на него посмотреть.

## Теория

### allure.attach — вложения вручную

`allure.attach(...)` прикладывает к результату теста произвольные данные: текст, JSON, скриншот, файл лога. Прикладывать вложения можно вручную прямо внутри теста — например, приложить тело ответа API, чтобы не листать логи в поисках того, что реально вернул сервер:

```python
with allure.step("Проверяем статус-код ответа"):
    allure.attach(
        response.text,
        name="response-body",
        attachment_type=allure.attachment_type.JSON,
    )
    assert response.status_code == 404
```

Ручные вложения удобны для конкретного места в конкретном тесте, но писать `allure.attach(...)` в каждом тесте вручную неудобно, если нужно одно и то же поведение для ЛЮБОГО теста определённого вида (например — скриншот для любого упавшего UI-теста).

### Автоматическое вложение через pytest hook

Именно для этого случая в общем репозитории уже настроен автоматический скриншот на падении — через pytest hook, один раз в `conftest.py`, а не в каждом тесте отдельно. Открой `boilerplate/conftest.py` и найди в конце файла:

```python
@pytest.hookimpl(hookwrapper=True)
def pytest_runtest_makereport(item, call):
    outcome = yield
    report = outcome.get_result()

    if report.when == "call" and report.failed:
        page: Page | None = item.funcargs.get("page")
        if page is not None:
            allure.attach(
                page.screenshot(),
                name="screenshot-on-failure",
                attachment_type=allure.attachment_type.PNG,
            )
```

Ключевая идея: **эта логика не встроена в каждый тест** — она в одном месте (`conftest.py`) и работает для всех UI-тестов автоматически, включая те, что напишешь ты сам в будущих PR.

### Три фазы теста: setup / call / teardown

У pytest каждый тест проходит через три фазы, и для каждой формируется свой `report`: `setup` (подготовка фикстур), `call` (выполнение тела теста) и `teardown` (освобождение фикстур после теста). У каждой фазы своё поле `report.when` со значением `"setup"`, `"call"` или `"teardown"`.

Хук выше специально проверяет `report.when == "call"` — то есть интересует падение именно в фазе выполнения самого теста. Если, например, упадёт фикстура на этапе `setup` (скажем, не удалось открыть страницу браузера), `report.when` будет равен `"setup"`, условие не выполнится, и скриншот не приложится — потому что `page` в этот момент, скорее всего, ещё не готова к использованию.

### pytest_runtest_makereport по частям

Остальные детали хука:

- `pytest_runtest_makereport` — это стандартный pytest hook, который вызывается после каждой фазы теста и формирует отчёт (`report`) об этой фазе.
- `hookwrapper=True` — превращает функцию в обёртку: сначала выполняется оригинальная логика pytest (`yield`), а затем — наш код после неё, уже с готовым `report` на руках.
- `item.funcargs.get("page")` — если тест использовал фикстуру `page` (то есть это UI-тест), Playwright-объект страницы будет доступен через `item.funcargs`. Для API/unit-тестов его там не будет — `page` окажется `None`, и вложение просто не приложится.
- `page.screenshot()` — Playwright снимает скриншот текущего состояния браузера в байтах, `allure.attach` прикладывает эти байты как PNG к результату теста.

## Пример

Ничего дополнительно писать не нужно — попробуй сломать тест специально, чтобы увидеть механизм в действии:

```python
# временно, для эксперимента — не коммитить
def test_broken_on_purpose(dashboard_page):
    dashboard_page.check_visible_toolbar_title()  # страница ещё не открыта, упадёт
```

Запусти `pytest -m ui --alluredir=allure-results`, сгенерируй отчёт (урок 5.4) и найди в упавшем тесте вложение `screenshot-on-failure`.

## Частые ошибки

- Пытаться делать `page.screenshot()` внутри самого теста в каждом `assert` "на всякий случай" — вместо этого используй уже готовый общий механизм в `conftest.py`, не дублируй его.
- Забыть, что hook сработает только если в тесте реально есть параметр `page` — если Page Object спрятан за другой фикстурой без него в сигнатуре, `item.funcargs` его не найдёт (в нашем boilerplate `registration_page`/`dashboard_page` сами зависят от `page`, так что фикстура всё равно попадает в `funcargs`).
- Прикладывать скриншот и для API-тестов "по аналогии" — там это бессмысленно, вместо этого для API-тестов полезнее прикладывать тело запроса/ответа через `allure.attach` с `attachment_type=allure.attachment_type.JSON`, как показано в теории выше.

## Мини-задания

1. **Разминка.** В любом своём unit- или API-тесте вручную приложи через `allure.attach(...)` простую текстовую строку (например, тестовые входные данные) с `attachment_type=allure.attachment_type.TEXT`. Прогони тест с `--alluredir=allure-results` и найди в папке результатов файл вложения, соответствующий этому тесту.
2. **Основное.** Специально сломай один свой UI-тест (например, поменяй ожидаемый текст в `expect(...).to_have_text(...)` на заведомо неверный), прогони с `--alluredir`, сгенерируй отчёт и убедись, что скриншот приложился автоматически. Не забудь откатить "поломку" после эксперимента.
3. **Ближе к практике.** В `test_get_user` или `test_get_user_not_found` (`boilerplate/tests/api/test_users.py`) добавь ручное вложение тела ответа API через `allure.attach(response.text, ..., attachment_type=allure.attachment_type.JSON)`, аналогично примеру из теории. Прогони тест и проверь в отчёте, что вложение с JSON-телом ответа появилось рядом со стандартными шагами теста.
4. **Со звёздочкой.** Представь гипотетическую фикстуру `hidden_page`, которая внутри себя создаёт Playwright `Page`, но в сигнатуре теста параметра `page` нет — тест принимает только `hidden_page`. Объясни (без изменения реального кода, письменно), почему автоматический скриншот из `conftest.py` в этом случае не приложится, даже если тест реально работает с браузером и падает.
