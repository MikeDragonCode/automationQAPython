# 5.4. Настройка и генерация отчёта

## Зачем это нужно

`allure-pytest` умеет только собирать сырые данные. Чтобы увидеть красивый HTML-отчёт с деревом тестов, графиками и историей — нужен отдельный инструмент, Allure CLI, и команда, которая превратит JSON в страницы.

## Теория

### allure-pytest и Allure CLI — два разных инструмента

Два инструмента, которые не стоит путать:

1. **`allure-pytest`** — Python-пакет, ставится через `pip install -r requirements.txt` (уже в зависимостях boilerplate). Он ничего не показывает сам — только пишет `*-result.json` в папку `--alluredir`.
2. **Allure CLI (`allure`)** — отдельная программа на Java, ставится один раз на машину (через `brew install allure` на macOS, `scoop install allure` на Windows, или вручную из архива с официального сайта). Именно она умеет превращать JSON в HTML.

Установка одного не устанавливает другой: `pip install allure-pytest` ничего не знает про Java-программу `allure`, и наоборот.

### allure serve и allure generate — два способа получить отчёт

Две полезные команды CLI, которые решают разные задачи:

- `allure serve allure-results` — генерирует отчёт во временную папку и сразу открывает его в браузере. Удобно для локальной разработки, когда просто нужно быстро посмотреть на результат.
- `allure generate allure-results -o allure-report --clean` — генерирует статический HTML-отчёт в постоянную папку `allure-report/`. Именно так обычно делают в CI, чтобы потом отчёт можно было опубликовать как артефакт (см. модуль 6), — в отличие от `serve`, эта команда не пытается сама открыть браузер (на CI-раннере браузера и не будет).

```bash
# локально, для себя
pytest --alluredir=allure-results
allure serve allure-results

# для CI / для сохранения результата
pytest --alluredir=allure-results
allure generate allure-results -o allure-report --clean
```

### Что уже настроено в CI общего репозитория

В `.github/workflows/ci.yml` и `.gitlab-ci.yml` общего репозитория уже настроена загрузка `allure-results` как артефакта пайплайна (см. `upload-artifact` / `artifacts:` в этих файлах) — этого достаточно, чтобы результаты не терялись после завершения job'а. Обрати внимание: CI-конфиг сохраняет именно сырые `allure-results` (JSON), а не готовый HTML — генерация статического отчёта (`allure generate`) в текущем пайплайне не выполняется. Полноценную публикацию сгенерированного HTML-отчёта (например, на GitHub Pages или во внешний Allure-сервис) курс намеренно не покрывает — это уже задача уровня "настройка инфраструктуры", а не работы автотестера.

### Как посмотреть отчёт после прогона в CI

Раз CI сохраняет только сырые JSON, а не готовый HTML, посмотреть красивый отчёт после пайплайна можно так: скачать артефакт `allure-results` со страницы прогона (вкладка Actions в GitHub или страница пайплайна в GitLab — подробнее об интерфейсе в модуле 6), распаковать архив локально и запустить на нём тот же `allure serve allure-results` или `allure generate`, что и для локальных результатов. Никакого отдельного механизма для CI не нужно — команды CLI одинаковые что для своих результатов, что для скачанных.

## Пример

Локальный цикл разработки:

```bash
pytest --alluredir=allure-results
allure serve allure-results
```

Цикл для CI (генерация в статику, без открытия браузера — на CI-раннере браузера и не будет):

```bash
pytest --alluredir=allure-results
allure generate allure-results -o allure-report --clean
```

## Частые ошибки

- Ставить `allure-pytest` и ждать, что команда `allure` уже доступна в терминале — это разные установки, `allure-pytest` не тянет за собой Java CLI.
- Коммитить `allure-results/` или `allure-report/` в git — это сгенерированные артефакты конкретного прогона, место им в `.gitignore` (уже сделано в boilerplate).
- Путать `--alluredir` (флаг pytest, куда писать сырые данные) и `-o` у `allure generate` (куда класть готовый HTML) — это два разных пути в двух разных командах.

## Частые ошибки при первом запуске

- `allure: command not found` — значит, CLI не установлен или не в `PATH`; `pip install allure-pytest` эту проблему не решает, это разные инструменты.
- Пустой отчёт — обычно означает, что `pytest` запускали без `--alluredir`, и в указанной папке просто нет файлов.

## Мини-задания

1. **Разминка.** Установи Allure CLI (один раз на свою машину) и прогони полный локальный цикл: `pytest --alluredir=allure-results` → `allure serve allure-results`. Найди в открывшемся отчёте вкладку "Suites" и убедись, что видишь дерево `epic -> feature -> test` из своих тестов.
2. **Основное.** Вместо `allure serve` выполни `allure generate allure-results -o allure-report --clean`, затем открой файл `allure-report/index.html` вручную (двойным кликом или через `file://`-путь в браузере). Сравни впечатление с `allure serve`: в чём разница между "временным отчётом, который сам открылся" и "постоянной папкой с готовым HTML".
3. **Ближе к практике.** Смоделируй ситуацию "скачал артефакт из CI": прогони тесты локально с `--alluredir=allure-results`, как будто это и есть распакованный артефакт с пайплайна. Затем открой `.github/workflows/ci.yml` (или `.gitlab-ci.yml`) и найди, в каком именно шаге сохраняется этот артефакт и куда на реальной странице прогона нужно нажать, чтобы его скачать.
4. **Со звёздочкой.** Сгенерируй локально и `allure-results/`, и `allure-report/`, затем выполни `git status` в корне проекта. Убедись, что обе папки не предлагаются к добавлению в коммит, и найди в `boilerplate/.gitignore` строки, которые за это отвечают — объясни, почему их отсутствие было бы проблемой для общего репозитория, куда сдают PR несколько студентов.
