# 7.4. Рефакторинг без поломок

## Зачем это нужно

К концу курса в общем репозитории накопилось дублирование: несколько похожих Page Object'ов, несколько похожих API-клиентов, возможно — повторяющиеся фикстуры. Рефакторинг мелких кусков — последний практический навык курса: изменить структуру кода, не сломав ни одного существующего теста.

## Теория

### Главное правило

Безопасный рефакторинг подчиняется простому правилу: **до и после рефакторинга набор тестов должен быть зелёным, и сами тесты (если они не являются предметом рефакторинга) не должны меняться.** Если для рефакторинга кода пришлось переписать тесты на него — это уже не совсем рефакторинг, а изменение поведения, и тикет стоит переформулировать.

### Практический алгоритм

1. **Убедись, что зона рефакторинга покрыта тестами.** Если метод, который собираешься менять, вообще не тестируется — рефакторинг рискованный: некому подтвердить, что поведение не изменилось. В этом случае первый шаг — написать тест на текущее поведение, и только потом рефакторить.
2. **Меняй маленькими шагами.** Например, вынося общий метод из двух Page Object в `BasePage`: сначала добавь метод в `BasePage`, прогони тесты (ничего не должно сломаться, старый код ещё используется); потом замени использование в одном классе, прогони тесты; потом в другом.
3. **Не смешивай рефакторинг с добавлением новой функциональности** в одном PR — это разные по духу изменения, и в случае проблемы откатить/понять причину гораздо сложнее, если они перемешаны.

### Рефакторинг мелкими шагами на практике

Шаг 2 выше стоит увидеть не одной фразой, а как последовательность отдельных состояний кода, каждое из которых зелёное. Для примера с `check_all_visible` (см. ниже) это выглядит так:

```python
# Шаг 1: добавили метод в BasePage, никто его ещё не использует
class BasePage:
    def check_all_visible(self, *locators) -> None:
        for locator in locators:
            expect(locator).to_be_visible()

# → прогнали весь набор тестов: всё зелёное, поведение не изменилось,
#   потому что RegistrationPage пока не вызывает новый метод

# Шаг 2: переключили RegistrationPage на новый метод
class RegistrationPage(BasePage):
    def check_visible_registration_form(self) -> None:
        self.check_all_visible(
            self.email_input, self.username_input,
            self.password_input, self.registration_button,
        )

# → прогнали весь набор тестов ещё раз: всё так же зелёное
```

Если на шаге 2 что-то упадёт — сразу понятно, что проблема именно в переключении `RegistrationPage` на общий метод, а не где-то ещё в PR, потому что между шагами не было других изменений. В этом и есть смысл маленьких шагов: каждый шаг сам по себе легко проверить и легко откатить.

### Тот же принцип для API-клиентов

Дублирование бывает не только у Page Object, но и у клиентов. Допустим, рядом с `UsersClient` появился `PostsClient` с похожей парой методов:

```python
# было — похожая пара методов в разных клиентах
class UsersClient(APIClient):
    def get_user_api(self, user_id: int) -> Response:
        return self.get(f"/users/{user_id}")

class PostsClient(APIClient):
    def get_post_api(self, post_id: int) -> Response:
        return self.get(f"/posts/{post_id}")
```

Оба метода — это "GET по числовому id к своему ресурсу". Вынести это можно в `APIClient` общим приёмом:

```python
# стало — общий метод в APIClient, специализированные клиенты его переиспользуют
class APIClient:
    ...
    def get_by_id(self, resource: str, item_id: int) -> Response:
        return self.get(f"/{resource}/{item_id}")

class UsersClient(APIClient):
    def get_user_api(self, user_id: int) -> Response:
        return self.get_by_id("users", user_id)

class PostsClient(APIClient):
    def get_post_api(self, post_id: int) -> Response:
        return self.get_by_id("posts", post_id)
```

Публичные имена методов (`get_user_api`, `get_post_api`) и их сигнатуры не поменялись — значит, ни один существующий тест, вызывающий эти методы, ничего не заметит. Изменилась только внутренняя реализация.

## Пример: вынос общего кода из двух Page Object

Допустим, у `RegistrationPage` и нового `LoginPage` появился одинаковый метод проверки видимости всех полей формы. Вместо дублирования:

```python
# было — похожий код в двух классах
class RegistrationPage(BasePage):
    def check_visible_registration_form(self) -> None:
        expect(self.email_input).to_be_visible()
        expect(self.username_input).to_be_visible()
        expect(self.password_input).to_be_visible()
        expect(self.registration_button).to_be_visible()
```

Можно вынести в `BasePage` общий вспомогательный метод, принимающий список локаторов:

```python
# стало — общая логика в BasePage
class BasePage:
    ...
    def check_all_visible(self, *locators) -> None:
        for locator in locators:
            expect(locator).to_be_visible()


class RegistrationPage(BasePage):
    def check_visible_registration_form(self) -> None:
        self.check_all_visible(
            self.email_input,
            self.username_input,
            self.password_input,
            self.registration_button,
        )
```

Ключевой момент: после такого изменения `test_successful_registration` из `boilerplate/tests/ui/test_registration.py` не меняется вообще — он по-прежнему вызывает `registration_page.check_visible_registration_form()` и ожидает того же поведения. Именно так выглядит "безопасный" рефакторинг: тест не заметил изменения реализации.

## Частые ошибки

- Рефакторить сразу всё, что "не нравится", вместо конкретного тикета — рефакторинг без чёткой границы легко превращается в незаконченный PR на тысячу строк.
- Не прогонять полный набор тестов после рефакторинга, ограничиваясь только тестами "по смыслу" затронутого модуля — используемые повсеместно базовые классы (`BasePage`, `APIClient`) могут повлиять на тесты, которые визуально с рефакторингом не связаны.
- Переименовывать публичные методы/классы, которые используются в тестах других студентов, без согласования — в общем репозитории это ломает чужой код, а не только свой.
- Рефакторить метод, у которого нет ни одного теста, "по памяти" — без теста на текущее поведение некому подтвердить, что после рефакторинга ничего не изменилось.

## Мини-задания

1. **Разминка.** Ниже — две функции с почти одинаковой логикой проверки. Ничего не ломая (тест ниже должен продолжать проходить без изменений), предложи, как вынести общую часть в одну вспомогательную функцию, которую вызовут обе:

   ```python
   def is_valid_username(username: str) -> bool:
       return 3 <= len(username) <= 20 and username.isalnum()

   def is_valid_slug(slug: str) -> bool:
       return 3 <= len(slug) <= 20 and all(ch.isalnum() or ch == "-" for ch in slug)

   # tests/unit/test_string_utils.py — должен остаться без изменений:
   def test_is_valid_username():
       assert is_valid_username("mike_qa123") in (True, False)  # не меняем
   ```

2. **Основное.** `RegistrationPage` и `DashboardPage` (см. `boilerplate/pages/`) — оба наследуются от `BasePage`, но в `DashboardPage` вручную повторяется тот же паттерн "открыть страницу и проверить, что попал на её URL", что уже частично есть в `BasePage.open()`/`check_current_url()`. Напиши, как оформить в `BasePage` общий метод `open_and_check(url)`, объединяющий `self.open(url)` и `self.check_current_url(url)`, и как после этого сократится `DashboardPage.check_opened()` — так, чтобы `test_successful_registration` из `tests/ui/test_registration.py` не изменился ни на строку.

3. **Ближе к практике.** Найди в общем репозитории (или предположи по структуре `boilerplate/`) один реальный кандидат на рефакторинг — повторяющийся кусок кода в двух похожих местах — и опиши план: что именно выносится, куда, какими маленькими шагами (по аналогии с разделом "Рефакторинг мелкими шагами на практике"), и какие тесты должны остаться зелёными после каждого шага, не меняя своего текста.

4. **Со звёздочкой.** Тикет просит переименовать метод `UsersClient.get_user_api()` в `fetch_user()`, потому что новое имя "понятнее". Проблема: этим методом в тестах пользуются ещё несколько студентов потока, и просто переименовать его — значит сломать их PR и ветки. Опиши безопасный способ провести это переименование в общем репозитории, не ломая чужой код одномоментно (подсказка: подумай про промежуточный шаг, где старое имя ещё работает, но помечено как устаревшее в пользу нового).
