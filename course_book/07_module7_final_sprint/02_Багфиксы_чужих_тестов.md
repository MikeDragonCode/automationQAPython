# 7.2. Багфиксы чужих тестов

## Зачем это нужно

Чинить чужой тест сложнее, чем свой: нет контекста "почему я это так написал", приходится восстанавливать логику по коду и по allure-отчёту. Это ровно тот навык, который отличает "прошёл курс" от "готов работать в команде".

## Теория

### Алгоритм работы с чужим упавшим/сломанным тестом

1. **Воспроизведи падение локально.** Не чини "на глаз" по одному только описанию тикета — сначала запусти тест сам и увидь то же самое.
2. **Прочитай allure-отчёт теста** (модуль 5) — шаги и, для UI, скриншот на падении часто сразу показывают, где расходится ожидание с реальностью.
3. **Определи тип проблемы** (подробно — в следующем разделе).
4. **Исправь минимально необходимое.** Тикет "почини тест X" не означает "перепиши файл с нуля".
5. **Прогони весь набор тестов**, не только починенный — исправление могло задеть соседние тесты, использующие тот же Page Object/клиент.

### Три типа проблемы — и как их отличить

**Баг в тесте** — тест написан некорректно: неверные ожидания, гонка состояний в самом тесте, копипаста без изменения параметров. Код, который тест проверяет, на самом деле работает правильно.

```python
# tests/api/test_users.py
def test_get_user(users_client):
    user = users_client.get_user(user_id=1)
    assert user.id == 2  # баг в тесте: сравнивает с чужим id, а не с тем, что запросили
```

Признак: если поправить сам тест (без единой строчки в `clients/`/`pages/`), он начинает стабильно проходить, и это соответствует тому, что реально возвращает API/UI.

**Баг в тестируемом коде** — тест написан верно, а код (Page Object, API-клиент), который он проверяет, действительно ведёт себя не так, как ожидается.

```python
# clients/users/users_client.py
def get_user_api(self, user_id: int) -> Response:
    return self.get(f"/users/{user_id + 1}")  # баг в коде: лишний +1 в пути
```

Признак: тест логически написан корректно (проверяет ровно то, что заявлено в названии), но стабильно получает не то значение — значит, чинить нужно `clients/`/`pages/`, а не сам тест.

**Флейковость** — тест то падает, то проходит без изменений кода; чаще всего из-за недостаточного ожидания в UI-тестах или из-за общего/изменчивого состояния данных в API-тестах (например, публичный демо-API вернул чуть другие данные).

Признак: локальный повторный запуск того же теста без единой правки иногда красный, иногда зелёный — если падение невозможно стабильно воспроизвести, это не "баг в тесте" и не "баг в коде" в чистом виде, а именно флейк, и чинить нужно устойчивость, а не логику.

### Читать контекст перед правкой

Прежде чем менять код, посмотри на соседние строки: docstring класса, комментарий над странным на первый взгляд условием, название соседних тестов в том же файле. Иногда решение, которое хочется "исправить", было осознанным компромиссом — например, обработка edge case, о котором тикет ничего не знает. Если решение кажется явно неверным — исправляй, но не игнорируя контекст молча.

## Пример: разбор флейкового UI-теста

Допустим, тест из `boilerplate/tests/ui/test_registration.py` изредка падает на CI со скриншотом, где форма ещё не полностью прогрузилась. Частая причина — клик или проверка происходят до того, как элемент на самом деле стал интерактивным. В Playwright это почти всегда лечится не добавлением `time.sleep(...)` (антипаттерн — не решает причину и просто тратит время), а использованием встроенных ожиданий (`expect(...)`), которые уже применяются в `RegistrationPage.check_visible_registration_form()`. Если ожидание уже есть, но проблема сохраняется — стоит проверить, не выполняется ли действие с элементом, для которого явного ожидания видимости ещё не добавили.

## Частые ошибки

- Чинить симптом, а не причину: например, просто ослабить проверку (`assert response.status_code in [200, 404]` вместо разбора, почему код вдруг стал 404).
- Добавлять `time.sleep()` как "быстрое решение" флейковости в UI-тестах — маскирует проблему, но не решает её и замедляет весь набор тестов.
- Не читать существующие комментарии/docstring в коде перед правкой — иногда странное на первый взгляд решение уже было осознанным компромиссом.
- Путать баг в тесте с багом в коде из-за спешки — исправить тест, когда на самом деле сломан код (или наоборот), и получить "зелёный", но неверный результат: тест зелёный, а реальное поведение приложения по-прежнему неправильное.

## Мини-задания

1. **Разминка.** Ниже — тест с одним явно обозначенным багом (баг в тесте, тип из теории). Найди его и опиши, как должна выглядеть исправленная строка:

   ```python
   @allure.title("Создание пользователя")
   def test_create_user(users_client):
       request = CreateUserRequestSchema(
           name="QA Student",
           username=get_random_username(),
           email=get_random_email(),
       )
       created_user = users_client.create_user(request)
       assert created_user.name == "QA Student"
       assert created_user.username == request.name  # <-- баг где-то здесь
   ```

2. **Основное.** В этом тесте баг тоже есть, но без подсказки, в какой именно строке — определи тип проблемы (баг в тесте или баг в коде) и объясни, по каким признакам ты это понял:

   ```python
   # pages/registration_page.py
   def fill_registration_form(self, email: str, username: str, password: str) -> None:
       self.email_input.fill(username)   # перепутаны email и username
       self.username_input.fill(email)
       self.password_input.fill(password)

   # tests/ui/test_registration.py
   def test_successful_registration(user_data, registration_page, dashboard_page):
       registration_page.open_page()
       registration_page.fill_registration_form(**user_data)
       registration_page.click_registration_button()
       dashboard_page.check_opened()
   ```

3. **Ближе к практике.** Тикет: "После рефакторинга фикстур тест `test_create_user` из `tests/api/test_users.py` стал иногда падать с ошибкой валидации email — раньше такого не было". Ниже — фикстура и тест. Найди проблему, возникающую из-за взаимодействия фикстуры с тестом (а не из-за одной только строчки внутри теста), и опиши, что изменить:

   ```python
   # conftest.py
   @pytest.fixture(scope="session")
   def new_user_request() -> CreateUserRequestSchema:
       return CreateUserRequestSchema(
           name="QA Student",
           username=get_random_username(),
           email=get_random_email(),
       )

   # tests/api/test_users.py
   def test_create_user(users_client, new_user_request):
       created_user = users_client.create_user(new_user_request)
       assert created_user.email == new_user_request.email

   def test_create_second_user(users_client, new_user_request):
       created_user = users_client.create_user(new_user_request)
       assert created_user.username != "duplicate"
   ```

   Подсказка: обрати внимание на `scope="session"` и на то, что даёт `get_random_email()`/`get_random_username()` при вызове один раз на всю сессию тестов, а не при каждом обращении к фикстуре.

4. **Со звёздочкой.** Тест ниже эмулирует реальную флейковость: он использует `time.sleep()` вместо ожидания Playwright и изредка падает на CI (но не локально, где машина обычно быстрее). Перепиши его так, чтобы он не полагался на фиксированную задержку, а дождался готовности элемента — по аналогии с `check_visible_registration_form()` из "Примера" этого урока:

   ```python
   def test_dashboard_shows_title(page, dashboard_page):
       dashboard_page.open(dashboard_page.URL)
       time.sleep(1)  # флейк: иногда 1 секунды не хватает на медленном CI
       assert dashboard_page.toolbar_title.text_content() == "Dashboard"
   ```
