# 4.17. Домашнее задание

## Формулировка

Открой PR в свой форк общего репозитория (`boilerplate/`) с 2–3 новыми UI-тестами на Playwright. Тесты должны работать через Page Object по образцу `RegistrationPage`/`DashboardPage` (уроки 4.12–4.14), а не через голые вызовы `page.locator(...)` внутри теста.

Минимальный набор изменений:

1. **Добавь новый Page Object.** Проще всего — `LoginPage` для страницы `.../#/auth/login`, по шаблону из урока 4.16. Класс должен наследоваться от `BasePage`, хранить `URL`, создавать локаторы в конструкторе через `super().__init__(page)` и содержать отдельные методы-действия (`open_page`, `fill_login_form`, `click_login_button`) и метод-проверку (`check_visible_login_form`).
2. **Добавь фикстуру `login_page`** в `boilerplate/conftest.py`, рядом с уже существующими `registration_page`/`dashboard_page`, по образцу урока 4.15.
3. **Напиши 2–3 UI-теста** в `tests/ui/` (можно новый файл `test_login.py`, можно дополнить `test_registration.py` — смотри по смыслу сценария). Как минимум один тест должен быть happy path, как минимум один — негативный сценарий.

### Из чего выбрать сценарии

Ниже — варианты, поведение которых мы заранее проверили вручную на реальном приложении, чтобы домашнее задание не строилось на догадках о том, как оно себя ведёт.

**Happy path: логин после регистрации.** У приложения нет заранее созданных тестовых пользователей — единственный способ получить рабочие email/пароль для логина — сначала зарегистрироваться. Сценарий: зарегистрировать нового пользователя через `registration_page` (как в `test_registration.py`), разлогиниться, затем залогиниться этими же данными через `login_page` и проверить, что снова открылся Dashboard.

**Негативный сценарий №1: регистрация с уже занятым email.** Если отправить форму регистрации с email, который уже зарегистрирован, приложение **не переходит на Dashboard** — URL остаётся `.../#/auth/registration`, а над формой появляется предупреждение с текстом `User already exists` (у него есть собственный `data-testid="registration-page-user-already-exists-alert"` — найдёшь его в DevTools так же, как в уроке 4.2). Тест: зарегистрировать пользователя один раз, затем повторить регистрацию с тем же email (и любым другим username) и проверить, что появилось это предупреждение, а URL не изменился.

**Негативный сценарий №2: валидация пустой формы.** Если открыть страницу регистрации и ничего не заполнять, кнопка `Registration` находится в заблокированном состоянии (атрибут `disabled`). Тест: открыть страницу регистрации и проверить через `expect(registration_button).to_be_disabled()`, что кнопка неактивна, пока форма не заполнена (это же можно проверить и для `LoginPage`, если её кнопка ведёт себя аналогично — проверь вручную перед тем, как писать тест).

Выбери любые 2–3 сценария из перечисленных (или похожие по духу) — необязательно реализовывать все три.

### Allure

В существующих тестах (`test_registration.py`) уже используются `@allure.epic`, `@allure.feature`, `@allure.title` на уровне класса/теста и `allure.step(...)` внутри теста. Подробно Allure разберём в модуле 5, но декоратор и шаги уже нужны в этом домашнем задании — bери `test_registration.py` как образец оформления, не изобретая новый стиль.

## Критерии "готово"

- [ ] Новый Page Object (например, `LoginPage`) добавлен в `pages/`, наследуется от `BasePage` по образцу `RegistrationPage`/`DashboardPage` — не переизобретает архитектуру заново.
- [ ] Локаторы созданы один раз в конструкторе и сохранены в атрибуты `self.*`, а не пересоздаются внутри методов.
- [ ] Фикстура для нового Page Object добавлена в `conftest.py` рядом с существующими (`registration_page`, `dashboard_page`).
- [ ] Есть минимум 2 новых UI-теста, среди них — минимум один явно негативный сценарий (не только happy path).
- [ ] Все тесты используют `@pytest.mark.ui` и `allure.step(...)` внутри теста (по образцу `test_registration.py`).
- [ ] Ни один тест не содержит `page.locator(...)` напрямую — только вызовы методов Page Object.
- [ ] `pytest -m ui -v` проходит локально зелёным целиком, включая уже существовавший до тебя `test_registration.py`.
- [ ] PR открыт в общий репозиторий, в описании — что сделано и как проверить (см. правила PR в `boilerplate/README.md`).

## Что не входит в это домашнее задание

- Подробная работа с Allure-отчётами (вложения, категории, окружение) — это модуль 5. Здесь достаточно декораторов и шагов на уровне, который уже есть в `test_registration.py`.
- CI — модуль 6. Проверяй тесты локально, зелёный пайплайн для этого PR пока не обязателен.
- Попапы и нативные диалоги браузера (урок 4.9) — в текущих сценариях учебного приложения их нет, специально их встраивать в домашнее задание не нужно.
