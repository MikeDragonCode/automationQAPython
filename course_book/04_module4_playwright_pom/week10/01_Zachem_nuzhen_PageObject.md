# 4.11. Зачем нужен PageObject: проблема "тест знает слишком много"

## Зачем это нужно

С этого урока мы переходим от отдельных скриптов к архитектуре, на которой построен весь `boilerplate/` — общий репозиторий, в который ты будешь сдавать домашки начиная с модуля 2. Понимание того, зачем нужен Page Object, важно не для сдачи теста на знание термина, а для того, чтобы твои будущие Page Object'ы (например, `LoginPage` в домашнем задании этого модуля) вписывались в существующую архитектуру, а не ломали её.

## Теория

### Тест, который писали бы без Page Object

К концу недели 9 у нас есть рабочий сценарий регистрации. Если записать его прямо в тестовую функцию, получится примерно так:

```python
page.goto("https://nikita-filonov.github.io/qa-automation-engineer-ui-course/#/auth/registration")

page.locator("[data-testid='registration-form-email-input'] input").fill(user_data["email"])
page.locator("[data-testid='registration-form-username-input'] input").fill(user_data["username"])
page.locator("[data-testid='registration-form-password-input'] input").fill(user_data["password"])
page.locator("[data-testid='registration-page-registration-button']").click()
```

Сейчас, пока в проекте один тест и один сценарий, это выглядит нормально. Но представим, что проект начал расти — появились новые проверки: регистрация с пустым паролем, с уже занятым email, с некорректным email, логин, выход из системы. Практически каждый такой тест будет заново использовать одни и те же локаторы:

```python
"[data-testid='registration-form-email-input'] input"
"[data-testid='registration-form-username-input'] input"
"[data-testid='registration-form-password-input'] input"
"[data-testid='registration-page-registration-button']"
```

### Почему дублирование локаторов — это проблема

Представим, что разработчик поменял разметку и локатор поля email превратился из `[data-testid='registration-form-email-input']` в `[data-testid='registration-email-input']`. Если этот локатор скопирован в десять тестов — исправлять придётся в десяти местах. В пятьдесят тестов — в пятидесяти. Причём проблема не только в объёме правок: чем больше копий одного и того же кода, тем выше шанс что-то пропустить и получить нестабильные тесты, которые проходят или падают в зависимости от того, где именно забыли обновить локатор.

### Почему это делает тест менее читаемым

Даже если бы локаторы никогда не менялись, есть вторая проблема. Представь не четыре строки с `page.locator(...)`, а сорок. Тест начинает описывать не сценарий пользователя, а технические детали реализации страницы: CSS-селекторы, вызовы Playwright, промежуточные переменные. При этом реальный сценарий очень простой:

1. Открыть страницу регистрации.
2. Заполнить форму.
3. Нажать кнопку регистрации.
4. Проверить, что открылся Dashboard.

Получается, что для компьютера тест понятен, а для человека — уже не очень.

### Идея Page Object

Решение — паттерн **Page Object**. Каждая страница приложения описывается отдельным классом (`RegistrationPage`, `DashboardPage`). Внутри такого класса находятся локаторы, действия пользователя и проверки, относящиеся именно к этой странице. Тест перестаёт работать напрямую с локаторами — вместо этого он работает с объектами страниц.

Было (тест разговаривает с Playwright напрямую):

```
найди поле email
заполни поле email
найди поле username
заполни поле username
найди кнопку
нажми кнопку
```

Стало (тест разговаривает на уровне пользовательских действий):

```python
registration_page.fill_registration_form(...)
registration_page.click_registration_button()
```

Появляется разделение ответственности: тест отвечает на вопрос "что делает пользователь", а класс страницы — на вопрос "как именно это реализовано технически" (какие локаторы, как найти кнопку, как проверить состояние). Если локатор поля email изменится, исправление потребуется внести только в одном месте — внутри `RegistrationPage`. Все тесты, использующие эту страницу, продолжат работать без изменений.

Важно понимать: Page Object — это не особенность Playwright и не возможность pytest. Это архитектурный паттерн организации автотестов, который используется во многих инструментах и языках.

### Из чего состоит Page Object: локаторы, действия, проверки

Внутри `RegistrationPage` (мы разберём его целиком на уроке 4.13) уже сейчас видно, что содержимое класса делится на три чётких группы, и это деление не случайное:

```python
# 1. Локаторы — созданы один раз в конструкторе
self.email_input = page.locator("[data-testid='registration-form-email-input'] input")
self.registration_button = page.locator("[data-testid='registration-page-registration-button']")

# 2. Действия пользователя — методы-глаголы
def fill_registration_form(self, email, username, password): ...
def click_registration_button(self): ...

# 3. Проверки состояния — методы с префиксом check_
def check_visible_registration_form(self): ...
```

Тест не видит первую группу вообще — он работает только со второй и третьей. Именно такое разделение и убирает из теста технические детали, а не что-то более сложное.

### Единообразные имена методов помогают ориентироваться в чужом коде

Присмотревшись к паттерну выше, можно заметить закономерность в названиях: методы, которые выполняют действие, начинаются с глагола (`open_page`, `fill_registration_form`, `click_registration_button`), а методы, которые ничего не меняют и только проверяют состояние страницы, — с `check_` (`check_visible_registration_form`). Это не требование Playwright или pytest, а просто договорённость внутри проекта. Но следовать ей стоит: увидев в чужом Page Object метод `check_opened()`, ты сразу, не читая тело метода, понимаешь, что это проверка, а не действие, — а значит, вызов этого метода ничего на странице не изменит.

## Пример

В `boilerplate/` этот паттерн уже реализован и работает — не как учебный пример "как могло бы быть", а как проверенный код, против которого реально проходит `pytest -m ui`:

```
boilerplate/
├── pages/
│   ├── base_page.py
│   ├── registration_page.py
│   └── dashboard_page.py
├── tests/ui/
│   └── test_registration.py
└── conftest.py
```

В следующих четырёх уроках мы разберём эти файлы построчно — не для того, чтобы переписать их (их менять не нужно), а чтобы понимать, по какому образцу добавлять новые страницы.

## Частые ошибки

- Считать, что Page Object — это обязательно много кода и сложная архитектура. На практике, как ты увидишь в `DashboardPage`, класс может быть совсем небольшим — ровно настолько большим, насколько того требуют тесты.
- Пытаться засунуть в один Page Object сразу несколько разных страниц приложения "для экономии файлов" — это возвращает ту же проблему дублирования и путаницы, от которой паттерн должен избавлять.
- Путать Page Object с фикстурами pytest — это разные вещи, которые, как мы увидим на уроке 4.15, отлично работают вместе: фикстура создаёт объект Page Object и передаёт его в тест.
