# 4.10. Проверка состояния страницы через expect()

## Зачем это нужно

Тест без проверок — это просто скрипт: он что-то делает, но не отвечает на вопрос "получилось или нет". Мы уже видели `expect()` в деле на примере URL и заголовка Dashboard. Теперь соберём более полную картину — какие проверки вообще бывают и когда какую использовать. Именно этот набор проверок ты будешь использовать в методах `check_*` при разборе `RegistrationPage` и `DashboardPage` на неделе 10.

## Теория

Все проверки в Playwright строятся по одному шаблону:

```python
expect(объект).to_что-то(ожидаемое_значение)
```

Где `объект` — это либо `page` (для проверок уровня страницы, например URL), либо результат `page.locator(...)` (для проверок конкретного элемента).

### Проверки видимости

```python
expect(locator).to_be_visible()
expect(locator).to_be_hidden()
```

`to_be_visible()` дожидается, пока элемент не появится в DOM и не станет видимым (не скрыт через CSS, не имеет нулевого размера). `to_be_hidden()` — обратная проверка: элемента либо нет в DOM, либо он скрыт.

### Проверки текста

```python
expect(locator).to_have_text("Dashboard")
expect(locator).to_contain_text("Dashboard")
```

`to_have_text(...)` проверяет точное совпадение текста элемента. `to_contain_text(...)` — что текст элемента содержит указанную подстроку. Используй `to_contain_text`, когда важна не вся строка целиком, а только её часть (например, сообщение об ошибке, где кроме текста есть ещё и код ошибки).

### Проверки значения поля

```python
expect(locator).to_have_value("user@example.com")
```

Проверяет текущее значение `input` или `textarea` — полезно после `.fill()`, чтобы убедиться, что значение действительно установилось (хотя обычно в этом нет необходимости — `.fill()` сам ждёт, пока поле не будет готово к вводу).

### Проверка атрибута элемента

Иногда важно проверить не текст и не видимость, а конкретный HTML-атрибут элемента — например, `href` у ссылки:

```python
expect(page.locator("a[data-testid='docs-link']")).to_have_attribute("href", "https://example.com/docs")
```

Это тот же принцип, что и у остальных проверок: `expect()` дождётся, пока атрибут не примет нужное значение (это важно, если атрибут выставляется JS-кодом не мгновенно), и только потом завершит проверку.

### Проверки состояния элемента

```python
expect(locator).to_be_enabled()
expect(locator).to_be_disabled()
expect(locator).to_be_checked()
```

Эти проверки полезны там, где интерфейс явно блокирует действия — например, кнопка отправки формы становится активной только после заполнения обязательных полей.

### Проверка URL страницы

```python
expect(page).to_have_url("https://nikita-filonov.github.io/qa-automation-engineer-ui-course/#/dashboard")
```

Мы уже использовали эту проверку для перехода на Dashboard. Обрати внимание: здесь в `expect()` передаётся не локатор, а сам объект `page`.

### Проверка количества элементов

```python
expect(page.locator("[data-testid='user-row']")).to_have_count(3)
```

Полезно для списков — например, убедиться, что после фильтрации осталось ровно нужное количество строк таблицы. Отдельный частый случай — проверка, что подходящих элементов нет вовсе: `expect(locator).to_have_count(0)` подтверждает отсутствие совпадений и одинаково хорошо работает и когда элемент скрыт, и когда его вообще нет в DOM.

### Отрицание проверки

У любой проверки есть форма с отрицанием — префикс `not_`:

```python
expect(locator).not_to_be_visible()
expect(locator).not_to_have_text("Error")
```

Это удобнее, чем оборачивать проверку в `assert not ...`: `not_to_be_visible()` так же умеет ждать, пока элемент не исчезнет, а не просто проверяет состояние один раз.

## Пример

Собираем несколько проверок в одном сценарии — открыли Dashboard и проверили сразу несколько фактов о странице:

```python
from playwright.sync_api import expect

expect(page).to_have_url("https://nikita-filonov.github.io/qa-automation-engineer-ui-course/#/dashboard")

dashboard_title = page.locator("[data-testid='dashboard-toolbar-title-text']")
expect(dashboard_title).to_be_visible()
expect(dashboard_title).to_have_text("Dashboard")
```

Именно эти три строки в чуть другом виде ты увидишь в методе `DashboardPage.check_visible_toolbar_title()` в `boilerplate/pages/dashboard_page.py` — переход к Page Object в следующем уроке не меняет сути проверок, а просто переносит их в отдельный класс.

## Частые ошибки

- Использовать `to_have_text(...)`, когда нужно проверить только часть текста — тест станет хрупким при малейшем изменении формулировки. В таких случаях лучше `to_contain_text(...)`.
- Проверять состояние элемента через `.is_visible()` (обычный метод, без ожидания) вместо `expect(...).to_be_visible()` — первый вариант не умеет ждать и может дать ложный отрицательный результат.
- Забывать про `not_to_...` и писать `assert not expect(...)` — так `expect()` не работает, у него есть собственный синтаксис отрицания.
- Проверять атрибут элемента "руками" через `get_attribute(...)` сразу после действия вместо `expect(...).to_have_attribute(...)` — теряется автоматическое ожидание, и проверка может сработать раньше, чем атрибут реально обновится.
