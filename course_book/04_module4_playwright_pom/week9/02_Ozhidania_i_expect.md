# 4.7. Автоматические ожидания и expect()

## Зачем это нужно

Реальные веб-страницы не появляются мгновенно: после клика может произойти переход на другой URL, элемент может отрисоваться с небольшой задержкой, форма может замениться сообщением об успехе. Если тест проверяет состояние страницы раньше, чем оно наступило, тест падает не потому, что приложение сломано, а потому что тест "не подождал". Это одна из самых частых причин нестабильных (flaky) UI-тестов, и Playwright решает эту проблему на уровне архитектуры — важно понимать, как именно.

## Теория

### Проблема: страница обновляется не мгновенно

Допустим, мы кликнули на кнопку Registration и сразу проверяем URL:

```python
page.locator("[data-testid='registration-page-registration-button']").click()
assert page.url == "https://nikita-filonov.github.io/qa-automation-engineer-ui-course/#/dashboard"
```

Если переход на Dashboard занимает даже небольшое время, `assert` может сработать раньше, чем URL успеет измениться, — и тест упадёт, хотя приложение работает правильно.

### Явные ожидания vs автоматические ожидания

Одно из решений этой проблемы, которое встречается в других инструментах автоматизации — явные ожидания: явно прописать в коде "подожди N секунд" или "жди появления элемента до N секунд, проверяя каждые полсекунды". Такой подход рабочий, но у него есть минусы: фиксированные паузы либо слишком короткие (тест всё равно падает), либо слишком длинные (тест выполняется медленнее, чем нужно).

Playwright устроен иначе — у него встроены **автоматические ожидания (auto-waiting)**. Большинство действий (`click()`, `fill()`) и все проверки через `expect()` сами ждут, пока элемент не окажется в нужном состоянии (появится в DOM, станет видимым, станет доступным для взаимодействия), и только после этого выполняются. Ждать вручную с помощью `time.sleep()` в Playwright-тестах, как правило, не нужно — это ключевая идея, отличающая Playwright от многих более старых инструментов автоматизации.

### `expect()` — проверки с автоматическим ожиданием

Для проверок в Playwright используется функция `expect`:

```python
from playwright.sync_api import expect
```

Пример проверки URL:

```python
expect(page).to_have_url("https://nikita-filonov.github.io/qa-automation-engineer-ui-course/#/dashboard")
```

Это не разовая сверка значения, как обычный `assert`. `expect(...)` умеет **повторно проверять условие в течение отведённого времени**, пока оно не станет истинным (или пока не истечёт таймаут). Если переход на Dashboard занимает долю секунды, `expect` дождётся этого перехода и только потом либо подтвердит успех, либо, если условие так и не выполнилось, завершит тест ошибкой с понятным сообщением.

Это же справедливо для проверок элементов:

```python
dashboard_title = page.locator("[data-testid='dashboard-toolbar-title-text']")
expect(dashboard_title).to_be_visible()
expect(dashboard_title).to_have_text("Dashboard")
```

`to_be_visible()` дожидается, пока элемент не станет видимым на странице. `to_have_text(...)` дожидается, пока текст элемента не совпадёт с ожидаемым.

### Почему `expect()`, а не `assert`

Можно было бы написать:

```python
assert page.url == expected_url
```

Но `assert` проверяет значение только один раз, в момент выполнения строки — без повторных попыток и без ожидания. `expect()` устроен так, что умеет ждать нужное состояние страницы, и именно поэтому в Playwright-тестах для проверок почти всегда используется `expect()`, а не обычный `assert`. Ты увидишь этот же принцип в `BasePage.check_current_url()` из `boilerplate/pages/base_page.py` на неделе 10 — там тоже используется `expect(self.page).to_have_url(...)`, а не `assert self.page.url == ...`.

### У `expect()` тоже есть предел ожидания

Автоматическое ожидание не значит "ждать вечно". У `expect()` есть предустановленный таймаут по умолчанию (несколько секунд), и если условие за это время так и не выполнилось, `expect()` останавливает выполнение с ошибкой. Этого значения обычно достаточно, но при необходимости таймаут можно переопределить для конкретной проверки через параметр `timeout` (в миллисекундах):

```python
expect(dashboard_title).to_be_visible(timeout=10_000)
```

Увеличивать таймаут стоит точечно — для конкретного места, где ты точно знаешь, что действие занимает больше времени обычного, — а не "на всякий случай" для всех проверок подряд. Иначе тест, в котором реально что-то сломалось, будет просто гораздо дольше сообщать об этом.

### `assert` всё ещё нужен — просто не для состояния страницы

Всё сказанное не значит, что обычный `assert` в Playwright-тестах больше не нужен вообще. Для сравнения значений, никак не связанных с состоянием браузера, — например, ты сам посчитал ожидаемое число в тестовых данных или сравниваешь две обычные Python-переменные, — `assert` по-прежнему на своём месте:

```python
expected_total = 10 + 25
assert expected_total == 35, "Неверная сумма в тестовых данных"
```

Правило простое: как только проверка касается того, что происходит на странице (виден ли элемент, какой у него текст, какой URL) — используй `expect()`, потому что там нужно ожидание. Как только речь про обычные значения, вычисленные в самом тесте, — обычного `assert` вполне достаточно.

### Что показывает ошибка, если `expect()` так и не дождался

Если время ожидания вышло, а условие так и не выполнилось, `expect()` завершает выполнение исключением с подробным сообщением: что именно проверялось, какое значение ожидалось и какое было получено по факту (или что элемент вовсе не был найден за отведённое время). Это удобнее, чем обычный `assert`, где пришлось бы самому дописывать пояснение вторым аргументом, чтобы понять, что пошло не так.

## Пример

Полный фрагмент с проверками после регистрации:

```python
from playwright.sync_api import expect, sync_playwright

with sync_playwright() as p:
    browser = p.chromium.launch(headless=False)
    page = browser.new_page()

    page.goto("https://nikita-filonov.github.io/qa-automation-engineer-ui-course/#/auth/registration")

    page.locator("[data-testid='registration-form-email-input'] input").fill("user@example.com")
    page.locator("[data-testid='registration-form-username-input'] input").fill("testuser")
    page.locator("[data-testid='registration-form-password-input'] input").fill("password123")
    page.locator("[data-testid='registration-page-registration-button']").click()

    expect(page).to_have_url(
        "https://nikita-filonov.github.io/qa-automation-engineer-ui-course/#/dashboard"
    )

    dashboard_title = page.locator("[data-testid='dashboard-toolbar-title-text']")
    expect(dashboard_title).to_be_visible()
    expect(dashboard_title).to_have_text("Dashboard")

    browser.close()
```

Мы проверяем и URL, и заголовок не потому, что это избыточно, а потому что это два разных факта: URL подтверждает, что приложение выполнило переход на нужный маршрут, а заголовок подтверждает, что страница действительно отрисовалась пользователю. Одной проверки URL не всегда достаточно — адрес мог измениться, а сама страница зависнуть на пустом экране.

## Частые ошибки

- Использовать `time.sleep()` "на всякий случай" вместо того, чтобы довериться `expect()` — это делает тесты медленнее и не решает проблему по-настоящему (если реальная задержка окажется больше, чем `sleep`, тест всё равно упадёт).
- Проверять состояние через `assert page.locator(...).is_visible()` сразу после действия — в отличие от `expect(...).to_be_visible()`, такая проверка не ждёт и может сработать до того, как элемент появится.
- Проверять только один признак результата (например, только URL) там, где для уверенности стоит проверить ещё и содержимое страницы.
- Увеличивать `timeout` "с запасом" для всех проверок подряд вместо того, чтобы разобраться, почему конкретное место работает медленно, — тест, в котором реально что-то сломалось, будет просто намного дольше сообщать об этом.
