# 4.1. HTML и DOM: как устроена веб-страница

## Зачем это нужно

Через несколько уроков ты начнёшь писать код, который открывает страницу, находит на ней поле `Email` и вводит туда текст. Чтобы код мог найти это поле, он должен понимать страницу не так, как её понимает человек ("вижу поле сверху слева"), а так, как её понимает браузер — как структуру элементов. Без этого понимания локаторы в следующих уроках будут выглядеть как магические заклинания, а не как логичные конструкции.

## Теория

### HTML описывает структуру, а не поведение

**HTML** — язык разметки, который описывает, из каких элементов состоит страница. Он не отвечает за поведение теста, только за структуру: где кнопка, где поле ввода, где текст.

Упрощённая форма регистрации в HTML:

```html
<form>
    <input type="email" name="email" />
    <input type="text" name="username" />
    <input type="password" name="password" />
    <button>Registration</button>
</form>
```

Здесь `<form>` — это форма, `<input>` — поле ввода, `<button>` — кнопка. Каждый такой элемент, который браузер отрисовывает на странице, соответствует одному тегу в HTML.

### Атрибуты добавляют элементу дополнительный смысл

У тега могут быть **атрибуты** — дополнительная информация об элементе, записанная прямо внутри открывающего тега:

```html
<input type="email" name="email" placeholder="Email" />
```

`type="email"` говорит, что поле для email, `name="email"` отличает это поле от других, `placeholder="Email"` задаёт подсказку, которую видит пользователь, пока поле пустое. Атрибуты — это то, за что в первую очередь будут цепляться наши локаторы: одинаковый тег `input` у трёх разных полей формы, но разные атрибуты позволяют их отличить друг от друга.

### Какие теги встретятся тебе чаще всего

Мы не изучаем вёрстку и не разбираем все теги HTML — для автоматизации достаточно узнавать в разметке несколько повторяющихся вещей:

- поля форм — `input`, `textarea`, `select`;
- кнопки — `button` (иногда `input type="submit"`);
- ссылки — `a`;
- тексты и заголовки — `p`, `span`, `h1`–`h6`;
- контейнеры, которые ничего не значат сами по себе, а просто группируют другие элементы, — `div`, `section`.

Плюс специальные тестовые атрибуты, о них — чуть ниже.

### DOM — дерево элементов, с которым работает браузер

**DOM (Document Object Model)** — это внутренняя модель страницы, которую браузер строит на основе HTML. DOM представляет страницу как дерево объектов: каждый элемент HTML становится узлом этого дерева, с которым можно работать программно — искать, читать текст, кликать, вводить данные.

Наша форма в виде дерева:

```
form
├── input type="email" name="email"
├── input type="text" name="username"
├── input type="password" name="password"
└── button "Registration"
```

Когда мы пишем:

```python
page.locator("input[name='email']").fill("user@example.com")
```

мы не говорим браузеру "найди красивое поле слева сверху". Мы даём точное техническое указание: "найди в DOM элемент `input`, у которого атрибут `name` равен `email`, и введи в него текст". Playwright всегда работает именно с DOM-деревом, а не с картинкой на экране.

Важная деталь: DOM не всегда совпадает с исходным HTML-файлом. После загрузки страницы JavaScript часто добавляет, удаляет или изменяет элементы (подгружает данные, показывает всплывающее окно, дорисовывает форму). DOM — это всегда *текущее* состояние страницы, а не то, что было написано в HTML изначально.

### Родитель, потомок, соседние элементы

Дерево — это не просто картинка, а рабочие термины, которыми удобно описывать положение элемента:

- **родитель** — элемент, который содержит другой элемент внутри себя (в нашем примере `form` — родитель для всех четырёх элементов внутри);
- **потомок** (или дочерний элемент) — элемент внутри другого (все `input` и `button` — потомки `form`);
- **соседние элементы** (siblings) — элементы на одном уровне вложенности с общим родителем (три `input` и `button` — соседи друг другу, они не вложены один в другой).

Эти термины пригодятся уже в следующих уроках: когда локатор ищет элемент "внутри" другого, речь идёт именно об отношении родитель → потомок, а не о случайном соседстве на экране.

### Атрибуты, которые важны для автотестов

- `id` — уникальный идентификатор, хорош, если не сгенерирован автоматически (`id="mui-12345"` — плохой пример).
- `name` — часто встречается у полей форм, хорошо подходит для локаторов.
- `class` — обычно про стили, часто автогенерируется сборщиками (`class="css-1a2b3c"`) и не годится для стабильных тестов.
- `data-testid` (и его варианты `data-test-id`, `data-qa`, `qa-id`) — атрибут, который разработчики добавляют специально для автотестов. Не влияет на вёрстку и обычно не меняется при рефакторинге — лучший кандидат для локатора.
- `role`, `aria-*` — атрибуты доступности, тоже пригодны для поиска элементов.

## Пример

Три поля формы регистрации выглядят в HTML почти одинаково — все они `input` — но у каждого свой набор атрибутов:

```html
<input type="email" name="email" />
<input type="text" name="username" />
<input type="password" name="password" />
```

Именно атрибуты позволяют тесту отличить одно поле от другого, хотя тег `input` у них общий. А как соседние элементы внутри одного `form`, все три поля и кнопка находятся на одном уровне дерева — ни одно из них не вложено в другое.

## Частые ошибки

- Пытаться выучить все теги HTML и правила вёрстки — для автотестов это лишнее, нужен только практический минимум для поиска элементов.
- Путать тег (`<button>`) и элемент целиком (`<button>Registration</button>`) — на практике разница не критична, но полезно понимать оба термина.
- Строить локаторы по автогенерированным `class` или `id`, не проверив, стабильны ли они между запусками.
- Забывать, что DOM может отличаться от исходного HTML-файла из-за JavaScript — то, что видно в браузере "здесь и сейчас", не всегда совпадает с тем, что лежит в HTML-файле на сервере.

## Мини-задания

1. **Разминка.** Открой любую веб-страницу (например, github.com), нажми правой кнопкой мыши на любую кнопку и выбери "Просмотреть код" / "Inspect". Найди в открывшемся HTML: тег элемента, хотя бы два его атрибута и текст внутри тега.
2. **Основное.** На той же странице найди элемент-контейнер, у которого явно есть несколько дочерних элементов (например, меню, список ссылок в футере или карточку с несколькими полями). Определи: кто здесь родитель, перечисли хотя бы трёх его потомков и укажи, какие из этих потомков являются соседними элементами друг другу.
3. **Ближе к практике.** Найди на любом сайте форму с текстовыми полями (поиск, форма подписки, форма логина). Для каждого поля выпиши тег и все его атрибуты. Определи, у какого из полей есть атрибут, похожий на специальный тестовый (`data-testid`, `data-qa`, `data-test` и т.п.) — если такого нет, зафиксируй, что на этом сайте разработчики его не используют.
4. **Со звёздочкой.** На той же странице найди элемент, у которого есть одновременно `class` (по виду автогенерированный, например `css-a1b2c3` или с случайным набором символов) и более простой, читаемый атрибут (`name`, `type`, `aria-label` или похожий). Объясни своими словами, какой из этих атрибутов ты бы выбрал для локатора в автотесте и почему `class` в таком виде — плохой кандидат.
