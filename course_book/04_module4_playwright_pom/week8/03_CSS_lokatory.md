# 4.3. CSS-локаторы

## Зачем это нужно

Вся UI-автоматизация сводится к двум действиям: найти элемент и что-то с ним сделать (кликнуть, ввести текст, проверить состояние). Про "что-то сделать" мы поговорим на неделе 9. Сейчас — про "найти элемент", и это самый важный навык UI Automation Engineer, потому что без него ни одно действие и ни одна проверка не сработают.

## Теория

**Локатор** — это описание элемента, по которому Playwright находит его на странице. Можно представить локатор как адрес: как человек ищет дом по адресу, так Playwright ищет элемент по локатору.

```python
page.locator("[data-testid='registration-page-registration-button']")
```

Эта строка означает: "найди элемент, у которого атрибут `data-testid` равен `registration-page-registration-button`". После того как элемент найден, с ним можно работать:

```python
page.locator("[data-testid='registration-page-registration-button']").click()
```

Один из самых распространённых способов описывать локаторы — **CSS-локаторы** (CSS-селекторы). Не пугайся слова CSS: нам не нужно изучать CSS как язык стилизации, нужен только его синтаксис поиска элементов по тегу, атрибутам, классам, `id` и вложенности.

### Поиск по тегу

Самый простой вариант локатора — по тегу. Он находит все элементы этого тега сразу:

```python
page.locator("input")   # все поля ввода
page.locator("button")  # все кнопки
```

На практике такие локаторы почти не используются сами по себе — на странице обычно несколько кнопок и полей, а тесту нужен конкретный элемент. Но именно от тега мы отталкиваемся, когда добавляем к нему уточнение.

### Поиск по атрибуту

Атрибутный локатор намного полезнее — он уточняет, какой именно элемент нужен:

```python
page.locator("input[name='email']")
```

Читается как: "найди тег `input`, у которого атрибут `name` равен `email`". Можно вообще не указывать тег:

```python
page.locator("[data-testid='email-input']")
```

Это значит: "найди любой элемент с атрибутом `data-testid='email-input'`". Такая запись — один из самых частых видов локаторов в реальных проектах.

### Несколько условий одновременно

Условия по тегу и атрибутам можно комбинировать в одном локаторе, просто указывая их подряд без пробела:

```python
page.locator("input[type='password']")
page.locator("input[type='text'][name='username']")
```

Второй пример читается так: "найди тег `input`, у которого одновременно `type='text'` **и** `name='username'`". Чем больше условий в одном локаторе, тем точнее он находит именно тот элемент, который нужен, — это особенно полезно, когда на странице несколько похожих полей.

### Классы и id — свой синтаксис

У классов и `id` есть сокращённая запись, отдельная от общего атрибутного синтаксиса `[attr='value']`:

```python
page.locator(".submit-button")   # то же самое, что [class='submit-button']
page.locator("#login-form")      # то же самое, что [id='login-form']
```

Точка (`.`) — это поиск по классу, решётка (`#`) — поиск по `id`. Оба варианта работают, но раз у элемента может быть несколько классов сразу (`class="btn btn-primary"`), точечная запись найдёт элемент, если среди его классов есть указанный, а не только если класс совпадает полностью.

### Поиск вложенных элементов

Иногда нужный элемент находится внутри другого. Например, в React-приложениях (и в нашем учебном приложении тоже) `data-testid` часто ставят на внешний контейнер, а не на сам `input`:

```html
<div data-testid="registration-form-email-input">
    <input type="text">
</div>
```

Чтобы получить именно `<input>`, а не внешний `<div>`, между двумя частями локатора ставится пробел:

```python
page.locator("[data-testid='registration-form-email-input'] input")
```

Пробел означает "внутри" (в терминах прошлого урока — "среди потомков"). Читается так: "найди элемент с этим `data-testid`, а внутри него — тег `input`".

### Какие атрибуты выбирать, а какие — нет

Хорошие кандидаты для локатора:

- **`data-testid`** — лучший вариант. Добавляется специально для автотестов, не влияет на вёрстку, обычно не меняется при рефакторинге.
- **`id`**, если он осмысленный и стабильный (`id="registration-button"`, а не `id="mui-12345"`).
- **`name`** — часто встречается в формах: `input[name="email"]`.

Плохие кандидаты:

- Автогенерированные классы: `class="css-1ruewdp"`.
- Автогенерированные `id`: `id="mui-12345"`, `id=":rd:"` (в нашем учебном приложении поля формы как раз используют такие динамические `id` — поэтому мы их не используем).
- Длинные цепочки вложенности: `div > div > div > button` или `.MuiContainer-root .MuiGrid2-root .MuiButton-root` — любое изменение вёрстки их ломает.

Кроме CSS существуют и **XPath-локаторы** — другой популярный синтаксис (например, поиск по тексту `//button[text()="Registration"]`). В этом курсе мы сознательно остаёмся на CSS-локаторах и `data-testid`: для нашего учебного приложения этого достаточно, а локаторы получаются короче и понятнее. Если продолжишь развиваться в UI-автоматизации, с XPath ты обязательно познакомишься отдельно.

## Пример

Для страницы регистрации нашего учебного приложения локаторы полей строятся с уточнением `input`, потому что `data-testid` стоит на контейнере:

```python
page.locator("[data-testid='registration-form-email-input'] input")
page.locator("[data-testid='registration-form-username-input'] input")
page.locator("[data-testid='registration-form-password-input'] input")
```

А для кнопки регистрации `data-testid` стоит прямо на `<button>`, поэтому уточнение не нужно:

```python
page.locator("[data-testid='registration-page-registration-button']")
```

Именно эти локаторы позже войдут в `RegistrationPage` (`boilerplate/pages/registration_page.py`) — можешь свериться, они совпадают дословно.

## Частые ошибки

- Забыть пробел перед `input`, когда `data-testid` стоит на внешнем контейнере — локатор не найдёт элемент или найдёт не тот.
- Строить локатор по классу, не проверив в DevTools, не сгенерирован ли он автоматически.
- Использовать слишком общий локатор (`page.locator("button")`) там, где на странице несколько кнопок — Playwright либо найдёт "не ту" кнопку, либо, если используется `expect()`, сообщит об ошибке из-за нескольких совпадений.
- Путать точечную запись класса (`.btn`) с атрибутным поиском по классу (`[class='btn']`) — они не всегда равнозначны, если у элемента несколько классов.

## Мини-задания

1. **Разминка.** Дан HTML: `<button class="btn btn-primary" id="submit-btn">Submit</button>`. Напиши три разных CSS-локатора для этой кнопки: по тегу и классу через точку, по `id` через решётку, и через атрибутный синтаксис `[id='...']`. Все три должны находить один и тот же элемент.
2. **Основное.** Открой страницу Dashboard учебного приложения (`.../#/dashboard`) в DevTools и найди заголовок `Dashboard`. Определи, на каком именно теге стоит атрибут `data-testid`, и напиши CSS-локатор для этого заголовка самостоятельно, не подглядывая в следующий урок.
3. **Ближе к практике.** Представь форму логина с таким HTML: `<div class="MuiInput-root css-a1b2c3"><input id="login-username" type="text"></div>` и `<input type="password" class="css-d4e5f6">`. Напиши по одному локатору для каждого из двух полей, обосновав выбор атрибута (почему не через `class`), и объясни, нужен ли пробел в локаторе первого поля.
4. **Со звёздочкой.** На странице, где есть несколько кнопок (например, "Sign in" и "Sign up" рядом), локатор `page.locator("button")` найдёт сразу обе. Опиши своими словами, что произойдёт, если такой локатор передать в `expect(...).to_be_visible()` или в `.click()`, и предложи два разных способа сузить локатор до одной конкретной кнопки (через атрибут и через уточнение текста, если оно тебе уже знакомо).
