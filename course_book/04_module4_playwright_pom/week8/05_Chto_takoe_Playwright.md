# 4.5. Что такое Playwright и зачем он нужен

## Зачем это нужно

Всё, что мы делали на этой неделе — HTML, DOM, DevTools, локаторы — было подготовкой к тому, чтобы понимать, с чем работает инструмент автоматизации. Теперь пора познакомиться с самим инструментом, который будет открывать браузер, находить элементы по нашим локаторам и выполнять действия. В этом курсе это [Playwright](https://playwright.dev/python/).

## Теория

**Playwright** — библиотека для автоматизации браузеров. Из Python-кода она умеет открывать страницы, находить элементы, вводить текст, кликать по кнопкам и проверять результат — то есть выполнять программно те же действия, которые обычно делает руками пользователь.

Например, пользователь открывает страницу регистрации, заполняет Email, Username, Password, нажимает Registration и видит Dashboard. Для Playwright это последовательность команд: открыть страницу → найти поле → ввести текст → найти кнопку → кликнуть → проверить результат. Именно такую последовательность мы соберём в следующих уроках.

### Как это устроено в общих чертах

Почти любой сценарий на Playwright строится по одной схеме:

1. Запустить браузер.
2. Открыть нужную страницу по URL.
3. Найти элементы через локаторы.
4. Выполнить действия (ввод текста, клики).
5. Проверить, что приложение отработало правильно.

Локатор поля Email мы уже знаем с прошлой недели:

```python
page.locator("[data-testid='registration-form-email-input'] input")
```

На прошлой неделе это была просто строка из урока про CSS-локаторы. Теперь она станет частью настоящего кода на Playwright.

### Playwright — не только про Python

Playwright изначально сделан так, чтобы одна и та же библиотека (с похожим API) существовала для нескольких языков — есть версии для JavaScript/TypeScript, Java, .NET и Python. Это не значит, что тесты можно переносить между языками автоматически, но общие принципы (локаторы, автоматические ожидания, работа с браузером) одинаковы везде. В этом курсе мы используем именно Python-версию — она встраивается в тот же `pytest`, с которым ты уже работал в модуле 1.

### Браузер, контекст и страница

Когда мы говорим "запустить браузер", у Playwright за этим стоит небольшая иерархия понятий, с которой полезно познакомиться заранее — дальше она не раз всплывёт:

- **Browser** — сам запущенный браузер (например, Chromium), один процесс.
- **Context** — что-то вроде отдельного профиля браузера внутри этого запущенного процесса: у каждого контекста свои куки, своё хранилище, свои сессии, как будто это разные пользователи за разными компьютерами, хотя физически используется один и тот же браузер.
- **Page** — конкретная вкладка внутри контекста. Именно с объектом `page` мы работаем большую часть времени: вызываем `page.locator(...)`, кликаем, вводим текст.

Когда в модуле 1 ты использовал pytest, а теперь встретишь готовую фикстуру `page` от `pytest-playwright` (в модуле 4 мы её не создаём сами, а просто используем) — по сути, это и есть такая страница внутри уже настроенного браузера и контекста, подготовленная для тебя заранее.

### Какой браузер используем

Playwright умеет управлять разными браузерами, в курсе мы используем **Chromium** — движок, на котором построены Chrome, Edge, Brave и другие. Запуск браузера выглядит так:

```python
browser = p.chromium.launch(headless=False)
```

Пока не нужно разбирать эту строку целиком — в следующем уроке пройдёмся по каждой части. Важно понять главное: эта команда запускает браузер, которым дальше управляет Playwright.

### Что значит `headless=False`

Параметр `headless=False` означает, что браузер откроется в обычном видимом окне — ты своими глазами увидишь, как Playwright заполняет поля и нажимает кнопки. Это удобно на старте: не нужно гадать, что происходит внутри теста.

Когда тесты уже стабильны, их часто запускают в `headless`-режиме — без видимого окна. Это удобно для серверов и CI/CD (об этом — в модуле 6), но пока видимый браузер понятнее. Важно понимать: это один и тот же Playwright с одним и тем же поведением — меняется только то, рисуется ли окно на экране. Локаторы, ожидания и результат теста от этого параметра не зависят, потому что Playwright, как мы уже выяснили в уроке про HTML и DOM, всегда работает с DOM-деревом страницы, а не с картинкой, которую видит человек.

## Пример

Пока у нас нет кода — только идея. В следующем уроке (4.6) мы напишем первый рабочий скрипт, который запускает Chromium, открывает вкладку и закрывает браузер. Это и станет первым практическим применением всего, что мы обсудили.

## Частые ошибки

- Ожидать, что Playwright "видит" страницу так же, как человек — на самом деле он всегда работает через DOM и локаторы, а не через распознавание картинки.
- Путать Playwright с расширением браузера или инструментом для вёрстки — это библиотека для автоматизации, которая используется из Python-кода.
- Забывать, что headless-режим и видимый режим — это один и тот же Playwright, просто разный параметр запуска браузера.
- Путать понятия "браузер", "контекст" и "страница" — например, думать, что `page` и есть весь запущенный браузер, а не одна вкладка внутри него.

2. **Основное.** Своими словами, опираясь на иерархию "браузер → контекст → страница" из теории, объясни, чем объект `page`, с которым мы будем работать в тестах, отличается от "браузера" целиком. Приведи аналогию (например, через вкладки в обычном браузере, которым ты пользуешься каждый день).
3. **Ближе к практике.** Представь, что твои Playwright-тесты сейчас запускаются локально с `headless=False`, чтобы ты видел процесс, а команде нужно перенести их на сервер без монитора для запуска в CI. Опиши, что именно нужно поменять в запуске браузера и почему сами локаторы и тесты при этом менять не придётся.
4. **Со звёздочкой.** Один из новичков решил, что если тест не может найти элемент по локатору, стоит попробовать переключить `headless=False` на `headless=True` (или наоборот) — вдруг поможет. Объясни своими словами, почему это не имеет смысла с точки зрения того, как Playwright ищет элементы, и в какую сторону стоит смотреть на самом деле (подсказка: вспомни, с чем именно работает Playwright — с картинкой или с DOM).
