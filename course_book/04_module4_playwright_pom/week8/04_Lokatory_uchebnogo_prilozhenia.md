# 4.4. Локаторы учебного приложения

## Зачем это нужно

Прежде чем на неделе 9 писать первый код на Playwright, полезно заранее знать все локаторы, которые понадобятся для сценария регистрации. Это стандартная практика: перед автоматизацией сценария сначала вручную (глазами и через DevTools) проходишь его шаги и выписываешь локаторы, а уже потом садишься писать код.

## Теория

### Сценарий, который мы будем автоматизировать

Наш первый сценарий — регистрация нового пользователя:

1. Открыть страницу регистрации.
2. Заполнить Email.
3. Заполнить Username.
4. Заполнить Password.
5. Нажать кнопку Registration.
6. Дождаться перехода на Dashboard.
7. Убедиться, что регистрация прошла успешно.

Для этого нам нужно уметь находить: поле Email, поле Username, поле Password, кнопку Registration, а после перехода — заголовок страницы Dashboard.

### Поля формы регистрации

У всех трёх полей одна и та же особенность: `data-testid` стоит не на самом `<input>`, а на его внешнем контейнере:

```html
<div data-testid="registration-form-email-input">
    ...
</div>
```

Поэтому локатор всегда состоит из двух частей — контейнер и вложенный `input`:

```python
page.locator("[data-testid='registration-form-email-input'] input")
page.locator("[data-testid='registration-form-username-input'] input")
page.locator("[data-testid='registration-form-password-input'] input")
```

### Кнопка Registration

Здесь `data-testid` расположен прямо на `<button>`, поэтому дополнительный `input` не нужен:

```python
page.locator("[data-testid='registration-page-registration-button']")
```

### Заголовок Dashboard

После успешной регистрации приложение перенаправляет на `.../#/dashboard`. Убедиться, что это действительно произошло, можно двумя способами: проверить URL и проверить заголовок страницы. Заголовок в HTML выглядит так:

```html
<h6 data-testid="dashboard-toolbar-title-text">
    Dashboard
</h6>
```

Локатор:

```python
page.locator("[data-testid='dashboard-toolbar-title-text']")
```

### Почему именно `data-testid`

У элементов есть множество атрибутов — `class`, `id`, `type`, `role`, `aria-*`. Технически можно построить локатор почти по любому из них. Но в нашем приложении разработчики специально подготовили `data-testid` для каждого важного элемента — это самый стабильный вариант, и именно на него мы будем опираться на протяжении всего курса. Такой подход широко распространён и в реальных проектах.

### Как убедиться, что локатор действительно уникален

Локатор по `data-testid` полезен настолько, насколько уникально это значение на странице. Если по ошибке (или из-за бага фронтенда) два разных элемента получат один и тот же `data-testid`, локатор будет находить сразу оба — и вести себя непредсказуемо. Прежде чем закладывать локатор в тест, стоит вручную убедиться, что он находит ровно один элемент: например, через поиск во вкладке Elements (см. прошлый урок) или просто внимательно просмотрев дерево DOM вокруг нужного элемента. Для локаторов из таблицы ниже мы уже это проверили — но привычку проверять самому стоит выработать сразу, а не поверить на слово таблице.

## Пример

Сводная таблица локаторов, с которыми мы будем работать в следующих уроках:

| Элемент | Локатор |
|---|---|
| Email | `[data-testid='registration-form-email-input'] input` |
| Username | `[data-testid='registration-form-username-input'] input` |
| Password | `[data-testid='registration-form-password-input'] input` |
| Кнопка Registration | `[data-testid='registration-page-registration-button']` |
| Заголовок Dashboard | `[data-testid='dashboard-toolbar-title-text']` |

Держи эту таблицу под рукой — именно эти локаторы уже используются в готовых `RegistrationPage` и `DashboardPage` в `boilerplate/pages/`, и на неделе 10 мы разберём их построчно.

## Частые ошибки

- Пропустить `input` в локаторе поля формы, потому что визуально контейнер и поле выглядят как один элемент.
- Спутать локатор заголовка Dashboard с локатором самой кнопки Registration — легко перепутать, если не смотреть в DevTools, а копировать по памяти.
- Проверять только URL после регистрации и не проверять, что страница реально отрисовалась (заголовок виден) — если приложение "зависло" на пустом экране или всё ещё показывает индикатор загрузки, проверка URL всё равно пройдёт.

## Мини-задания

1. **Разминка.** Открой страницу регистрации учебного приложения и через DevTools найди поле Email. Сверься с таблицей из "Примера" — убедись, что `data-testid` контейнера действительно `registration-form-email-input`, а внутри лежит `<input>`.
2. **Основное.** Открой учебное приложение и вручную (мышкой) пройди весь сценарий: заполни форму регистрации любыми данными и нажми Registration. После перехода на Dashboard через DevTools убедись, что локатор `[data-testid='dashboard-toolbar-title-text']` из таблицы выше действительно указывает на видимый заголовок "Dashboard".
3. **Ближе к практике.** На открытой странице Dashboard воспользуйся поиском внутри вкладки Elements (из прошлого урока) и проверь, сколько элементов на странице находится по локатору `[data-testid='dashboard-toolbar-title-text']`. Убедись, что ровно один — если поиск покажет больше, это будет сигналом, что локатор не такой надёжный, как кажется.
4. **Со звёздочкой.** Представь ситуацию: сразу после клика по кнопке Registration URL в адресной строке уже поменялся на `.../#/dashboard`, но сама страница ещё долю секунды показывает пустой экран или индикатор загрузки, прежде чем отрисуется заголовок "Dashboard". Объясни своими словами, почему проверки "URL сменился" недостаточно для вывода "регистрация прошла успешно", и какую вторую проверку (из таблицы выше) стоит добавить, чтобы быть уверенным, что страница реально загрузилась.
