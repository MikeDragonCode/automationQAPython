# 1.7. Фикстуры: зачем нужны и как объявляются

## Зачем это нужно

Начиная с модуля 3 в `boilerplate/conftest.py` появятся фикстуры вроде `users_client` (готовый API-клиент) и `registration_page` (готовый Page Object). Вы будете получать их в тестах просто как параметр функции, даже не задумываясь, откуда они берутся. Чтобы это не выглядело магией, нужно один раз разобраться в механизме на простом примере — без API и без браузера.

## Теория

**Фикстура** — это функция, которая готовит данные или окружение для теста. pytest вызывает её сам и передаёт результат в тест — достаточно указать имя фикстуры как параметр тестовой функции.

Фикстура объявляется декоратором `@pytest.fixture`:

```python
import pytest


@pytest.fixture
def numbers():
    return list(range(1, 11))
```

А используется так — просто как аргумент теста, без единого импорта:

```python
def test_numbers_length(numbers):
    assert len(numbers) == 10
```

Когда pytest видит параметр `numbers` в сигнатуре теста, он ищет фикстуру с таким именем, вызывает её и подставляет результат в переменную `numbers` внутри теста. Вы никогда не вызываете фикстуру напрямую — `numbers()` — этим занимается pytest.

### Что можно вернуть из фикстуры

Фикстура — обычная функция, поэтому вернуть из неё можно что угодно: число, строку, список, словарь, экземпляр класса. Тесту не важен тип значения — важно, что оно уже готово к использованию, без подготовки внутри самого теста:

```python
@pytest.fixture
def sample_user():
    return {"username": "mike_qa", "role": "tester"}


def test_sample_user_role(sample_user):
    assert sample_user["role"] == "tester"
```

### Чем фикстура отличается от параметризации

Параметризация (прошлый урок) — это несколько *разных* прогонов одного теста с разными входными данными. Фикстура — это подготовка *одних и тех же* (или предсказуемо подготовленных) данных или объекта, которые нужны тесту для работы, но не являются предметом самой проверки. Один и тот же тест обычно не «параметризуется через фикстуру» — для вариативности данных внутри одного теста используется `parametrize`, а фикстура отвечает за подготовку окружения.

### yield-фикстуры: подготовка и очистка

Если фикстуре нужно не только подготовить, но и «убрать за собой» после теста (закрыть файл, удалить временные данные, разорвать соединение), вместо `return` используется `yield`:

```python
@pytest.fixture
def tracked_numbers():
    print("\n[setup] готовим данные")
    data = list(range(1, 6))
    yield data
    print("[teardown] очистка после теста")
```

Код до `yield` выполняется перед тестом, само значение после `yield` передаётся в тест, а код после `yield` выполняется после того, как тест завершится — независимо от того, прошёл он или упал.

### autouse: фикстуры, которые запускаются без явного запроса

Иногда подготовку нужно выполнить для всех тестов подряд, даже если ни один из них явно её не запрашивает — например, напечатать разделитель в логе перед каждым тестом. Для этого у `@pytest.fixture` есть параметр `autouse=True`:

```python
@pytest.fixture(autouse=True)
def log_test_name(request):
    print(f"\n--- running {request.node.name} ---")
```

Такая фикстура выполняется для каждого теста в той области, где она объявлена (файл, класс или весь проект — в зависимости от того, где лежит её объявление), даже если ни один тест не упомянул её имя в параметрах. Здесь же встречается `request` — специальная встроенная фикстура pytest, через которую можно узнать, например, имя текущего теста (`request.node.name`). `autouse` стоит использовать редко и осознанно: если таких фикстур в проекте становится много, понять из одной сигнатуры теста, что на самом деле происходит перед его запуском, уже не получится.

## Пример

Фикстура и тесты для функции `chunk_list` из `boilerplate/utils/string_utils.py`:

```python
import pytest

from utils.string_utils import chunk_list


@pytest.fixture
def numbers():
    return list(range(1, 11))


def test_chunk_list_by_three(numbers):
    result = chunk_list(numbers, 3)
    assert result[0] == [1, 2, 3]


def test_chunk_list_last_chunk_size(numbers):
    result = chunk_list(numbers, 3)
    assert result[-1] == [10]
```

Обе тестовые функции получают свежий список `[1, 2, ..., 10]`, ни разу не создавая его внутри тела теста напрямую. Если запустить эти тесты с флагами `-s -v` вместе с yield-версией фикстуры (`tracked_numbers`), в выводе будет видно, что `[setup]` печатается перед каждым тестом, а `[teardown]` — сразу после:

```
[setup] готовим данные
tests/test_fixtures_demo.py::test_one PASSED
[teardown] очистка после теста
[setup] готовим данные
tests/test_fixtures_demo.py::test_two PASSED
[teardown] очистка после теста
```

Это происходит потому, что фикстура без явно указанного `scope` пересоздаётся для *каждого* теста — подробнее об этом в следующем уроке.

## Частые ошибки

* Объявить `@pytest.fixture`, но не указать её имя в параметрах теста — тогда pytest просто не вызовет эту фикстуру для этого теста, и данные окажутся недоступны.
* Вызывать фикстуру как обычную функцию: `data = numbers()` — так фикстуры не используются, это ломает саму идею (pytest должен вызывать её сам, с учётом scope и кеширования).
* Писать код после `yield`, забыв, что до этого места фикстура «висит» в подготовленном состоянии на протяжении всего теста — если в setup-части (до `yield`) возникает исключение, тест не выполнится вовсе, а teardown-часть (после `yield`) не будет вызвана.
* Использовать `return` и `yield` одновременно в одной фикстуре — до первого `return`/`yield` доходит выполнение, а код ниже становится недостижимым и не выполняется никогда.

## Мини-задания

1. **Разминка.** Напишите фикстуру `browser_names`, возвращающую список `["chrome", "firefox", "safari"]`, и один тест, который проверяет, что в списке ровно 3 элемента.
2. **Основное.** Напишите фикстуру `sample_words`, возвращающую список из 5 слов (часть — палиндромы, часть — нет), и два теста, которые её используют: один проверяет длину списка, второй — что `is_palindrome(...)` для конкретного слова из списка возвращает ожидаемое значение.
3. **Ближе к практике.** Напишите фикстуру `sample_response`, возвращающую словарь, имитирующий кусок ответа API (например, `{"status": 200, "body": {"id": 1, "name": "Mike"}}`), и тест, который проверяет и `status`, и вложенное значение `body["name"]`. Затем перепишите ту же фикстуру через `yield`, добавив `print` до и после `yield` — запустите тесты с флагами `-s -v` и убедитесь, что в выводе видна и подготовка, и очистка.
4. **Со звёздочкой.** Напишите фикстуру, в которой сначала стоит `return some_value`, а следующей строкой — недостижимый `yield other_value`. Заранее письменно предположите, какое значение получит тест: то, что после `return`, или то, что после `yield`. Затем напишите тест, который использует эту фикстуру и печатает полученное значение, запустите его и сравните результат со своим предположением.
