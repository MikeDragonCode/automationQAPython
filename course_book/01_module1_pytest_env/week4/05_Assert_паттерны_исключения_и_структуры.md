# 1.11. Assert-паттерны: исключения и сложные структуры

## Зачем это нужно

Реальные функции не только возвращают значения — они ещё и падают на некорректном вводе. `chunk_list` из `boilerplate/utils/string_utils.py` уже поднимает `ValueError`, если передать неположительный размер чанка, и такое поведение тоже нужно проверять тестами. А результаты функций часто оказываются не числом или строкой, а списком или словарём — для них тоже есть свои, стандартные приёмы сравнения. Это ровно те паттерны, которые проверяются в домашнем задании модуля.

## Теория

### Проверка исключений: pytest.raises

Чтобы проверить, что код действительно поднимает нужное исключение, используется контекстный менеджер `pytest.raises`:

```python
import pytest

with pytest.raises(ValueError):
    chunk_list([1, 2, 3], 0)
```

Тест **пройдёт**, только если внутри блока `with` действительно будет поднято исключение указанного типа (или его подкласс). Если исключения не произойдёт вовсе — тест упадёт с ошибкой о том, что `ValueError` не было поднято. Если будет поднято исключение другого типа — оно просто «пролетит» дальше и тест тоже упадёт, но уже с этим другим исключением.

Можно дополнительно проверить текст сообщения об ошибке через параметр `match` (это регулярное выражение, сверяемое со строковым представлением исключения):

```python
with pytest.raises(ValueError, match="positive integer"):
    chunk_list([1, 2, 3], -1)
```

Если нужен доступ к самому объекту исключения — например, чтобы проверить дополнительные атрибуты, — используется `as`:

```python
with pytest.raises(ValueError) as excinfo:
    chunk_list([1, 2, 3], 0)

assert "positive integer" in str(excinfo.value)
```

У `excinfo` есть и другие полезные атрибуты — например, `excinfo.type` хранит сам класс поднятого исключения, если нужно свериться с ним напрямую: `assert excinfo.type is ValueError`.

### pytest.raises внутри параметризованного теста

Из предыдущих уроков вы уже знаете `@pytest.mark.parametrize` — его можно сочетать с `pytest.raises`, чтобы одним тестом проверить сразу несколько некорректных входов вместо копирования одного и того же теста под каждое значение:

```python
@pytest.mark.parametrize("bad_size", [0, -1, -5])
def test_chunk_list_rejects_various_bad_sizes(bad_size):
    with pytest.raises(ValueError):
        chunk_list([1, 2, 3], bad_size)
```

pytest прогонит этот тест трижды — по одному разу на каждое значение `bad_size` — и в каждом прогоне ожидает `ValueError`.

### Сравнение списков и словарей

Оператор `==` в Python рекурсивно сравнивает списки, словари, кортежи и множества по содержимому — никаких специальных методов не нужно:

```python
result = chunk_list([1, 2, 3, 4, 5], 2)
assert result == [[1, 2], [3, 4], [5]]
```

Это работает и для вложенных структур (список словарей, словарь списков) — Python сравнит их поэлементно на любую глубину. При падении такого `assert` pytest покажет структурный диф — какие элементы или ключи отличаются, а не просто «False».

### Когда порядок не важен

Если функция не гарантирует порядок элементов, а важен только состав, сравнивайте через `sorted(...)` (для списков) или приведение к `set(...)` (если элементы уникальны и хешируемы):

```python
result = chunk_list(["b", "a", "c"], 3)
assert sorted(result[0]) == ["a", "b", "c"]
```

### Когда нужно проверить только часть структуры

Сравнивать структуру целиком через `==` неудобно, если в ней есть поля, которые вы не хотите (или не можете) жёстко зафиксировать — например, `id` или `created_at` в ответе API, которые каждый раз разные. В этом случае проверяют только нужные ключи по отдельности:

```python
response_body = {"id": 17, "email": "user@example.com", "created_at": "2026-01-01T00:00:00"}

assert response_body["email"] == "user@example.com"
assert "id" in response_body
```

То же самое можно записать компактнее, сравнив только нужное подмножество пар ключ-значение — `dict.items()` поддерживает операции сравнения множеств, и `<=` здесь означает «все пары слева есть и в словаре справа»:

```python
expected_subset = {"email": "user@example.com"}
assert expected_subset.items() <= response_body.items()
```

### Дроби: pytest.approx

Прямое сравнение вычисленных чисел с плавающей точкой через `==` ненадёжно из-за особенностей их внутреннего представления (`0.1 + 0.2 == 0.3` в Python — `False`). Для таких случаев в pytest есть `pytest.approx`:

```python
assert 0.1 + 0.2 == pytest.approx(0.3)
```

Он же прекрасно работает и внутри списков/словарей значений, если такие структуры содержат дробные числа:

```python
result = {"average": 0.1 + 0.2, "count": 3}
assert result == {"average": pytest.approx(0.3), "count": 3}
```

## Пример

```python
import pytest

from utils.string_utils import chunk_list


def test_chunk_list_rejects_non_positive_size():
    with pytest.raises(ValueError):
        chunk_list([1, 2, 3], 0)


def test_chunk_list_rejects_negative_size_with_message():
    with pytest.raises(ValueError, match="positive integer"):
        chunk_list([1, 2, 3], -1)


def test_chunk_list_result_structure():
    result = chunk_list([1, 2, 3, 4, 5], 2)
    assert result == [[1, 2], [3, 4], [5]]


def test_user_data_shape():
    data = {
        "email": "user@example.com",
        "username": "testuser",
        "password": "password123",
    }
    assert data == {
        "email": "user@example.com",
        "username": "testuser",
        "password": "password123",
    }
    assert set(data.keys()) == {"email", "username", "password"}
```

Первые два теста — это ровно та же идея, что уже реализована в `boilerplate/tests/unit/test_string_utils.py` в тесте `test_chunk_list_rejects_non_positive_size`, только с добавлением проверки текста сообщения через `match`. Третий и четвёртый — типовые примеры сравнения структур: список списков (важен порядок) и словарь (сравнение по значению целиком плюс отдельная проверка набора ключей).

## Частые ошибки

* Вызывать проверяемый код **до** блока `with pytest.raises(...)`, а не внутри него — тогда исключение произойдёт до того, как pytest начнёт его «ловить», и тест упадёт с необработанным исключением вместо чёткого сообщения о провале ожидания.
* Не понимать, что если код внутри `pytest.raises(...)` **не** поднимает исключение — тест **падает**. Это ожидаемое поведение: `pytest.raises` описывает обязательное условие, а не «опциональную подстраховку».
* Использовать слишком широкий тип исключения, например `pytest.raises(Exception)`, вместо конкретного `ValueError` — тест в этом случае пройдёт даже при неправильном типе исключения, маскируя реальные баги в коде.
* Сравнивать вычисленные дробные значения через `==` вместо `pytest.approx` и получать редкие, «случайные» падения теста из-за погрешности округления.

## Мини-задания

1. **Разминка.** Напишите тест на `pytest.raises` для `chunk_list` с новым некорректным значением размера — `-3`, которое ещё не встречалось в уроке.
2. **Основное.** Напишите ещё один тест на `pytest.raises` для `chunk_list` с другим некорректным значением размера (например, `-5`), и отдельный тест, сравнивающий собранный вручную словарь (свою придуманную структуру данных, например «результат теста»: `{"name": ..., "passed": ..., "duration": ...}`) с ожидаемым словарём через `==`.
3. **Ближе к практике.** Напишите параметризованный тест, который через `@pytest.mark.parametrize` проверяет `chunk_list` на трёх некорректных значениях размера сразу (`0`, `-1`, `-10`), оборачивая вызов в `pytest.raises(ValueError)`. Отдельно напишите тест на «фейковый» ответ API вида `{"id": 42, "email": "user@example.com", "created_at": "2026-01-01T00:00:00"}`, который проверяет только `email` и наличие ключа `id`, игнорируя `created_at` — так, как будто это поле каждый раз новое и его нельзя жёстко зафиксировать.
4. **Со звёздочкой.** Вызовите `chunk_list(None, 2)` внутри `with pytest.raises(Exception):` — тест пройдёт, потому что `None` при попытке вычислить его длину вызывает исключение, а `Exception` — достаточно широкий тип, чтобы поймать почти любое из них. Затем замените `Exception` на `ValueError` и снова запустите тест. Определите, какой именно тип исключения реально поднимается в этом случае, и письменно объясните, почему первая версия теста была потенциально опасной, хотя формально проходила.
