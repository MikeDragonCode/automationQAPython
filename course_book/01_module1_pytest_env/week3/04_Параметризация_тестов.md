# 1.4. Параметризация тестов (@pytest.mark.parametrize)

## Зачем это нужно

Одна и та же функция обычно проверяется не на одном входном значении, а на нескольких: типичный случай, граничный случай, некорректный ввод. Копировать тестовую функцию под каждый набор данных — плохая идея: код дублируется, а при изменении логики проверки придётся править её в десяти местах. `@pytest.mark.parametrize` решает эту задачу — один тест, много входных данных.

## Теория

Декоратор `@pytest.mark.parametrize` принимает два аргумента:

1. строку с именами аргументов через запятую;
2. список наборов значений — по одному набору на тестовый «прогон».

```python
@pytest.mark.parametrize(
    "text, expected",
    [
        ("racecar", True),
        ("hello", False),
    ],
)
def test_is_palindrome(text, expected):
    assert is_palindrome(text) is expected
```

pytest превращает это в **два независимых теста** — по одному на каждую строку из списка. Каждый из них получает свои значения `text` и `expected` и падает или проходит отдельно от других: если один набор данных сломает функцию, остальные всё равно будут выполнены и покажут свой результат.

### Как выглядят id параметризованных тестов

В выводе pytest каждый вариант получает собственный, автоматически сгенерированный идентификатор на основе переданных значений:

```
test_is_palindrome[racecar-True]
test_is_palindrome[hello-False]
```

Эти id можно использовать и для точечного запуска: `python -m pytest tests/unit/test_string_utils.py -k racecar`.

Если автоматические id получаются длинными или нечитаемыми (например, для сложных объектов), их можно задать вручную через параметр `ids`:

```python
@pytest.mark.parametrize(
    "text, expected",
    [("racecar", True), ("hello", False)],
    ids=["palindrome", "not-a-palindrome"],
)
```

### Чем parametrize лучше обычного цикла

Логично предположить, что вместо декоратора можно просто пройтись циклом по данным внутри одного теста:

```python
def test_is_palindrome_loop():
    cases = [("racecar", True), ("hello", False)]
    for text, expected in cases:
        assert is_palindrome(text) is expected
```

Разница принципиальная: это по-прежнему **один** тест. Если упадёт проверка на первой паре, цикл прервётся прямо там, и вы не узнаете, что произошло с остальными парами — та же проблема, что и с обычным Python-скриптом из первого урока модуля. `@pytest.mark.parametrize`, в отличие от цикла, создаёт несколько **независимых** тестов: у каждого свой результат, каждый можно запустить отдельно по node id или через `-k`, и падение одного никак не влияет на выполнение и отчёт по остальным.

### Несколько параметризаций на одном тесте

Если применить `@pytest.mark.parametrize` дважды к одной функции, pytest выполнит тест для **всех комбинаций** значений из обоих декораторов (декартово произведение). Это мощный, но редко нужный на практике приём — используйте его аккуратно, чтобы не получить сотни тестов там, где хватило бы одного списка кортежей.

## Пример

Это ровно то, что уже сделано в `boilerplate/tests/unit/test_string_utils.py`:

```python
import pytest

from utils.string_utils import chunk_list, count_vowels, is_palindrome, slugify


@pytest.mark.unit
@pytest.mark.parametrize(
    "text, expected",
    [
        ("racecar", True),
        ("A man a plan a canal Panama", True),
        ("hello", False),
        ("", True),
    ],
)
def test_is_palindrome(text, expected):
    assert is_palindrome(text) is expected
```

Один тест `test_is_palindrome` при запуске `python -m pytest -v` превращается в четыре строки вывода:

```
test_is_palindrome[racecar-True] PASSED
test_is_palindrome[A man a plan a canal Panama-True] PASSED
test_is_palindrome[hello-False] PASSED
test_is_palindrome[-True] PASSED
```

Обратите внимание: имена аргументов в строке `"text, expected"` — это одновременно и параметры функции `def test_is_palindrome(text, expected):`, и заголовки колонок для списка кортежей ниже. Порядок значений внутри каждого кортежа должен совпадать с порядком имён в строке.

## Частые ошибки

* Количество значений в кортеже не совпадает с количеством имён аргументов (например, названы `"text, expected"`, а в кортеже три значения) — pytest упадёт с ошибкой уже на этапе сбора тестов (`collection error`), а не во время выполнения.
* Для одного аргумента оборачивать значения в лишние кортежи из одного элемента: если аргумент один, список выглядит как `["racecar", "hello"]`, а не `[("racecar",), ("hello",)]`.
* Не давать `ids` там, где автоматические идентификаторы получаются нечитаемыми (например, для списков или словарей) — в выводе pytest тогда появляются что-то вроде `test_x[data0]`, `test_x[data1]`, по которым невозможно понять, какой именно случай упал.
* Игнорировать параметризацию и продолжать писать пять почти одинаковых тестовых функций подряд «по старой памяти» — если тело теста и логика проверки одинаковы, а отличаются только данные, это сигнал использовать `parametrize`.

## Мини-задания

1. **Разминка.** Параметризуйте тест для `is_palindrome` из примера в теории двумя наборами данных (например, `"madam"` и `"python"`) и запустите `python -m pytest -v` — убедитесь, что в выводе появились два отдельных теста со своими id.
2. **Основное.** Возьмите функцию `count_vowels` из `boilerplate/utils/string_utils.py` и напишите для неё параметризованный тест минимум с 4 наборами данных: смешанный русский/английский текст, текст в верхнем регистре, текст без гласных (например, `"rhythm gym"`), пустая строка.
3. **Ближе к практике.** Напишите параметризованный тест для `slugify` минимум с тремя реалистичными «грязными» строками, похожими на то, что реально вводят пользователи (например, `"  Best Product!!  "`, `"UPPER CASE TEXT"`, `"уже-с-дефисами"`), и задайте каждому набору свой читаемый `id` через параметр `ids`, вместо того чтобы полагаться на автоматически сгенерированные.
4. **Со звёздочкой.** Возьмите тест `test_is_palindrome_loop` из примера в теории (цикл вместо parametrize), намеренно добавьте в список `cases` пару с неверным ожидаемым значением (например, `("racecar", False)`) и запустите тест — убедитесь, что вы вообще не видите, дошёл ли цикл до остальных пар после падения. Перепишите этот же тест через `@pytest.mark.parametrize` с той же неверной парой и убедитесь, что теперь в выводе видно результат по каждой паре отдельно, включая те, что идут после сломанной.
