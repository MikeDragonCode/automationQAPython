# 1.2. Как pytest находит тесты

## Зачем это нужно

Самая частая проблема новичков с pytest — «я написал тест, а он не запускается». В 9 случаях из 10 причина в том, что файл или функция названы не по правилам, которые pytest использует для поиска тестов. Разобравшись один раз в правилах discovery, вы перестанете терять на этом время.

## Теория

Когда вы выполняете `pytest` без аргументов, инструмент не запускает все `.py`-файлы подряд — он ищет файлы и функции по конкретным правилам именования.

### Правило для файлов

По умолчанию pytest ищет файлы, которые называются `test_*.py` (или `*_test.py`). Все остальные `.py`-файлы игнорируются как тестовые — в них может быть любой код, но pytest не станет заглядывать внутрь в поисках тестов.

```
test_string_utils.py     # найдёт
string_utils_test.py     # тоже найдёт
string_utils.py          # проигнорирует — это код под тестом, не тест
helpers.py                # проигнорирует
```

В этом курсе договорились всегда использовать префикс `test_` — так же делает и `boilerplate` (`tests/unit/test_string_utils.py`).

### Правило для функций

Внутри найденного файла pytest ищет функции, имя которых тоже начинается с `test_`.

```python
def test_is_palindrome_true_for_racecar():   # найдёт и выполнит
    ...

def is_palindrome_true_for_racecar():        # проигнорирует
    ...
```

Функция без префикса `test_` для pytest — обычный Python-код, не тест. Ошибок и предупреждений при этом не будет: pytest просто молча её не соберёт.

### testpaths и rootdir

В файле `boilerplate/pytest.ini` есть строка:

```ini
testpaths = tests
```

Она говорит pytest: «ищи тесты только внутри папки `tests/`, не сканируй весь проект». Это ускоряет поиск и защищает от случайного попадания в сборку постороннего кода. `pytest.ini` также определяет **rootdir** — корень проекта, от которого считаются все относительные пути (`testpaths` в том числе).

### Node id — как указать конкретный тест

Если нужно запустить не всё подряд, а один файл, класс или даже одну функцию, используется node id — путь к файлу плюс `::` и имя теста:

```bash
python -m pytest tests/unit/test_string_utils.py
python -m pytest tests/unit/test_string_utils.py::test_chunk_list_splits_evenly
```

Ещё один полезный инструмент отбора — флаг `-k`, который фильтрует тесты по подстроке в имени:

```bash
python -m pytest -k slugify
```

Эта команда запустит все тесты, в имени (и в id параметризованных вариантов) которых встречается `slugify` — например, `test_slugify[Hello World-hello-world]`.

## Пример

Структура `boilerplate` показывает типичный подход:

```
boilerplate/
├── pytest.ini            # testpaths = tests
└── tests/
    ├── unit/
    │   └── test_string_utils.py
    ├── api/
    │   └── test_users.py
    └── ui/
        └── test_registration.py
```

Все тестовые файлы лежат в `tests/`, названы с префиксом `test_`, все тестовые функции внутри них тоже названы с префиксом `test_`. Благодаря `testpaths = tests` команда `python -m pytest`, запущенная из корня `boilerplate`, найдёт их все, а вот файл `utils/string_utils.py` даже не будет рассмотрен как потенциальный источник тестов — в нём просто нет функций с префиксом `test_`, да и лежит он вне `tests/`.

## Частые ошибки

* Файл лежит не в директории из `testpaths` (например, тест по ошибке создан в корне проекта, а не в `tests/`) — pytest его не найдёт при обычном запуске `python -m pytest`, хотя явный путь `python -m pytest my_test.py` сработает.
* Тестовая функция названа без префикса `test_` (например, `check_palindrome()`) — pytest молча пропустит её, никакой ошибки не будет, и это легко не заметить.
* Тестовый класс с собственным `__init__` — pytest не может создавать экземпляры таких классов и пропускает их со специальным предупреждением. В этом курсе тесты в основном пишутся как функции, а не как классы, именно чтобы не сталкиваться с этим ограничением.
* Ожидание, что `-k слово` работает как точное совпадение имени — на самом деле это подстрока, и `-k user` заодно найдёт `test_user_data`, `test_users_client` и всё, что содержит эту подстроку.

## Мини-задание

В своём учебном проекте (не в `boilerplate`) создайте файл `tests/test_discovery_demo.py` с двумя функциями:

```python
def test_this_will_run():
    assert 1 + 1 == 2

def this_will_not_run():
    assert 1 + 1 == 3
```

Запустите `python -m pytest -v` и убедитесь, что pytest собрал (`collected`) только один тест, а не два. Затем запустите этот же тест по node id: `python -m pytest tests/test_discovery_demo.py::test_this_will_run`.
