# 1.5. Маркеры тестов: @pytest.mark и запуск через -m

## Зачем это нужно

Когда в проекте появляются разные виды тестов — unit, API, UI — почти всегда нужно уметь запускать не всё сразу, а только нужную группу: например, только быстрые unit-тесты во время разработки и полный набор перед мержем. Именно для такого разделения существуют маркеры — и `boilerplate/pytest.ini` уже содержит готовый набор (`ui`, `api`, `unit`, `smoke`, `regress`), которым вы будете пользоваться весь курс.

## Теория

Маркер — это метка, которую можно повесить на тест с помощью декоратора `@pytest.mark.<имя>`:

```python
import pytest


@pytest.mark.unit
def test_something():
    ...
```

Важно понимать: **маркер сам по себе никак не влияет на выполнение теста**. Он не меняет логику, не добавляет проверок — это чистая метаинформация, которую можно использовать при отборе тестов для запуска.

На один тест можно повесить сразу несколько маркеров:

```python
@pytest.mark.unit
@pytest.mark.smoke
def test_something():
    ...
```

### Запуск по маркеру

Флаг `-m` фильтрует тесты по выражению с маркерами:

```bash
python -m pytest -m unit
```

Выполнит только тесты, помеченные `@pytest.mark.unit`.

Выражение после `-m` поддерживает булеву логику — `and`, `or`, `not`:

```bash
python -m pytest -m "unit and not smoke"
python -m pytest -m "api or ui"
```

Если выражение содержит пробелы, в shell его нужно обязательно взять в кавычки — иначе `and`/`or`/`not` будут восприняты как отдельные аргументы командной строки, а не части одного выражения.

### Что если тестов с таким маркером нет

Если под маркер не подошёл ни один тест, pytest не считает это ошибкой — он просто сообщит `no tests ran` и завершится с отдельным кодом возврата (это стоит иметь в виду, если вы настраиваете CI-скрипты, которые проверяют код завершения команды).

## Пример

В `boilerplate/pytest.ini` уже зарегистрированы маркеры:

```ini
[pytest]
markers =
    ui: UI-тесты (Playwright)
    api: API-тесты (requests)
    unit: тесты чистых функций/утилит, без сети и без браузера
    smoke: быстрый набор критичных проверок
    regress: полный регрессионный набор
```

А в `boilerplate/tests/unit/test_string_utils.py` каждый тест помечен маркером `unit`:

```python
@pytest.mark.unit
@pytest.mark.parametrize(...)
def test_is_palindrome(text, expected):
    ...
```

Запустите:

```bash
python -m pytest -m unit -v
```

и увидите только тесты из `test_string_utils.py` (в этом модуле других тестов, кроме unit, вы ещё не пишете). А команда:

```bash
python -m pytest -m "api or ui"
```

в самом `boilerplate` найдёт тесты из `tests/api/` и `tests/ui/` — они относятся к более поздним модулям курса, но уже сейчас можно увидеть, как один и тот же набор тестов делится на группы одной и той же командой `-m`.

## Частые ошибки

* Опечатка в имени маркера (`@pytest.mark.unti` вместо `unit`) — тест окажется помечен другим, несуществующим маркером и просто не попадёт в нужную выборку; без дополнительной настройки (см. следующий урок про `--strict-markers`) pytest в лучшем случае покажет предупреждение, которое легко пропустить.
* Думать, что `-m` как-то ускоряет или распараллеливает выполнение — это не так, `-m` только выбирает подмножество уже найденных тестов, ничего не меняя в том, как каждый из них выполняется.
* Забывать кавычки вокруг составного выражения с `and`/`or`/`not` в shell.
* Помечать маркером тесты «на всякий случай», без чёткого критерия — если непонятно, что означает маркер и когда его использовать, он быстро теряет смысл как инструмент фильтрации.

## Мини-задание

В `boilerplate` выполните `python -m pytest -m unit -v` и убедитесь, что в выводе только тесты из `test_string_utils.py`. Затем выполните `python -m pytest -m "api or ui"` и объясните в одно предложение, что означает получившийся результат (сколько тестов запустилось и почему).
