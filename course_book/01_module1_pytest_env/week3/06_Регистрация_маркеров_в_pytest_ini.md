# 1.6. Регистрация маркеров и --strict-markers

## Зачем это нужно

Маркер с опечаткой — одна из самых незаметных проблем в тестовых проектах: тест продолжает «зелёным» проходить локально, просто перестаёт попадать в нужную выборку по `-m`, и это может остаться незамеченным неделями, пока кто-то не спросит: «а почему в CI не запустился ни один smoke-тест?». `--strict-markers`, уже включённый в `boilerplate/pytest.ini`, превращает такую опечатку из тихой проблемы в громкую ошибку прямо на старте.

## Теория

Если использовать маркер, не сообщив о нём pytest заранее, появится предупреждение:

```
PytestUnknownMarkWarning: Unknown pytest.mark.something - is this a typo?
```

Тест при этом всё равно выполнится — это только предупреждение, а не ошибка. Проблема в том, что предупреждения легко теряются в общем выводе, особенно в CI, где логов много.

### Регистрация маркеров

Чтобы pytest знал о маркере, его нужно зарегистрировать в конфиге — в этом курсе это `pytest.ini`:

```ini
[pytest]
markers =
    ui: UI-тесты (Playwright)
    api: API-тесты (requests)
    unit: тесты чистых функций/утилит, без сети и без браузера
    smoke: быстрый набор критичных проверок
    regress: полный регрессионный набор
```

Формат простой: имя маркера, двоеточие, короткое описание. Описание — не формальность: оно показывается в `pytest --markers` и помогает всей команде понимать, что означает каждый маркер, не заглядывая в код.

### --strict-markers

Сама по себе регистрация в `markers =` убирает предупреждение, но не запрещает использовать незарегистрированные маркеры — предупреждение просто не появится для того, что не зарегистрировано, зато не появится и ошибки для нового, случайно написанного с опечаткой маркера. Флаг `--strict-markers` меняет поведение: любой маркер, отсутствующий в списке `markers =`, превращается в **ошибку** уже на этапе сбора тестов, и запуск падает целиком, а не продолжается с предупреждением.

В `boilerplate/pytest.ini` это уже включено через `addopts`:

```ini
addopts = -ra --strict-markers
testpaths = tests
```

`addopts` — список флагов командной строки, которые pytest подставляет автоматически при каждом запуске, как если бы вы вписывали их вручную в `python -m pytest ...`. Помимо `--strict-markers`, здесь есть `-ra` — флаг, включающий короткую сводку в конце запуска по всем тестам, результат которых отличается от простого «прошёл» (упавшие, пропущенные, ожидаемо неудавшиеся и т. п.), чтобы такие тесты не терялись в потоке точек и `PASSED`.

## Пример

Допустим, вы добавили тесту новый маркер, не вписав его в `pytest.ini`:

```python
@pytest.mark.slow
def test_something_heavy():
    ...
```

При `--strict-markers` запуск `python -m pytest` завершится ошибкой ещё до выполнения тестов:

```
'slow' not found in `markers` configuration option
```

Чтобы исправить, маркер нужно зарегистрировать точно так же, как уже сделано для остальных:

```ini
[pytest]
markers =
    ui: UI-тесты (Playwright)
    api: API-тесты (requests)
    unit: тесты чистых функций/утилит, без сети и без браузера
    smoke: быстрый набор критичных проверок
    regress: полный регрессионный набор
    slow: тесты с заметным временем выполнения
```

После этого ошибка исчезает, а маркер `slow` становится полноценной, задокументированной частью проекта — как и остальные пять.

## Частые ошибки

* Добавить новый маркер в код теста и забыть зарегистрировать его в `pytest.ini` — с `--strict-markers` весь запуск (а не только один тест) остановится с ошибкой ещё до выполнения.
* Зарегистрировать маркер без описания после двоеточия — формально сработает, но другим разработчикам придётся гадать, что маркер означает.
* Считать, что `--strict-markers` также проверяет корректность имён фикстур — это не так, это два независимых механизма: незарегистрированная фикстура и так даёт отдельную понятную ошибку `fixture '...' not found`, `--strict-markers` касается исключительно маркеров.
* Копировать `addopts` из чужого проекта без понимания, что означает каждый флаг — например, слепо добавлять флаги, специфичные для другого CI-окружения.

## Мини-задание

В своём учебном проекте с настроенным `pytest.ini` (по образцу `boilerplate/pytest.ini`, включая `--strict-markers`) добавьте к одному из тестов маркер `@pytest.mark.wip`, не регистрируя его. Запустите `python -m pytest` и сохраните текст ошибки. Затем зарегистрируйте `wip` в `pytest.ini` и убедитесь, что запуск снова проходит без ошибок.
