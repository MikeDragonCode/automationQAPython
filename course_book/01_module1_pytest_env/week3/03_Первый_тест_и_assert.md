# 1.3. Первый тест и простые assert

## Зачем это нужно

Сам по себе тест без проверок ничего не стоит — pytest умеет находить и запускать функции, но именно `assert` внутри них решает, работает код или нет. Умение писать понятные, однозначные проверки и быстро читать вывод pytest при падении теста — базовый навык, без которого невозможно работать с автотестами дальше, будь то API или UI.

## Теория

В отличие от `unittest` (модуль тестирования, встроенный в стандартную библиотеку Python), где нужно писать `self.assertEqual(a, b)`, `self.assertTrue(x)` и десятки похожих методов, в pytest используется обычное ключевое слово Python:

```python
assert условие
```

Если условие истинно — ничего не происходит, тест продолжается. Если ложно — pytest поднимает `AssertionError` и помечает тест как упавший.

Ключевая особенность pytest — **assertion rewriting**: pytest переписывает `assert`-выражения так, чтобы при падении показать не просто «AssertionError», а подробности — какие именно значения сравнивались и чем они отличаются. Это то, что отличает `assert a == b` в pytest от того же кода в обычном Python-скрипте: в pytest вы получаете читаемый диф, а не голое исключение.

### Что можно проверять через assert

```python
assert result == expected        # равенство
assert result != expected        # неравенство
assert "abc" in result           # вхождение
assert result                    # истинность (truthy)
assert not result                # ложность (falsy)
assert result is None
assert result is not None
```

Отдельных «специальных» функций для этого не нужно — весь арсенал сравнений Python работает напрямую.

### assert сравнивает не только простые значения

Точно так же `==` работает и со списками, и со словарями — Python сравнивает их структурно, а не по ссылке:

```python
assert [1, 2, 3] == [1, 2, 3]                                    # списки — поэлементно, порядок важен
assert {"id": 1, "name": "Mike"} == {"name": "Mike", "id": 1}    # словари — по парам ключ-значение, порядок не важен
```

Это пригодится уже совсем скоро: в API-тестах модуля 3 ответ сервера почти всегда приходит как словарь или список словарей, и `assert response_json == expected_json` — рабочий способ сравнить их целиком. Если равенство не выполнится, pytest покажет, какая именно часть структуры отличается, а не просто «структуры не равны» (более сложные случаи — вложенные структуры, сравнение без учёта порядка списков — разберём отдельно позже в модуле).

### Один тест — одна проверяемая идея

Тест может содержать несколько `assert` подряд, но как только первый из них не выполнится, выполнение теста немедленно прерывается — строки после упавшего `assert` не выполнятся вообще. Поэтому хорошая практика — называть тест так, чтобы по имени было понятно, какое именно поведение он проверяет, и держать в тесте связанные между собой проверки одного сценария, а не собирать в одну функцию проверки разных, не связанных друг с другом вещей.

### Структура теста: Arrange-Act-Assert

Удобный способ организовать тело теста — три условных шага:

1. **Arrange** — подготовить входные данные.
2. **Act** — вызвать проверяемую функцию.
3. **Assert** — сравнить результат с ожиданием.

Для маленьких тестов на чистых функциях первый шаг часто вырождается в одну строку или вовсе отсутствует.

## Пример

Возьмём функцию `count_vowels` из `boilerplate/utils/string_utils.py` и напишем для неё простой, непараметризованный тест (параметризацию разберём в следующем уроке):

```python
from utils.string_utils import count_vowels


def test_count_vowels_counts_ru_and_en():
    # Act
    result = count_vowels("Hello Привет")

    # Assert
    assert result == 4
```

Если бы функция считала неверно и вернула, скажем, `3`, pytest показал бы примерно такое падение:

```
def test_count_vowels_counts_ru_and_en():
        result = count_vowels("Hello Привет")
>       assert result == 4
E       assert 3 == 4

tests/unit/test_string_utils.py:52: AssertionError
```

Обратите внимание: pytest сам подставил конкретные значения (`3 == 4`) — это и есть assertion rewriting в действии, вам не нужно было писать сообщение об ошибке вручную.

## Частые ошибки

* **Классическая ловушка**: `assert (result == expected, "сообщение об ошибке")`. Это выражение — не проверка с сообщением, а сравнение с непустым кортежем `(False, "сообщение")` или `(True, "сообщение")`, который в Python **всегда истинен**, потому что это непустой объект. Такой тест никогда не упадёт, даже если `result != expected`. Правильно передавать сообщение через запятую вне скобок: `assert result == expected, "сообщение об ошибке"`.
* Сравнивать вычисленные дробные числа через `==` — из-за особенностей чисел с плавающей точкой `0.1 + 0.2 == 0.3` в Python равно `False`. Для таких случаев есть отдельный инструмент — `pytest.approx` (разберём в модуле 1, неделя 4).
* Заворачивать `assert` в `try/except`, «чтобы тест не падал» — это не чинит проблему, а прячет её; тест перестаёт быть полезным.
* Проверять сразу несколько независимых сценариев в одной функции («и так, и так, и ещё вот так») — при падении неясно, какая именно часть сломалась, а часть проверок после первого падения вообще не выполнится.

## Мини-задания

1. **Разминка.** Напишите один тест `test_is_palindrome_true_for_racecar`, который проверяет `is_palindrome("racecar") is True`. Запустите его и убедитесь, что он проходит.
2. **Основное.** Для функции `slugify` из `boilerplate/utils/string_utils.py` напишите (без параметризации) три отдельных теста с говорящими именами: текст уже в нижнем регистре без изменений; текст, состоящий только из знаков препинания и пробелов (проверьте, что результат — пустая строка); текст с пробелами по краям. Запустите их и убедитесь, что все три проходят.
3. **Ближе к практике.** Напишите тест для `chunk_list` из `boilerplate/utils/string_utils.py`: вызовите `chunk_list(list(range(6)), 2)` и одним `assert` сравните результат целиком со списком `[[0, 1], [2, 3], [4, 5]]` — как в примере из теории про сравнение структур.
4. **Со звёздочкой.** Напишите тест, в котором намеренно допустите классическую ловушку: `assert (2 + 2 == 5, "сложение сломано")`. Запустите его и убедитесь, что тест прошёл, хотя `2 + 2 != 5`. Исправьте тест, убрав лишние скобки (`assert 2 + 2 == 5, "сложение сломано"`), и убедитесь, что теперь он честно падает.
