# 2.6 Конфликты слияния: откуда берутся и как решать

## Зачем это нужно

Как только над одним репозиторием работает больше одного человека, конфликты слияния —
это не "что-то пошло не так", а нормальная часть процесса. В общем репозитории `boilerplate/`
несколько студентов будут добавлять функции в одни и те же файлы (`utils/string_utils.py`,
`conftest.py`) — рано или поздно твоя ветка столкнётся с чужой. Важно не бояться этого экрана
с `<<<<<<<`, а уметь спокойно его разобрать.

## Теория

Git умеет автоматически сливать изменения, если они не пересекаются: ты правил одну часть файла,
кто-то другой — совсем другую. Конфликт возникает, когда обе стороны изменили **одни и те же
строки** одного файла (или одна сторона файл изменила, а другая — удалила) — Git не может
угадать, какой вариант правильный, и просит решить это тебя.

Конфликт внутри файла выглядит так:

```python
<<<<<<< HEAD
def reverse_words(text: str) -> str:
    return " ".join(text.split()[::-1])
=======
def reverse_words(text: str) -> str:
    words = text.split()
    words.reverse()
    return " ".join(words)
>>>>>>> feature/add-reverse-words
```

- Всё между `<<<<<<< HEAD` и `=======` — версия из твоей текущей ветки.
- Всё между `=======` и `>>>>>>> <имя ветки>` — версия из ветки, которую сливаешь.
- Сами маркеры `<<<<<<<`, `=======`, `>>>>>>>` — это не часть кода, их нужно убрать вручную после
  того, как выбран (или скомбинирован) правильный вариант.

Порядок действий при разрешении конфликта локально:

1. Синхронизируй `main`: `git switch main && git pull origin main`.
2. Вернись в свою ветку: `git switch feature/add-reverse-words`.
3. Подтяни актуальный `main` в свою ветку: `git merge main` (конфликт, если он есть, покажется
   именно сейчас — в твоей ветке, а не в общем `main`, где его увидели бы все).
4. Открой файлы, помеченные как конфликтные (`git status` покажет список), и вручную реши, какой
   код должен остаться — один из вариантов, оба, или что-то новое, что совмещает оба намерения.
5. Убери маркеры `<<<<<<<`, `=======`, `>>>>>>>` полностью — если оставить хоть один, файл сломает
   синтаксис.
6. Прогони тесты локально — конфликт мог быть разрешён технически верно, но логически неправильно.
7. `git add <файл>`, затем `git commit` (Git сам предложит сообщение вида "Merge branch 'main'
   into ...", его можно оставить как есть).
8. `git push` — обновлённая ветка и PR обновятся автоматически.

Небольшой лайфхак, который резко снижает число и размер конфликтов: чаще подтягивай `main` в свою
ветку, не откладывая работу на неделю — чем дольше ветка живёт отдельно, тем больше в ней успевает
разойтись с `main`.

## Пример

Два студента параллельно добавляют функции в `utils/string_utils.py`. Первый успел смёржить свой
PR первым — в `main` уже есть чужая функция `reverse_words`. Второй студент, синхронизируя свою
ветку `feature/add-count-words` с `main`, получает конфликт — потому что оба добавляли новую
функцию в конец одного и того же файла, и Git не может понять, в каком порядке их сохранить:

```python
<<<<<<< HEAD
def count_words(text: str) -> int:
    return len(text.split())
=======
def reverse_words(text: str) -> str:
    return " ".join(text.split()[::-1])
>>>>>>> main
```

Решение здесь простое — обе функции нужны, конфликт "ложный" (пересеклись только соседние строки):

```python
def count_words(text: str) -> int:
    return len(text.split())


def reverse_words(text: str) -> str:
    return " ".join(text.split()[::-1])
```

После этого — `git add utils/string_utils.py`, `git commit`, прогнать тесты, `git push`.

## Частые ошибки

- В панике удалить целиком "чужую" сторону конфликта, не поняв, что она делала — это потеря
  чужой работы, а не решение конфликта.
- Забыть убрать один из маркеров (`<<<<<<<` остаётся в файле) — файл перестаёт быть валидным
  Python-кодом, тесты падают с `SyntaxError`.
- Запушить разрешённый конфликт, не прогнав тесты — конфликт мог "разрешиться" без синтаксических
  ошибок, но с логической: например, случайно выбрана более старая версия функции.
- Пытаться разрешать конфликт прямо в `main`, а не в своей feature-ветке — тогда неразрешённое
  состояние временно оказывается в общей ветке, которой пользуются все.

## Мини-задание

Специально создай конфликт в тренировочном репозитории: заведи две ветки от одного `main`, в обеих
измени одну и ту же строку одного файла по-разному, смёржи одну ветку в `main`, а во второй сделай
`git merge main` — и разреши получившийся конфликт руками по шагам из этого урока.
