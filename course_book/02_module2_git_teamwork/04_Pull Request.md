# 2.4 Pull Request: что это и зачем

## Зачем это нужно

С этого модуля любое домашнее задание сдаётся Pull Request'ом. Это не формальность "для галочки" —
это основной механизм, которым код попадает в общий репозиторий в любой команде, где ты будешь
работать после курса. Разобраться, что такое PR и зачем он нужен, важнее, чем выучить его кнопки.

## Теория

Pull Request (PR) — это не примитив самого Git, а функция хостинга (GitHub, GitLab и т. п.):
запрос на слияние одной ветки в другую, обёрнутый в обсуждение и ревью. Технически "взять и
влить" ветку можно и одной командой `git merge` — но тогда никто, кроме тебя, не увидит
изменения до того, как они уже окажутся в `main`.

Схема, по которой работает весь курс дальше (её называют **GitHub flow**):

```
main ──●───────────────────────────────●──   (стабильная ветка)
         \                             /
          ●──●──●  (commits)  ──── PR ●       (feature-ветка)
       создал ветку   работал   открыл PR → ревью → правки → approve → merge
```

1. Создаёшь ветку от актуального `main` (урок 2.3).
2. Делаешь один или несколько коммитов с решением задачи.
3. Пушишь ветку на GitHub (`git push -u origin <branch>`).
4. Открываешь Pull Request: указываешь, из какой ветки в какую хочешь влить изменения.
5. CI (если настроен, подробно — в модуле 6) автоматически прогоняет тесты на твоей ветке.
6. Ревьюер смотрит diff, оставляет комментарии.
7. Ты правишь код по комментариям, пушишь новые коммиты — они автоматически появляются в том же PR.
8. Когда ревьюер согласен — approve, и PR мёржится в `main`.

Зачем этот процесс, а не прямой `push` в `main`:

- **Контроль качества** — второй человек видит код до того, как он попадёт в общую ветку, а не
  после.
- **Явная точка для обсуждения** — комментарии привязаны к конкретным строкам кода и остаются в
  истории, в отличие от устного "я тебе там в чате написал".
- **Проверка перед слиянием** — CI может заблокировать merge, если тесты падают.
- **Обмен знаниями** — читая чужие PR, ты видишь, как решают задачи другие, а твой код видят и
  комментируют тоже не в пустоту.

Анатомия страницы PR на GitHub:

- **Title** и **Description** — что и зачем сделано (подробно — в уроке 2.5).
- **Files changed** — diff: что именно добавлено/удалено/изменено.
- **Commits** — список коммитов ветки.
- **Checks** — статус автоматических проверок (CI).
- **Conversation** — обсуждение и комментарии ревьюеров.

Если работа ещё не закончена, но хочется показать прогресс или получить CI-фидбек раньше времени —
можно открыть **Draft PR**: тот же PR, но помеченный как черновик, чтобы никто не начал ревью
раньше времени.

## Пример

Продолжаем ветку `feature/add-reverse-words` из предыдущего урока:

```bash
git push -u origin feature/add-reverse-words
```

После этого на странице форка на GitHub появляется баннер "Compare & pull request" — нажимаешь на
него, указываешь:

- **base**: `main` (куда вливаем),
- **compare**: `feature/add-reverse-words` (что вливаем),

заполняешь Title и Description (как именно — урок 2.5) и нажимаешь **Create pull request**.
С этого момента PR открыт, виден всем, и в него можно продолжать пушить новые коммиты по
результатам ревью — они автоматически добавятся в тот же diff.

## Частые ошибки

- Открыть PR из `main` своего форка в `main` оригинального репозитория, потому что забыли создать
  отдельную ветку — тогда в PR попадает вообще всё, что есть в твоём форке, а не одна задача.
- Оставить Title вида "changes" и пустое Description — ревьюеру приходится самому разбираться,
  что и зачем сделано.
- Открыть PR и забыть про него на две недели, пока в `main` не накопились изменения, из-за которых
  ветка уже не мёржится без конфликтов.
- Не посмотреть на статус CI перед тем, как звать ревьюера — просить ревью падающего кода.

## Мини-задание

В своём форке `boilerplate/` (или в любом тренировочном репозитории на GitHub) открой Draft PR
для любой маленькой правки. Изучи интерфейс: вкладку Files changed, вкладку Checks, где появляются
комментарии. Пока не мёржи — просто разберись, что где находится.
