# 2.9 Git flow этого курса: форк → ветка → PR → ревью → merge

## Зачем это нужно

Все предыдущие уроки модуля были про отдельные кирпичики — ветки, PR, конфликты, ревью. Этот
урок собирает их в один цикл, который ты будешь повторять для каждого домашнего задания с этого
модуля и до конца курса. Дальше в модулях 3–5 в этот же цикл просто подставляются новые задачи
(API-клиент, Page Object, Allure-шаги) — сам процесс не меняется.

## Теория

### Полный цикл одной задачи

Полный цикл одной задачи в общем репозитории `boilerplate/`:

1. **Форк — один раз.** Форкаешь `boilerplate/` в свой GitHub-аккаунт (урок 2.2). Это разовое
   действие на весь курс, а не на каждую задачу.
2. **Синхронизация перед стартом.** Перед тем как начинать новую задачу, подтяни актуальный
   `main`: `git switch main`, `git fetch upstream`, `git merge upstream/main`, `git push origin
   main`. Это особенно важно начиная с модуля 3 — новые задачи строятся поверх кода, который
   влили другие студенты (новые API-клиенты, Page Object'ы), и работа от устаревшего `main`
   почти гарантированно приведёт к конфликтам.
3. **Новая ветка.** `git switch -c feature/<короткое-описание>` (или `fix/...` для багфиксов) —
   урок 2.3.
4. **Реализация — маленькая и по структуре репозитория.** Правишь код, следуя уже существующим
   паттернам: новая функция — в `utils/`, тест — в соответствующей папке `tests/unit|api|ui/`,
   новый клиент — рядом с `UsersClient` в `clients/`. Не переписывай архитектуру заново ради одной
   задачи (это явное правило самого `boilerplate/README.md`).
5. **Коммиты и локальная проверка.** Осмысленные коммиты (урок 2.1), обязательно `pytest` локально
   перед тем, как пушить — зелёные тесты снимают половину возможных комментариев ревьюера.
6. **Push и открытие PR.** `git push -u origin feature/<...>`, затем PR на GitHub (урок 2.4).
   Уточни у преподавателя/в когорте, куда именно в вашем случае открывается PR — в `main` своего
   же форка (и тогда ревьюер смотрит форк) или сразу в оригинальный `boilerplate` (если у группы
   настроен единый репозиторий с правами для всех студентов). Механика PR одинаковая в обоих
   случаях, разница — только в том, какой репозиторий указан как base.
7. **Описание по шаблону.** Что сделано / почему / как проверить (урок 2.5).
8. **Ревью одногруппника.** Просишь ревью в чате когорты, отвечаешь на комментарии, пушишь
   исправления (урок 2.7).
9. **Конфликты, если возникли.** Синхронизируешь ветку с `main`, разрешаешь конфликты локально
   (урок 2.6), снова прогоняешь тесты, пушишь.
10. **Merge.** После approve (и зелёного CI, если он настроен — модуль 6) PR мёржится. Конкретный
    способ (обычный merge или squash) обычно закреплён в самом репозитории — придерживайся того,
    что уже принято, а не выбирай на своё усмотрение.
11. **Уборка.** Удаляешь смёрженную ветку (`git branch -d feature/...`, GitHub предложит удалить
    и remote-версию), синхронизируешь `main` ещё раз.
12. **Следующая задача — с шага 2.**

### Разовые шаги vs то, что повторяется каждый раз

Легко потеряться в двенадцати пунктах, если не разделить их по частоте:

- **разово, один раз на весь курс** — шаг 1 (форк);
- **на каждую задачу, от начала до конца** — шаги 2-12, весь цикл целиком, включая уборку в
  конце.

То есть форк — это не "шаг перед первой задачей", а вообще отдельное разовое действие, а сама
рабочая последовательность (синхронизация → ветка → код → PR → ревью → merge → уборка) —
это то, что выполняется заново для каждого домашнего задания вплоть до конца курса.

### Куда именно открывается PR: свой форк или upstream

Шаг 6 не зря отдельно уточняет этот момент — на практике встречаются оба варианта организации
курса:

- **base: `main` твоего собственного форка** — ревьюер смотрит PR в твоём репозитории, у тебя
  там же есть права смёржить самому после approve;
- **base: `main` оригинального `upstream`-репозитория** — используется, если у всей группы
  настроен один общий репозиторий с правами на запись для всех студентов, тогда форк вообще не
  обязателен, PR открывается сразу туда.

Механика самого PR (Files changed, ревью, комментарии) одинаковая в обоих случаях — разница
только в том, какой репозиторий указан как **base** на странице создания PR (урок 2.4).

## Пример

Чек-лист из шагов выше, применённый к конкретной домашней задаче — добавить в `boilerplate/`
ещё одну функцию в `utils/string_utils.py` с тестом (по аналогии с `week3-4` модуля 1):

```bash
git switch main && git fetch upstream && git merge upstream/main && git push origin main

git switch -c feature/add-count-words

# utils/string_utils.py — добавили count_words()
# tests/unit/test_string_utils.py — добавили тест(ы) для count_words()

pytest -m unit

git add utils/string_utils.py tests/unit/test_string_utils.py
git commit -m "Add count_words util with tests"

git push -u origin feature/add-count-words
# → открыть PR на GitHub, описание по шаблону из урока 2.5
# → попросить ревью у одногруппника
# → ответить на комментарии, если есть
# → merge после approve
```

Именно эта последовательность — минимально достаточный набор шагов для сдачи домашнего задания
модуля (см. `99_Домашнее_задание.md`).

## Частые ошибки

- Создать новую ветку от устаревшего локального `main`, не подтянув `upstream` — это самая частая
  причина "необъяснимых" конфликтов при открытии PR.
- Взять в одну ветку/PR сразу две задачи — договорённость "одна задача — одна ветка — один PR"
  действует с первого дня общего репозитория.
- Не уточнить у преподавателя, куда именно в вашей группе открывается PR (в свой форк или в общий
  upstream-репозиторий), и в итоге открыть PR туда, где его никто не увидит.
- Забыть удалить смёрженную ветку — со временем список веток превращается в свалку, в которой
  легко случайно продолжить работу в устаревшей ветке.

## Мини-задания

1. **Разминка.** В своём уже форкнутом `boilerplate/` выполни только шаг синхронизации (шаг 2):
   `git switch main`, `git fetch upstream`, `git merge upstream/main`, `git push origin main`.
   Обрати внимание на вывод — "Already up to date" или реальные изменения — это ровно та команда,
   с которой начинается любая новая задача.
2. **Основное.** Не подглядывая в этот урок, распиши по шагам (на бумаге или в заметке) весь цикл
   от форка до удаления смёрженной ветки своими словами. Затем сверься с уроком — какие шаги забыл
   или перепутал порядок.
3. **Ближе к практике.** Пройди цикл целиком по-настоящему на одной по-настоящему маленькой
   задаче в своём форке `boilerplate/` (например, поправь опечатку или добавь короткий докстринг):
   синхронизация → новая ветка → коммит → push → открытие (пусть даже Draft) PR с описанием по
   шаблону из урока 2.5.
4. **Со звёздочкой.** Специально нарушь шаг 2: создай новую ветку от **не синхронизированного**
   локального `main` (пропусти `fetch upstream` / `merge upstream/main`), сделай в ней коммит и
   запушь. Затем представь (или, если получится, воспроизведи с двумя локальными клонами), что
   пока ты работал, в `upstream` кто-то другой уже что-то влил. Синхронизируй свою ветку задним
   числом (`git fetch upstream`, `git merge upstream/main` — уже находясь в feature-ветке) и
   разреши конфликт, если он возник, по шагам из урока 2.6.
