# 2.3 Ветки: branch, checkout, switch

## Зачем это нужно

В общем репозитории одновременно работает вся группа. Если все коммитят прямо в `main`, любая
неудачная правка одного человека ломает работу всех остальных. Ветки решают это: каждая задача
делается изолированно, и в `main` попадает только то, что уже проверено и одобрено ревьюером.

## Теория

Ветка в Git — это не копия файлов, а просто именованный указатель на коммит. Когда ты создаёшь
ветку, Git не копирует проект — он лишь запоминает, "с какого коммита начинается эта линия
разработки". Именно поэтому переключение между ветками — мгновенная операция.

```
A---B---C           (main)
         \
          D---E---F  (feature/add-slugify)
```

`A`, `B`, `C` — коммиты в `main`. От коммита `C` создана ветка `feature/add-slugify`, в ней
появляются свои коммиты `D`, `E`, `F`, которые пока никак не влияют на `main`. Когда работа
готова и прошла ревью, эта ветка сливается обратно (подробно про слияние — в уроках 2.4 и 2.6).

Команды:

```bash
git branch                     # список локальных веток, текущая отмечена *
git branch -a                  # включая ветки на remote
git branch <name>               # создать ветку (без переключения на неё)
git switch <name>               # переключиться на существующую ветку
git switch -c <name>            # создать ветку и сразу переключиться на неё
git checkout <name>             # старый вариант switch, тоже переключает ветку
git checkout -b <name>          # старый вариант switch -c
git branch -d <name>             # удалить локальную ветку (только если она уже слита)
```

`git switch` появился позже как более понятная замена части возможностей `git checkout`
(у `checkout` слишком много разных задач: переключение веток, откат файлов, создание веток).
Оба варианта рабочие, `switch` просто читается яснее — в этом курсе будем использовать его.

Практика, которая экономит нервы: **`main` всегда должен быть рабочим**. Вся разработка — в
отдельных ветках, названных по смыслу задачи: `feature/add-slugify`, `fix/wrong-status-code`.
Осмысленное имя ветки — это тоже часть коммуникации с командой, по нему сразу понятно, что внутри.

## Пример

Работаем в своём форке `boilerplate/`. Хотим добавить новую функцию в `utils/string_utils.py`
и тест к ней — создаём для этого отдельную ветку от актуального `main`:

```bash
git switch main
git pull origin main                     # убедились, что main свежий

git switch -c feature/add-reverse-words

# правим utils/string_utils.py, добавляем tests/unit/test_string_utils.py
git add utils/string_utils.py tests/unit/test_string_utils.py
git commit -m "Add reverse_words util with tests"

git branch
#   main
# * feature/add-reverse-words
```

`main` при этом не тронут — если сейчас переключиться обратно (`git switch main`), новой функции
там не будет, она существует только в ветке `feature/add-reverse-words`, пока не будет
смёржена через PR.

После того как ветка смёржена и в ней больше нет нужды:

```bash
git switch main
git branch -d feature/add-reverse-words
```

## Частые ошибки

- Решать несколько разных задач в одной ветке — потом невозможно замёржить одну часть без другой.
- Не глядя, в какой ветке находишься, и закоммитить правку прямо в `main` (проверяй `git branch`
  или подсказку текущей ветки в терминале/IDE перед коммитом).
- Создать ветку от устаревшего `main` (забыли `git pull` перед `git switch -c`) — задачи, которые
  уже слиты в `main` другими, не попадают в твою ветку, и дальше при открытии PR вылезают лишние
  конфликты.
- Пытаться удалить веткой `-d` ветку с ещё не смёрженными коммитами — Git специально
  откажется это делать (принудительно это можно обойти `-D`, но так легко потерять работу
  безвозвратно).

## Мини-задание

В тренировочном репозитории создай две независимые ветки от `main` для двух разных мелких правок
(например, две разные функции). Переключайся между ними и наблюдай, как меняется содержимое
файлов — в каждой ветке видна только "своя" работа.
