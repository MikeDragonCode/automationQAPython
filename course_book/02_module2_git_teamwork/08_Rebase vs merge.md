# 2.8 Rebase vs merge: коротко о том, что это

## Зачем это нужно

Слово "rebase" рано или поздно встретится: в подсказке GitHub ("This branch has conflicts that
must be resolved" с предложением rebase или merge), в чужом PR, в статье про Git. Этот урок не
учит тебя пользоваться rebase каждый день — для домашних заданий курса хватит `merge`, — но
объясняет, что это такое, чтобы термин не пугал и чтобы не сделать с ним что-то необратимое.

## Теория

И `merge`, и `rebase` решают одну и ту же задачу — "взять изменения из другой ветки", но по-разному
обращаются с историей коммитов.

### merge: сохраняет обе истории

`merge` создаёт новый, отдельный merge-коммит, который объединяет две истории. Ничего не
переписывается, все коммиты обеих веток остаются как есть:

```
A---B---C-------M   (main)
         \     /
          D---E      (feature)
```

В `git log --oneline --graph` это видно как явное разветвление и слияние — по графу можно
восстановить, что ветки когда-то расходились:

```bash
git log --oneline --graph
# *   M Merge branch 'feature' into main
# |\
# | * E ...
# | * D ...
# * | C ...
# |/
# * B ...
```

### rebase: переписывает историю

`rebase` переносит коммиты твоей ветки так, будто они изначально были написаны поверх нового
состояния другой ветки. История становится линейной, но у перенесённых коммитов **меняются
хэши** — фактически это новые коммиты с тем же содержимым:

```
A---B---C---D'---E'   (feature, после rebase на main)
```

Здесь `D'` и `E'` — не те же коммиты, что `D` и `E` были раньше, а их копии с новой точкой отсчёта.

### rebase -i: причесать локальные коммиты

Отдельное применение rebase — не синхронизация с другой веткой, а причёсывание собственной
истории перед тем, как её кто-то увидит: объединить несколько мелких коммитов "wip", "wip2",
"fix typo" в один осмысленный. Общий принцип — интерактивный `git rebase -i` открывает список
последних коммитов, где можно пометить их для объединения (`squash`) или переформулировать
сообщение; точные детали интерфейса зависят от версии Git, здесь важно только само существование
этой возможности — специально тренировать её в этом курсе не будем.

### Почему нельзя rebase публичную ветку

Из механики rebase следует главное правило: **не делай rebase ветки, которую уже видели/скачали
другие люди**. Если кто-то успел сделать `git pull` твоей ветки до rebase, а после rebase историю
переписали — у него в локальной копии останутся старые коммиты, а у тебя — новые с другими
хэшами, и синхронизация превратится в путаницу (детальный пример — в "Со звёздочкой" ниже).

### Когда что уместно

- **merge** — безопасный дефолт для синхронизации своей ветки с `main` (то, что показано в
  уроке 2.6). Именно так стоит делать в этом курсе.
- **rebase** — часто используют для того, чтобы почистить историю локальных коммитов перед
  открытием PR, или в командах, которые сознательно поддерживают линейную историю `main`. После
  rebase локальной ветки, которую больше никто не скачивал, для обновления remote нужен
  `git push --force` (точнее, более безопасный `--force-with-lease`) — обычный `push` откажется,
  потому что история разошлась.

### Что принято в этом курсе

Тестами и домашками проверяется результат, а не то, каким способом ты синхронизировал ветку с
`main` — используй `git pull` / `git merge`, это самый предсказуемый вариант, пока ты не
наработал привычку понимать, что делает rebase в конкретной ситуации.

## Пример

Одни и те же две ветки — что получится в истории при merge и при rebase:

```
До:
A---B---C           (main)
     \
      D---E          (feature)

После git merge main (находясь в feature):
A---B---C---------M   (feature)
     \           /
      D---------E

После git rebase main (находясь в feature):
A---B---C---D'---E'   (feature)
```

После merge в истории виден отдельный merge-коммит `M` и то, что ветки расходились и снова
сошлись. После rebase — ровная линия коммитов, как будто `feature` всегда создавалась от текущего
`C`, а не от старого `B`.

## Частые ошибки

- Сделать rebase ветки, которую уже забрал себе (`git pull`) кто-то ещё, без предупреждения —
  у него в истории образуется путаница с "дублирующимися" коммитами.
- Перепутать `git pull` (по умолчанию — fetch + merge) с rebase — это разные операции, хотя `git
  pull --rebase` тоже существует и делает третье: подтягивает изменения и переносит твои коммиты
  поверх них.
- Сделать `git push --force` в общую ветку, которой пользуются другие, без согласования — это
  может стереть чужие коммиты на remote.

## Мини-задания

1. **Разминка.** В тренировочном репозитории сделай подряд три локальных коммита с сообщениями
   `wip`, `wip2`, `fix typo` (не важно, что именно меняется в файле). Посмотри `git log --oneline`
   и своими словами опиши, почему такая история — ровно та проблема, для решения которой обычно
   применяют rebase -i.
2. **Основное.** В песочнице [Learn Git Branching](https://learngitbranching.js.org/?locale=ru_RU)
   пройди уровень, посвящённый rebase, и в 2-3 предложениях своими словами опиши, чем результат
   отличается от того, что получилось бы в том же сценарии через merge.
3. **Ближе к практике.** В тренировочном репозитории повтори сценарий "main ушёл вперёд, пока ты
   работал в feature-ветке" (как в уроке 2.6), но в этот раз, следуя принятой в курсе практике,
   реши его через `git merge main` в свою ветку. Посмотри `git log --oneline --graph` и опиши,
   чем этот граф отличался бы, если бы вместо merge был сделан rebase.
4. **Со звёздочкой.** Смоделируй ситуацию из "Частых ошибок" с двумя локальными клонами одного
   тренировочного репозитория ("клон A" и "клон B" — как будто это твой компьютер и компьютер
   коллеги). Из клона A запушь feature-ветку, из клона B сделай её `git pull`. Затем в клоне A
   сделай `git rebase` этой ветки на обновлённый `main` и `git push --force-with-lease`. После
   этого в клоне B попробуй обычный `git pull` — зафиксируй, что покажет Git, и объясни своими
   словами, почему это происходит.
