# 2.2 Публикация на GitHub: remote, push, pull, форк

## Зачем это нужно

Локальный репозиторий — это хорошо, но общий репозиторий курса `boilerplate/` живёт на GitHub,
и с этого модуля именно туда попадают все домашние задания в виде Pull Request. Прежде чем
говорить про ветки и PR, нужно понять один механический шаг: как локальная копия проекта
связывается с удалённым репозиторием и обменивается с ним изменениями.

## Теория

GitHub — это хостинг для Git-репозиториев плюс набор инструментов поверх него: Pull Request'ы,
Issues, ревью кода, CI (GitHub Actions). Сам Git не обязан знать про GitHub — это просто ещё один
"удалённый репозиторий", с которым можно синхронизироваться.

Связь с удалённым репозиторием:

```bash
git remote add origin <URL-репозитория>   # добавить удалённый репозиторий с именем origin
git remote -v                              # посмотреть, какие remote'ы уже подключены
```

Обмен изменениями:

```bash
git push -u origin main   # отправить локальную ветку main на origin, запомнить связь (-u)
git push                  # дальше можно просто push, Git помнит, куда
git pull origin main      # забрать изменения с origin и слить их в текущую ветку
```

`git pull` — это фактически `git fetch` (скачать изменения) + `git merge` (слить их с твоей
веткой) одной командой.

Получить копию существующего репозитория целиком — не `init`, а `clone`:

```bash
git clone <URL-репозитория>
```

### Форк vs клон

Если у тебя есть права на запись в репозиторий — достаточно `git clone` и `git push` напрямую.
Но у `boilerplate/` — общего репозитория курса — у тебя таких прав нет и не будет: это стартовый
шаблон для всех студентов. Поэтому используется схема **fork**:

1. На GitHub нажимаешь **Fork** на странице `boilerplate` — GitHub создаёт полную копию
   репозитория в твоём аккаунте, с правами на запись.
2. Клонируешь **свой форк** к себе на компьютер (`git clone <URL-твоего-форка>`) — это станет
   remote'ом `origin`.
3. Добавляешь оригинальный `boilerplate` как ещё один remote — по конвенции его называют
   `upstream`:

```bash
git remote add upstream <URL-оригинального-boilerplate>
git remote -v
# origin    <твой форк>       (fetch/push)
# upstream  <оригинальный boilerplate>  (fetch/push)
```

Дальше `origin` — твоя рабочая копия, в неё пушишь свои ветки. `upstream` — используется только
для того, чтобы периодически подтягивать изменения из оригинального репозитория (`git fetch
upstream` + `git merge upstream/main`), если он обновится.

Для авторизации `git push` на GitHub логин/пароль уже не используются — нужен либо личный токен
доступа (Personal Access Token), либо настроенный SSH-ключ. Как именно оформить доступ, зависит
от того, что использует твоя когорта/платформа — уточни у преподавателя, если возникнут проблемы
с авторизацией при первом `push`.

## Пример

Форкаем и клонируем общий репозиторий курса:

```bash
# 1. Нажал Fork на странице boilerplate на GitHub — получил свою копию
# 2. Клонирую свой форк
git clone git@github.com:<your-username>/boilerplate.git
cd boilerplate

# 3. Добавляю оригинальный репозиторий как upstream
git remote add upstream git@github.com:<course-org>/boilerplate.git
git remote -v

# 4. Перед началом работы — синхронизирую main с upstream
git fetch upstream
git switch main
git merge upstream/main
git push origin main
```

После этого локальная папка `boilerplate/` содержит актуальную структуру общего репозитория
(`clients/`, `pages/`, `tests/unit|api|ui/`, `conftest.py`, `pytest.ini`) — и готова к тому, чтобы
от неё создать первую рабочую ветку (следующий урок).

## Частые ошибки

- Пытаться сделать `git push` прямо в оригинальный `boilerplate`, а не в свой форк — GitHub вернёт
  ошибку доступа: писать можно только в свой форк.
- Забыть синхронизировать форк с `upstream` перед началом новой задачи — новая ветка создаётся от
  устаревшего `main`, и потом это выливается в лишние конфликты при открытии PR.
- Перепутать `origin` и `upstream` местами при добавлении remote'ов.
- Сделать изменения, забыть `git pull`, и только потом обнаружить, что на сервере уже другая
  версия файла — это тоже источник конфликтов (урок 2.6).

## Мини-задание

Форкни `boilerplate/` в свой GitHub-аккаунт (по-настоящему — это тот же репозиторий, с которым ты
будешь работать весь курс). Склонируй форк локально, добавь `upstream`, указывающий на оригинальный
репозиторий, и убедись командой `git remote -v`, что оба remote'а настроены правильно.
