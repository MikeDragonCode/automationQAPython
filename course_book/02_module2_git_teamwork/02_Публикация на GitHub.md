# 2.2 Публикация на GitHub: remote, push, pull, форк

## Зачем это нужно

Локальный репозиторий — это хорошо, но общий репозиторий курса `boilerplate/` живёт на GitHub,
и с этого модуля именно туда попадают все домашние задания в виде Pull Request. Прежде чем
говорить про ветки и PR, нужно понять один механический шаг: как локальная копия проекта
связывается с удалённым репозиторием и обменивается с ним изменениями.

## Теория

GitHub — это хостинг для Git-репозиториев плюс набор инструментов поверх него: Pull Request'ы,
Issues, ревью кода, CI (GitHub Actions). Сам Git не обязан знать про GitHub — это просто ещё один
"удалённый репозиторий", с которым можно синхронизироваться.

### Remote: как Git узнаёт, куда пушить

Локальный репозиторий по умолчанию ни с чем не связан. Связь задаётся явно:

```bash
git remote add origin <URL-репозитория>   # добавить удалённый репозиторий с именем origin
git remote -v                              # посмотреть, какие remote'ы уже подключены
# origin  git@github.com:mike-qa/boilerplate.git (fetch)
# origin  git@github.com:mike-qa/boilerplate.git (push)
```

`origin` — это просто общепринятое имя для "основного" удалённого репозитория, а не
зарезервированное слово: технически remote можно назвать как угодно, но менять конвенцию без
причины не стоит — ты запутаешь и себя, и того, кто будет читать твои команды в чате.

### push и pull — обмен изменениями

```bash
git push -u origin main   # отправить локальную ветку main на origin, запомнить связь (-u)
git push                  # дальше можно просто push, Git помнит, куда
git pull origin main      # забрать изменения с origin и слить их в текущую ветку
```

Флаг `-u` (`--set-upstream`) нужен один раз для каждой ветки — после него Git запоминает, что
локальная `main` связана с `origin/main`, и дальше достаточно голого `git push` без аргументов.

`git pull` — это фактически `git fetch` (скачать изменения) + `git merge` (слить их с твоей
веткой) одной командой. Если хочется сначала посмотреть, что изменилось, не сливая сразу — можно
сделать `git fetch` отдельно и посмотреть `git log origin/main`, прежде чем мёржить.

### git clone vs git init

`init` создаёт **новый** пустой репозиторий там, где до этого Git не было. `clone` делает
противоположное — скачивает **уже существующий** репозиторий целиком, вместе со всей историей
коммитов, и сразу настраивает `origin` на исходный URL:

```bash
git clone <URL-репозитория>
cd <название-репозитория>
git remote -v
# origin  <URL-репозитория> (fetch)
# origin  <URL-репозитория> (push)   — remote origin уже настроен, add делать не нужно
```

Так весь курс, начиная с этого урока, будет получать `boilerplate/` — не `init`, а `clone`
(со своим нюансом форка, см. ниже).

### Форк vs клон

Если у тебя есть права на запись в репозиторий — достаточно `git clone` и `git push` напрямую.
Но у `boilerplate/` — общего репозитория курса — у тебя таких прав нет и не будет: это стартовый
шаблон для всех студентов. Поэтому используется схема **fork**:

1. На GitHub нажимаешь **Fork** на странице `boilerplate` — GitHub создаёт полную копию
   репозитория в твоём аккаунте, с правами на запись.
2. Клонируешь **свой форк** к себе на компьютер (`git clone <URL-твоего-форка>`) — это станет
   remote'ом `origin`.
3. Добавляешь оригинальный `boilerplate` как ещё один remote — по конвенции его называют
   `upstream`:

```bash
git remote add upstream <URL-оригинального-boilerplate>
git remote -v
# origin    <твой форк>       (fetch/push)
# upstream  <оригинальный boilerplate>  (fetch/push)
```

Дальше `origin` — твоя рабочая копия, в неё пушишь свои ветки. `upstream` — используется только
для того, чтобы периодически подтягивать изменения из оригинального репозитория (`git fetch
upstream` + `git merge upstream/main`), если он обновится.

### Авторизация: токен или SSH-ключ

Для авторизации `git push` на GitHub логин/пароль уже не используются — нужен либо личный токен
доступа (Personal Access Token), либо настроенный SSH-ключ. Внешне это видно по формату URL
удалённого репозитория: HTTPS-адрес (`https://github.com/...`) обычно связан с токеном, SSH-адрес
(`git@github.com:...`) — с ключом; оба варианта равноценны, разница только в способе
авторизации. Как именно оформить доступ, зависит от того, что использует твоя когорта/платформа —
уточни у преподавателя, если возникнут проблемы с авторизацией при первом `push`.

## Пример

Форкаем и клонируем общий репозиторий курса:

```bash
# 1. Нажал Fork на странице boilerplate на GitHub — получил свою копию
# 2. Клонирую свой форк
git clone git@github.com:<your-username>/boilerplate.git
cd boilerplate

# 3. Добавляю оригинальный репозиторий как upstream
git remote add upstream git@github.com:<course-org>/boilerplate.git
git remote -v

# 4. Перед началом работы — синхронизирую main с upstream
git fetch upstream
git switch main
git merge upstream/main
git push origin main
```

После этого локальная папка `boilerplate/` содержит актуальную структуру общего репозитория
(`clients/`, `pages/`, `tests/unit|api|ui/`, `conftest.py`, `pytest.ini`) — и готова к тому, чтобы
от неё создать первую рабочую ветку (следующий урок).

## Частые ошибки

- Пытаться сделать `git push` прямо в оригинальный `boilerplate`, а не в свой форк — GitHub вернёт
  ошибку доступа: писать можно только в свой форк.
- Забыть синхронизировать форк с `upstream` перед началом новой задачи — новая ветка создаётся от
  устаревшего `main`, и потом это выливается в лишние конфликты при открытии PR.
- Перепутать `origin` и `upstream` местами при добавлении remote'ов.
- Сделать изменения, забыть `git pull`, и только потом обнаружить, что на сервере уже другая
  версия файла — это тоже источник конфликтов (урок 2.6).

## Мини-задания

1. **Разминка.** Создай новый пустой репозиторий на GitHub (тренировочный, не `boilerplate`).
   Локально в пустой папке сделай `git init`, затем `git remote add origin <URL>` и проверь
   `git remote -v` — без единого коммита или push, только чтобы увидеть, как настраивается связь.
2. **Основное.** Форкни `boilerplate/` в свой GitHub-аккаунт (по-настоящему — это тот же
   репозиторий, с которым ты будешь работать весь курс). Склонируй форк локально, добавь
   `upstream`, указывающий на оригинальный репозиторий, и убедись командой `git remote -v`, что
   оба remote'а настроены правильно.
3. **Ближе к практике.** Синхронизируй только что склонированный форк: `git fetch upstream`,
   `git switch main`, `git merge upstream/main`, `git push origin main`. Даже если изменений нет
   и Git ответит "Already up to date" — важно проиграть саму последовательность команд, потому
   что именно её ты будешь повторять перед каждой новой задачей курса (см. урок 2.9).
4. **Со звёздочкой.** Смоделируй частую ошибку "забыл синхронизировать форк перед новой задачей".
   Возьми тренировочный репозиторий из задания 1, сделай в нём вторую локальную папку-клон (как бы
   "чужой" компьютер) и закоммить в `origin` через неё изменение, которое первая копия не видела.
   Не подтягивая это изменение, создай в первой копии новую ветку от локально устаревшего `main`
   и убедись, что нового коммита в ней нет. Затем синхронизируйся правильно (`git pull origin
   main`) и посмотри, как решилась бы эта же ситуация без лишних сюрпризов.
