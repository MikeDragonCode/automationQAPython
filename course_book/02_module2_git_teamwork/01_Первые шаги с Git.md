# 2.1 Первые шаги с Git: init, add, commit, .gitignore

## Зачем это нужно

Тесты — это код, а код без истории изменений — это код, который страшно менять: непонятно,
что было раньше, кто и зачем что-то поправил, и как откатиться, если новая правка всё сломала.
В реальной работе QA automation engineer видит Git каждый день: смотрит `git log`, чтобы понять,
когда появился баг, использует `git blame`, чтобы найти автора строки, и уж точно не может отдать
код на ревью без ветки и коммитов. Начнём с самого фундамента — трёх команд, без которых Git
вообще не запускается.

## Теория

Git — распределённая система контроля версий: у каждого разработчика есть полная копия истории
проекта на своей машине, а не только на сервере. Это значит, что коммитить, смотреть историю и
откатывать изменения можно офлайн — синхронизация с сервером (GitHub) происходит отдельным шагом
(об этом — в следующем уроке).

### Три состояния файла

У файла в Git есть три состояния:

- **working directory** — то, что ты видишь и редактируешь в IDE прямо сейчас;
- **staging area (индекс)** — "черновик" следующего коммита: сюда ты явно добавляешь то, что
  хочешь зафиксировать;
- **repository** — история коммитов, уже сохранённая в `.git`.

Разделение на staging area — не лишняя сложность, а возможность собрать в один коммит только
связанные изменения, даже если в рабочей папке правок больше. Файл проходит эти состояния
последовательно:

```bash
echo "print('hi')" > app.py
git status
# Untracked files: app.py            — файл существует, но Git о нём ещё не знает

git add app.py
git status
# Changes to be committed: app.py    — файл в staging area, ждёт коммита

git commit -m "Add app.py"
git status
# nothing to commit, working tree clean   — изменение сохранено в истории репозитория
```

### Основные команды

```bash
git init                  # создать новый локальный репозиторий в текущей папке
git status                # что изменилось / что в staging area / что не отслеживается
git add <file>            # добавить конкретный файл в staging area
git add .                 # добавить все изменённые и новые файлы
git commit -m "сообщение" # зафиксировать содержимое staging area как новый коммит
git log --oneline         # короткая история коммитов
```

`git init` запускается один раз на проект — создаёт скрытую папку `.git`, где Git хранит всю
историю. Всё остальное (`add`, `commit`, `log`) выполняется постоянно, по кругу, по мере работы.

### git diff и git restore — посмотреть и отменить

Это отдельная от `add`/`commit` идея: как посмотреть, что именно изменилось, и как откатить
изменение, если оно не понадобилось, — до того как оно попало в staging area или коммит.

```bash
# в app.py поменяли print('hi') на print('hello')
git diff
# -print('hi')
# +print('hello')      — построчный diff рабочей папки относительно последнего коммита

git restore app.py
git diff
# (пусто) — файл вернулся к состоянию последнего коммита, правка отменена безвозвратно
```

### git config: кто автор коммита

Перед первым коммитом Git нужно один раз представить, кто ты:

```bash
git config --global user.name "Имя Фамилия"
git config --global user.email "you@example.com"
```

Эти данные попадают в каждый коммит как автор — именно по ним в PR и в `git log` будет видно,
кто что написал:

```bash
git log -1
# Author: Имя Фамилия <you@example.com>
# Date:   ...
#     Add app.py
```

### .gitignore

Не всё, что лежит в папке проекта, должно попадать в репозиторий: виртуальное окружение,
кэш `pytest`, отчёты Allure, файлы IDE — всё это специфично для конкретной машины и раздувает
репозиторий без пользы. Список исключений задаётся в файле `.gitignore` в корне проекта —
Git просто не будет предлагать добавить эти файлы в staging area. Правило можно указывать как
конкретным именем, так и маской:

```
.venv/          # вся папка целиком
*.pyc           # любой файл с этим расширением, в любой папке
.env
```

Важная деталь: `.gitignore` действует только на файлы, которые Git **ещё не отслеживает**. Если
файл уже был закоммичен раньше, добавление его в `.gitignore` задним числом ничего не изменит —
его нужно сначала явно убрать из-под отслеживания (`git rm --cached`), это разбирается в
мини-заданиях ниже.

### Что делает коммит «хорошим»

Хороший коммит — маленький и про одно: одна логическая правка, а не "накопил за неделю и залил
разом". Сообщение коммита пишется в повелительном наклонении и коротко объясняет суть:

```bash
git commit -m "Add slugify function"   # хорошо: понятно, что сделано, без раскрытия деталей diff
git commit -m "fix"                    # плохо: что именно исправлено — неизвестно
```

Через месяц по `git log --oneline` с сообщениями второго типа невозможно восстановить, что вообще
происходило в проекте — а с сообщениями первого типа это тривиально.

## Пример

Представим, что ты только что написал `utils/string_utils.py` и тест к нему (как в модуле 1) и
хочешь зафиксировать это как первый коммит проекта:

```bash
cd my_practice_repo
git init

git status
# видно: utils/, tests/, .venv/, __pycache__/ — всё как untracked
```

Сначала — `.gitignore`, точно такой же принцип использует `boilerplate/.gitignore` в общем
репозитории курса:

```
.venv/
__pycache__/
*.pyc
.pytest_cache/
allure-results/
allure-report/
.env
.idea/
.vscode/
```

Теперь `git status` больше не предлагает добавить `.venv/` и кэш — и можно спокойно добавлять всё
остальное:

```bash
git add .gitignore
git commit -m "Add .gitignore"

git add utils/string_utils.py tests/unit/test_string_utils.py
git commit -m "Add string utils with is_palindrome, slugify and tests"

git log --oneline
# a1b2c3d Add string utils with is_palindrome, slugify and tests
# f4e5d6c Add .gitignore
```

Два коммита — два самостоятельных смысловых шага, а не одна большая свалка изменений.

## Частые ошибки

- Сделать `git add .` до того, как появился `.gitignore` — в репозиторий улетают `.venv/` и
  `__pycache__/`, и потом их приходится вычищать отдельным коммитом.
- Сообщения коммитов вида `fix`, `wip`, `update` — через месяц по такой истории невозможно понять,
  что вообще произошло.
- Один гигантский коммит на всю неделю работы — сложно ревьюить, сложно откатить только одну
  часть, если что-то одно оказалось неудачным.
- Коммитить не глядя, не проверив `git status` перед `git add` — так в репозиторий попадают
  случайные файлы (например, настройки IDE, если забыли `.gitignore`).

## Мини-задания

1. **Разминка.** В пустой папке создай один файл, но не коммить его. Пройди все три состояния по
   очереди и после каждого шага смотри `git status`: файл как untracked → `git add` → файл в
   staging area → `git commit` → рабочая папка чистая. Убедись, что вывод `git status` меняется
   ровно так, как описано в теории.
2. **Основное.** Создай локальную папку с парой Python-файлов (можно взять свои решения из
   модуля 1). Инициализируй в ней Git-репозиторий, добавь `.gitignore` по образцу из примера выше
   и сделай три отдельных осмысленных коммита: например, отдельно `.gitignore`, отдельно функцию,
   отдельно тест к ней. Проверь результат через `git log --oneline`.
3. **Ближе к практике.** У тебя в рабочей папке одновременно оказались две несвязанные правки:
   исправление бага в одной функции и добавление докстринга в другую. Не смешивай их в один
   коммит — используй `git add <конкретный файл>` дважды, чтобы получить два отдельных
   осмысленных коммита, и перед каждым коммитом проверь `git diff` (или `git status`), что в
   staging area именно то, что ты ожидаешь.
4. **Со звёздочкой.** Специально наступи на грабли из "Частых ошибок": сделай `git add .` и
   коммит **до** того, как создал `.gitignore`, — так, чтобы папка `__pycache__/` (запусти любой
   скрипт, чтобы она появилась) попала в репозиторий. Затем создай `.gitignore` и убедись, что
   `git status` больше не помогает — файл уже отслеживается. Исправь это командой
   `git rm -r --cached __pycache__` (файлы останутся на диске, но перестанут отслеживаться) и
   закоммить исправление отдельным коммитом с понятным сообщением.
