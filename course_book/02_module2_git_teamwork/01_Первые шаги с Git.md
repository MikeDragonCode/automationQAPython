# 2.1 Первые шаги с Git: init, add, commit, .gitignore

## Зачем это нужно

Тесты — это код, а код без истории изменений — это код, который страшно менять: непонятно,
что было раньше, кто и зачем что-то поправил, и как откатиться, если новая правка всё сломала.
В реальной работе QA automation engineer видит Git каждый день: смотрит `git log`, чтобы понять,
когда появился баг, использует `git blame`, чтобы найти автора строки, и уж точно не может отдать
код на ревью без ветки и коммитов. Начнём с самого фундамента — трёх команд, без которых Git
вообще не запускается.

## Теория

Git — распределённая система контроля версий: у каждого разработчика есть полная копия истории
проекта на своей машине, а не только на сервере. Это значит, что коммитить, смотреть историю и
откатывать изменения можно офлайн — синхронизация с сервером (GitHub) происходит отдельным шагом
(об этом — в следующем уроке).

У файла в Git есть три состояния:

- **working directory** — то, что ты видишь и редактируешь в IDE прямо сейчас;
- **staging area (индекс)** — "черновик" следующего коммита: сюда ты явно добавляешь то, что
  хочешь зафиксировать;
- **repository** — история коммитов, уже сохранённая в `.git`.

Разделение на staging area — не лишняя сложность, а возможность собрать в один коммит только
связанные изменения, даже если в рабочей папке правок больше.

Основные команды:

```bash
git init                  # создать новый локальный репозиторий в текущей папке
git status                # что изменилось / что в staging area / что не отслеживается
git add <file>            # добавить конкретный файл в staging area
git add .                 # добавить все изменённые и новые файлы
git commit -m "сообщение" # зафиксировать содержимое staging area как новый коммит
git log --oneline         # короткая история коммитов
git diff                  # что изменилось в рабочей папке относительно последнего коммита
git restore <file>        # отменить незакоммиченные изменения в файле
```

Перед первым коммитом Git нужно один раз представить, кто ты:

```bash
git config --global user.name "Имя Фамилия"
git config --global user.email "you@example.com"
```

Эти данные попадают в каждый коммит как автор — именно по ним в PR будет видно, кто что написал.

### .gitignore

Не всё, что лежит в папке проекта, должно попадать в репозиторий: виртуальное окружение,
кэш `pytest`, отчёты Allure, файлы IDE — всё это специфично для конкретной машины и раздувает
репозиторий без пользы. Список исключений задаётся в файле `.gitignore` в корне проекта —
Git просто не будет предлагать добавить эти файлы в staging area.

Хороший коммит — маленький и про одно: одна логическая правка, а не "накопил за неделю и залил
разом". Сообщение коммита пишется в повелительном наклонении и коротко объясняет суть:
`Add slugify function`, а не `fix`, `wip` или `changes`.

## Пример

Представим, что ты только что написал `utils/string_utils.py` и тест к нему (как в модуле 1) и
хочешь зафиксировать это как первый коммит проекта:

```bash
cd my_practice_repo
git init

git status
# видно: utils/, tests/, .venv/, __pycache__/ — всё как untracked
```

Сначала — `.gitignore`, точно такой же принцип использует `boilerplate/.gitignore` в общем
репозитории курса:

```
.venv/
__pycache__/
*.pyc
.pytest_cache/
allure-results/
allure-report/
.env
.idea/
.vscode/
```

Теперь `git status` больше не предлагает добавить `.venv/` и кэш — и можно спокойно добавлять всё
остальное:

```bash
git add .gitignore
git commit -m "Add .gitignore"

git add utils/string_utils.py tests/unit/test_string_utils.py
git commit -m "Add string utils with is_palindrome, slugify and tests"

git log --oneline
# a1b2c3d Add string utils with is_palindrome, slugify and tests
# f4e5d6c Add .gitignore
```

Два коммита — два самостоятельных смысловых шага, а не одна большая свалка изменений.

## Частые ошибки

- Сделать `git add .` до того, как появился `.gitignore` — в репозиторий улетают `.venv/` и
  `__pycache__/`, и потом их приходится вычищать отдельным коммитом.
- Сообщения коммитов вида `fix`, `wip`, `update` — через месяц по такой истории невозможно понять,
  что вообще произошло.
- Один гигантский коммит на всю неделю работы — сложно ревьюить, сложно откатить только одну
  часть, если что-то одно оказалось неудачным.
- Коммитить не глядя, не проверив `git status` перед `git add` — так в репозиторий попадают
  случайные файлы (например, настройки IDE, если забыли `.gitignore`).

## Мини-задание

Создай локальную папку с парой Python-файлов (можно взять свои решения из модуля 1). Инициализируй
в ней Git-репозиторий, добавь `.gitignore` по образцу из примера выше и сделай три отдельных
осмысленных коммита: например, отдельно `.gitignore`, отдельно функцию, отдельно тест к ней.
Проверь результат через `git log --oneline`.
