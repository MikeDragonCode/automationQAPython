# 2.5 Как оформить понятный PR

## Зачем это нужно

PR, который ревьюер понимает за две минуты, получает фидбек в тот же день. PR на 600 строк без
описания либо неделю лежит без внимания, либо ревьюер бегло пролистывает его и пропускает баги.
Оформление PR — это не бюрократия, а способ уважать время того, кто будет твой код читать —
а по кругу и своё собственное, когда ревьюером окажешься ты.

## Теория

### Одна задача — одна ветка — один PR

Это правило уже звучало в уроках про ветки, но именно здесь становится понятно, зачем оно нужно:
маленький PR можно просмотреть целиком и удержать в голове. PR, который чинит баг, добавляет фичу
и заодно переформатировал соседний файл — это уже три разных PR, слепленных в один, и ревьюеру
придётся распутывать, что из этого относится к делу.

### Маленький diff — осознанный выбор

Чем больше строк в PR, тем ниже качество ревью: внимание ревьюера конечно, и после определённого
объёма правки просто "одобряют не глядя". Если задача объективно большая — её стоит разбить на
несколько последовательных PR, каждый из которых уже сам по себе рабочий и осмысленный шаг.

### Понятный заголовок

Заголовок — это то, что видно в списке PR и в истории `main` после merge, часто без открытия
самого PR. Он должен отвечать на вопрос "что сделано", а не описывать процесс работы:

| Заголовок | Оценка |
|---|---|
| `Add reverse_words util with tests` | хорошо — понятно, что и где |
| `Fix status code check in UsersClient` | хорошо — понятно, какой баг и где |
| `update` | плохо — что именно обновлено? |
| `fix bug` | плохо — какой из багов? |
| `changes after review` | плохо — итоговый заголовок PR виден в истории `main` и через полгода, "после ревью" там уже ничего не скажет |

### Описание — не для галочки

Минимальный полезный шаблон:

```markdown
## Что сделано
Добавлена функция reverse_words в utils/string_utils.py + тесты в tests/unit/test_string_utils.py.

## Почему / зачем
Нужна для тренировки работы с git flow курса (модуль 2, домашнее задание).

## Как проверить
pytest -m unit -k reverse_words
```

### Скриншоты для UI-изменений

Для UI-изменений (актуально с модуля 4) в описание стоит добавить скриншот "было/стало" —
ревьюеру не придётся поднимать ветку локально, чтобы увидеть результат своими глазами.

### Самопроверка перед тем, как звать ревьюера

Собственный diff стоит один раз просмотреть на GitHub перед тем, как просить ревью: убрать
отладочные `print`, закомментированный старый код, случайно попавшие в коммит файлы (снова привет
`.gitignore` из урока 2.1). Это экономит ревьюеру время на то, что ты и сам можешь заметить —
пятиминутный самостоятельный просмотр обычно снимает половину будущих комментариев.

## Пример

PR в `boilerplate/`, который добавляет новую функцию по аналогии с существующими в
`utils/string_utils.py` — ровно так, как это описано в правилах самого репозитория
(`boilerplate/README.md`: "Одна задача — одна ветка — один PR", "В описании PR — что сделано и как
проверить"):

**Title:** `Add reverse_words util with unit tests`

**Description:**

```markdown
## Что сделано
Добавлена функция `reverse_words(text: str) -> str` в utils/string_utils.py —
меняет порядок слов в строке местами. Добавлены параметризованные тесты
в tests/unit/test_string_utils.py по аналогии с существующими тестами модуля.

## Как проверить
pytest -m unit -k reverse_words

## Дополнительно
Ничего в существующих файлах, кроме добавленных строк, не менялось.
```

Такой PR ревьюер прочитает за минуту, поймёт объём изменений по одному предложению и сразу
запустит нужную команду вместо того, чтобы гадать, что тестировать.

## Частые ошибки

- В один PR попадает рефакторинг соседнего файла "заодно, раз уж открыл" — вперемешку с основной
  задачей.
- Пустое описание или один заголовок без единого пояснения.
- Diff на сотни строк из-за автоформатирования IDE, которое переформатировало весь файл, а не
  только изменённые строки (стоит отключить агрессивное автоформатирование для чужих файлов или
  форматировать точечно).
- PR отправлен на ревью без единого локального запуска тестов — CI (или ревьюер) находит то, что
  можно было найти за 10 секунд самому.

## Мини-задания

1. **Разминка.** Дано словесное описание изменения: "добавил проверку формата email и тесты к
   ней". Напиши для него один хороший заголовок PR (в духе `Add email format validation with
   tests`) и рядом — один явно плохой вариант (`update`, `fix` и т.п.), чтобы на контрасте увидеть
   разницу.
2. **Основное.** Возьми одно из своих решений модуля 1 (соло-задание) и оформи для него
   "PR-описание" по шаблону выше — Title + Что сделано / Почему / Как проверить — как будто это
   реальный PR. Это тренирует формулировать суть изменения кратко ещё до того, как есть настоящий
   общий репозиторий, в который можно её отправить.
3. **Ближе к практике.** Представь diff, который вперемешку содержит: (а) новую функцию с тестом,
   (б) рефакторинг соседней функции "заодно, раз уж открыл файл", (в) исправление опечатки в
   README. Опиши, как правильно оформить Title и Description для PR, который должен содержать
   **только** пункт (а) — и что стоит сделать с (б) и (в) до того, как звать ревьюера (правило
   "одна задача — один PR" из теории).
4. **Со звёздочкой.** Найди у себя (или составь на словах) diff, который сильно раздут
   автоформатированием IDE: одна реально изменённая строка внутри файла, который целиком
   переформатирован (отступы, кавычки). Опиши, как отличить в Files changed "настоящее" изменение
   от косметического, и как поступить, чтобы будущий PR не создавал такой шум — отключить
   агрессивное автоформатирование для чужих файлов или форматировать точечно.
