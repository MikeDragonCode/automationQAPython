# Style guide для уроков курса

Единый формат — чтобы весь курс читался как одна книга, а не как склейка трёх разных.

## Структура файла урока

```markdown
# N.M. Название урока

## Зачем это нужно
2–4 предложения: где это встретится в реальной работе QA automation engineer.

## Теория
Объяснение своими словами (не копипаста из источника), с минимумом воды.
Код — во **fenced code block** с указанием языка (```python, ```bash, ```yaml).

## Пример
Рабочий, самодостаточный пример кода. Если это про boilerplate — показать,
как метод/тест встраивается в существующую структуру `boilerplate/`, а не
как отдельный файл в вакууме.

## Частые ошибки
2–4 пункта: что обычно ломается у новичков на этой теме.

## Мини-задание
Небольшая практическая задача на 10–20 минут, привязанная к теме урока.

## Домашнее задание
(указывается только в последнем уроке недели/темы)
Чёткая формулировка + критерии "готово" (что именно проверяется).
Начиная с модуля 2 — явно указано, что сдаётся PR-ом в общий репозиторий.
```

## Язык и тон

- Русский язык, на "ты", без канцелярита.
- Термины — по-английски там, где так принято в индустрии (fixture, assert, locator, pipeline), не изобретать русские кальки.
- Код и имена переменных/функций — только на английском.
- Никаких выдуманных фактов про инструменты — если не уверены в деталях версии/API, пишем общий принцип, а не конкретную цифру.

## Нумерация

`N.M` — модуль.урок (например `3.2` = модуль 3, второй урок). Внутри модуля недели — просто подпапки `weekX/`.

## Как работает переиспользование источников

- Материал из трёх исходных курсов **переписывается**, а не копируется дословно — сохраняем идею, примеры адаптируем под общий репозиторий и единый стиль.
- Если пример кода в источнике использует несовместимую с курсом библиотеку (например HTTPX там, где у нас `requests`), — адаптируем на лету, сохраняя суть, но не оставляем несоответствий.
- Исходные курсы (`stepik-*`) — только на чтение, в них ничего не меняем.
