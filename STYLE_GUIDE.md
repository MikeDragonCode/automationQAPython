# Style guide для уроков курса

Единый формат — чтобы весь курс читался как одна книга, а не как склейка трёх разных.

## Структура файла урока

```markdown
# N.M. Название урока

## Зачем это нужно
2–4 предложения: где это встретится в реальной работе QA automation engineer.

## Теория
Объяснение своими словами, с минимумом воды, но **не в ущерб полноте** — см. "Объём теории" ниже.
Код — во **fenced code block** с указанием языка (```python, ```bash, ```yaml).
Каждая нетривиальная идея сопровождается отдельным маленьким примером кода прямо
в теории, а не только одним общим примером в конце урока.

## Пример
Более крупный, рабочий, самодостаточный пример кода, собирающий тему воедино.
Если это про boilerplate — показать, как метод/тест встраивается в существующую
структуру `boilerplate/`, а не как отдельный файл в вакууме.

## Частые ошибки
2–4 пункта: что обычно ломается у новичков на этой теме.

## Мини-задания
**3–4 задания на тему, от простого к сложному** (не одно) — см. раздел
"Прогрессия мини-заданий" ниже.

## Домашнее задание
(указывается только в последнем уроке недели/темы)
Чёткая формулировка + критерии "готово" (что именно проверяется).
Начиная с модуля 2 — явно указано, что сдаётся PR-ом в общий репозиторий.
```

## Объём теории

Аудитория курса — QA manual инженеры, среди которых не все уверенно чувствуют
себя даже с JSON. Слишком сжатая теория — главный риск: студент кое-как
проходит модули 0–3, а на модуле 4 (Playwright + POM, где нужно бегло читать
чужой код) спотыкается не о Playwright, а о непонятые основы Python из модуля 0.
Поэтому:

- Лучше на 30% длиннее и с одним лишним примером, чем компактно, но с пробелом
  в понимании.
- Не сваливай всю тему одним абзацем — дроби её на подзаголовки (`###`) внутри
  "Теории", каждый со своим маленьким примером кода.
- Если тема состоит из нескольких независимых идей (например, "срезы строк" и
  "методы строк") — это разные подзаголовки с разными примерами, а не одно
  предложение с перечислением через запятую.
- Лучше пусть студент дольше идёт к модулю 4, но уверенно, чем быстрее — но с
  пробелами, которые всплывут именно там, где отступать уже некуда.

## Прогрессия мини-заданий

Вместо одного "Мини-задания" на урок — **3–4 отдельных задания**, пронумерованных
и растущих по сложности:

1. **Разминка** — тренирует ровно один факт из "Теории", изолированно, почти
   один в один повторяет пример из теории с другими данными.
2. **Основное** — комбинирует 2–3 факта из этого урока (как в текущем формате
   "одно мини-задание на урок").
3. **Ближе к практике** — сценарий, похожий на то, с чем реально сталкивается
   QA automation инженер (тестовые данные, статус-коды, проверка структуры).
4. *(если тема достаточно богатая)* **Со звёздочкой** — задание с подвохом или
   edge case, который явно упомянут в "Частых ошибках" этого урока.

Если тема короткая и честно не тянет на 4 независимых уровня сложности — делай
3, но не меньше. Каждое задание — самостоятельная, отдельно проверяемая
формулировка (не "а еще сделай..." одним предложением после первого задания).

## Язык и тон

## Язык и тон

- Русский язык, на "ты", без канцелярита.
- Термины — по-английски там, где так принято в индустрии (fixture, assert, locator, pipeline), не изобретать русские кальки.
- Код и имена переменных/функций — только на английском.
- Никаких выдуманных фактов про инструменты — если не уверены в деталях версии/API, пишем общий принцип, а не конкретную цифру.

## Нумерация

`N.M` — модуль.урок (например `3.2` = модуль 3, второй урок). Внутри модуля недели — просто подпапки `weekX/`.

## Проверочные вопросы урока (для ридера)

Каждый обычный урок (не `00_overview.md`, не `99_*.md`) сопровождается файлом
`<то же имя>.quiz.json` рядом с уроком — набор из **4–6 вопросов** с выбором
ответа, которые ридер показывает по одному, друг за другом, как условие
разблокировки следующего урока.

Формат:

```json
{
  "questions": [
    {
      "question": "Текст вопроса — строго по содержимому ЭТОГО урока",
      "options": ["вариант A", "вариант B", "вариант C", "вариант D"],
      "correct": 2,
      "explain": "1-2 предложения, почему это верный ответ (показывается после правильного ответа)"
    }
  ]
}
```

Правила:
- От 4 до 6 вопросов на урок, у каждого ровно 4 варианта и ровно один верный (`correct` — индекс с 0).
- Вопросы должны бить в **разные** аспекты урока (не переформулировки одного и того же факта пятью способами) — если в уроке есть несколько идей/шагов/частых ошибок, каждый хороший кандидат на отдельный вопрос.
- Каждый вопрос решаем строго по материалу этого урока — не по будущим темам и не по общей эрудиции.
- Проверяем то, что реально понадобится QA automation инженеру (решение, частую ошибку, "почему так, а не иначе") — не дату выхода Python, не синтаксическую экзотику мимо практики курса.
- Неверные варианты — правдоподобные ошибки новичка, а не абсурдный отвлекающий мусор.
- Уровень сложности = уровень изложения теории в уроке: не проще и не сложнее.
- Если в уроке реально мало самостоятельного материала для 4 разных вопросов (короткий, обзорный урок) — можно 3, но это исключение, не норма.

## Playground: код, который реально проверяется (только модуль 0)

Pyodide (Python в браузере, без бэкенда) может выполнять только чистый Python без
сети, файлового I/O и настоящего браузера — раннер напрямую вызывает функции
`test_...` из `tests`, без реального pytest. Поэтому файл `<то же имя>.exercise.json`
существует **только для уроков модуля 0** (Python-база, чистые функции без внешних
зависимостей). Модуль 1 (pytest) уже требует настоящих pytest-механизмов —
fixtures, conftest, маркеры — которые этот раннер не воспроизводит, поэтому там
(как и в модулях 2–7: Git, реальные HTTP-запросы, Playwright, Allure, CI) мини-задания
остаются только текстовыми, без автопроверки в браузере. "Прогрессия мини-заданий"
(3–4 задания на урок, см. выше) обязательна для уроков **всех** модулей — `exercise.json`
для модуля 0 лишь дополнительно даёт этим заданиям исполняемую форму.

Формат — **массив из 3–4 заданий**, один к одному повторяющих порядок и
формулировки из раздела "Мини-задания" в `.md`:

```json
{
  "exercises": [
    {
      "prompt": "Формулировка задания 1 (разминка) — как в Мини-заданиях, но для интерфейса кода",
      "starter": "def is_adult(age):\n    # твой код здесь\n    pass\n",
      "tests": "def test_adult():\n    assert is_adult(20) is True\n\ndef test_minor():\n    assert is_adult(10) is False\n"
    },
    {
      "prompt": "Формулировка задания 2 (основное)",
      "starter": "...",
      "tests": "..."
    }
  ]
}
```

Как это работает: в ридере каждое задание — отдельный редактор со своей кнопкой
"Запустить"; код студента и `tests` этого же задания выполняются в одном
пространстве имён — функции/классы из `tests` обращаются к тому, что определил
студент, напрямую, без импорта. Раннер находит в `tests` все функции с именем
`test_...` и запускает каждую отдельно, ловя `assert`. Урок засчитан, когда
пройдены **все** задания массива (задания не блокируют друг друга — студент может
решать в любом порядке, но по умолчанию идёт по порядку от простого к сложному).

Правила:
- 3–4 элемента массива, **в том же порядке и с той же формулировкой**, что и
  пункты 1–4 из "Мини-заданий" этого урока — не придумывай новое задание отдельно
  для кода, переводи в исполняемую форму то, что уже написано в `.md`.
- `starter` каждого задания — ровно тот код, который увидит студент при открытии
  (обычно сигнатура функции/класса с `pass` или заглушкой).
- `tests` — 2-6 функций `test_...`, каждая с одним чётким `assert` (или парой
  связанных assert на один и тот же аспект). Проверяй ровно то поведение, которое
  описано в соответствующем мини-задании — не больше и не меньше.
- Название функции/класса в `starter` должно точно совпадать с тем, что вызывают `tests`.
- Каждое следующее задание в массиве может переиспользовать функции/классы,
  написанные в `starter` предыдущего (продолжая тему), либо быть независимым —
  но их `starter` не связаны технически (каждое задание выполняется в собственном
  пространстве имён), так что если задание 2 опирается на код из задания 1,
  повтори нужный код в `starter` задания 2.
- Никаких внешних библиотек, файлового I/O или сети — Pyodide это либо не потянет,
  либо потянет ненадёжно. Чистые функции на стандартной библиотеке.
- Сообщения об ошибке ассертов должны быть человекочитаемыми (второй аргумент assert),
  чтобы студент понимал, что именно не так, а не только "AssertionError".

## Авторский текст

- Весь материал пишется своими словами, а не копируется откуда-либо — примеры сразу адаптированы под общий репозиторий и единый стиль курса.
- Если пример кода тянет за собой несовместимую с курсом библиотеку (например что-то, где у нас принят `requests`) — адаптируем на лету, сохраняя суть, но не оставляем несоответствий.
